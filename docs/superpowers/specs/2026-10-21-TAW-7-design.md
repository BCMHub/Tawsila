## 1. Purpose, decisions and boundaries

A new user creates or regains a Tawsila account with Google or Apple, and only then reaches the app. Sign-up asks for no phone number. A verified phone is required later, before the first ride post or request (TAW-5).

**Owner decisions (requirements):**
1. Google or Apple authentication is required before browsing; there is no guest, anonymous or phone sign-up.
2. Platform policy: iOS offers Google and Apple; Android offers Google only; Apple on Android is deferred.
3. Google uses the **native** library (`@react-native-google-signin/google-signin`) with `signInWithIdToken`; Apple uses the native flow (`expo-apple-authentication`) with `signInWithIdToken`. Both need development builds (not Expo Go) from the start.
4. The session is stored in `expo-secure-store` through a chunked adapter.
5. The minimal account row is created by a transactional trigger on `auth.users`; there is no registration function and no local registration marker.
6. Supabase's default automatic linking of identities with the same verified email is accepted; the application adds no linking logic.
7. `needs_profile` is defined by this spec (section 4).
8. TAW-4 (profile, 18+, consent), TAW-5 (phone verification, ride gating) and TAW-6 are not implemented here, and their amendments need the owner's separate approval.

**Out of scope:** phone number and OTP at sign-up; email or password sign-in; account deletion, logout and Apple token revocation (a separate card is required before any store submission); Figma design work (a separate design card); production deployment; store setup. The cross-card product flow (stages D to H) is informative, in `2026-10-24-signup-onboarding-flow-informative.md`, and is not part of this gate.

**Constraints that stay:** the TAW-2 Egypt privacy and region gates are not waived; only test identities and a test Supabase project are used (sections 7 and 8).

## 2. Flows (stages A to C of the product flow)

**A. Welcome.** No valid session: show the provider buttons for the platform (Google on both, Apple on iOS only). One attempt at a time: while an attempt is running the buttons are disabled.

**B. Provider authentication.**
- **Apple (iOS):** `AppleAuthentication.signInAsync` with name and email scopes, then `supabase.auth.signInWithIdToken({ provider: 'apple', token: identityToken })`. Replay protection (a nonce) must be enabled end to end: Supabase validates the nonce when one is supplied, the Supabase guide's Flutter example sends the SHA-256 hash to Apple and the raw value to Supabase, and whether `expo-apple-authentication` forwards the nonce as given is **UNVERIFIED**; the plan verifies it on a device and records the result. Call `isAvailableAsync()` first. Apple returns the name only on the first authorization, so the client stores it with `supabase.auth.updateUser({ data: { full_name, given_name, family_name } })` straight after the first success. Nothing is copied to `accounts`; TAW-4 may offer it as a prefill the user confirms.
- **Google (iOS and Android):** `GoogleSignin.configure` (web client ID, plus the iOS client scheme as the library requires), `signIn`, then `supabase.auth.signInWithIdToken({ provider: 'google', token: idToken })`. Supabase's nonce check stays on; if the chosen library version cannot supply a nonce, turning the check off is a security trade-off that needs the owner's explicit approval, it is not decided here. Whether the library's free tier is adequate for Android (the paid tier is said to include the Credential Manager APIs) is **UNVERIFIED** and an owner prerequisite.
- **Cancellation, denial, unavailability, a second tap while in progress and an unexpected provider error** end the attempt and return to Welcome with no session change and no route change. Cancellation shows no error; real failures show a short non-sensitive retry message. No provider event alone opens a protected route.

**C. Account read.** With a valid session the app reads the user's own `accounts` row. If it is missing (a trigger bug or a manual deletion) the app fails closed to `account_provision_error` with a retry; it never creates the row from the client and never opens the tabs.

## 3. Data model and authorization

`public.accounts`:

| Column | Type | Rule |
|---|---|---|
| `user_id` | `uuid` primary key, references `auth.users(id)` on delete cascade | the Supabase user |
| `phone_e164` | `text` null | null until TAW-5; when present, `^\+[1-9][0-9]{7,14}$` |
| `phone_verified` | `boolean not null default false` | settable only by trusted server code (TAW-5) |
| `profile_completed_at` | `timestamptz` null | settable only by trusted server code (TAW-4) |
| `created_at` | `timestamptz not null default now()` | |

- Constraints: `check (not phone_verified or phone_e164 is not null)`; a partial unique index on `phone_e164 where phone_verified` (verified numbers are unique; unverified numbers never grant anything).
- **Trigger:** `public.handle_new_user()` is `security definer`, `set search_path = ''`, `after insert on auth.users for each row`, and does one plain insert of `(user_id)` into `accounts`. It does not swallow errors: **a failure fails the sign-up** (Supabase surfaces a generic "Database error saving new user"; the Supabase docs warn that a failing trigger blocks sign-ups, so it stays minimal and tested). It fires only when an `auth.users` row is created, so returning sign-ins and identity linking to an existing user do not touch it. This replaces any "lost response" reconciliation: the row exists in the same transaction as the user.
- **RLS:** enabled; one `select` policy (`user_id = (select auth.uid())`); no insert, update or delete policy and no privilege for `anon` or `authenticated` beyond `select` on the own row. `phone_verified` and `profile_completed_at` are therefore not client-writable; TAW-4 and TAW-5 add their own `security definer` functions.
- Nothing exposes `phone_e164`, provider tokens or provider email to other users, or copies provider email or name into a public profile.

## 4. Routing, session and the `needs_profile` seam

**States (derived, never persisted):** `signed_out`, `authenticating` (a provider attempt is running), `account_provision_error`, `needs_profile`, `ready_to_browse`. `needs_phone_verification` is a contextual gate on the ride action (TAW-5), not a global state.

**Derivation:** no SDK session gives `signed_out`; a session with no own row gives `account_provision_error`; a row with `profile_completed_at is null` gives `needs_profile`; a row with `profile_completed_at` set gives `ready_to_browse`. The tabs open only in `ready_to_browse`. There is no local marker: the SDK session plus the server row are the sources of truth, and the first render after a cold start waits for the session read and the row read with a bounded timeout, showing a loading screen (never the tabs) and, on timeout with a stored session, a retry state (never a sign-out).

**`needs_profile` seam (definition):** TAW-7 only reads `profile_completed_at`; nothing in TAW-7 sets it, so `needs_profile` is where a new user stops until TAW-4 delivers the profile and consent steps and a trusted function that sets `profile_completed_at`. For testing, a **dev-only bypass** exists: in `__DEV__` builds the debug screen offers "Skip profile (dev)", which sets an in-memory flag that makes the router treat the signed-in user as `ready_to_browse`; it is not persisted, writes nothing to the database, and does not exist in production builds. TAW-7 does not claim that browsing is production-ready.

**Session handling (requirements, any implementation):**
1. The **SDK session is the authority.** The app follows what auth-js actually holds; it never keeps a signed-in state against the SDK.
2. Auth events (`INITIAL_SESSION`, `SIGNED_IN`, `SIGNED_OUT`, `TOKEN_REFRESHED`) and the app's own inputs are handled **one at a time**; a handler finishes before the next starts.
3. **Temporary failures** (network, HTTP 5xx, a timeout) never end a session and show a connection notice. **Terminal failures** (an invalid or revoked refresh token, a deleted user) end it exactly once and return to `signed_out`.
4. `AuthRefreshDiscardedError` (auth-js 2.118: the server rotated the token but the client deliberately did not store it because a concurrent sign-out changed storage) is a successful no-op: no retry, no sign-out of its own (recognised with `isAuthRefreshDiscardedError`). `refreshSession` is never called inside a `TOKEN_REFRESHED` handler.
5. Every network call the app starts for session or account reads has a timeout; an abandoned call's late result is ignored, and an expired timeout also stops it from starting further session-changing work.
6. After unmount nothing writes storage or ends a session; the app-wide client singleton is never `dispose()`d.
7. Refresh runs only in the foreground (`startAutoRefresh` when the app is active, `stopAutoRefresh` otherwise); `detectSessionInUrl` is false.
8. **Storage:** the session is stored through a chunked `expo-secure-store` adapter: entries stay under the historical 2 KB platform limit and values must be ASCII. Replacement is **generation-based**: a write stores all chunks under a fresh generation id and only then writes the small manifest (`{ generation, count }`) that points to them; reads follow the manifest only, so a replacement interrupted at any point leaves the previous manifest and its chunks intact and readable, and chunks of an unreferenced generation are never read; the previous generation is deleted only after the new manifest is written; a manifest whose chunks are missing reads as no session; deleting removes the manifest first. Adapter operations are serialized (one at a time). iOS keychain data can survive an uninstall, so a stale session may exist after a reinstall; the app treats it like any session (it is validated by the first row read).

## 5. Identity linking and duplicates

Automatic linking of identities that share a verified email is a Supabase default and is accepted; its Google, Apple and private-relay specifics and whether it can be turned off are **UNVERIFIED** (the plan records the observed behaviour). Different emails, including an Apple private-relay address, stay separate accounts. Manual cross-email linking would be a separate reviewed feature. A second account that later tries to verify a number already verified elsewhere is TAW-5's collision case (informative document).

## 8. Privacy and abuse

Provider ID tokens and OAuth tokens are never stored in application tables, logs or analytics; Supabase keeps what its own operation needs. No provider email or name is shown to other users or copied to a public profile. Only test identities are used until the Egypt privacy and region gates are passed. Abuse controls rely on Supabase Auth's rate limits and settings for sign-ins; there is no anonymous sign-up and no cleanup job; OTP and SMS abuse controls belong to TAW-5.

## 9. Tests and evidence

By blast radius, written before the implementation:
1. **Database (pgTAP, local stack or the hosted test project):** the trigger creates exactly one row per new auth user in the same transaction; a forced failure of the row insert (for example a temporary `check (false)` constraint) aborts the `auth.users` insert; returning sign-in and identity linking create no row; RLS lets a user read only their own row; direct insert, update and delete are denied; `phone_verified` and `profile_completed_at` cannot be written by the client; `phone_verified` requires a phone; verified numbers are unique and unverified duplicates are allowed; the E.164 check holds.
2. **Session and routing (Jest):** the storage adapter survives a failed replacement of an existing session at every write boundary (the old session stays readable, no mixed chunks, a missing chunk reads as no session, operations run one at a time); state derivation for every combination of session and row; no tabs on a provider event alone; `needs_profile` is terminal without the dev bypass and `ready_to_browse` with it, and the bypass does not exist when `__DEV__` is false; temporary failures keep the session; a terminal failure ends it once; `AuthRefreshDiscardedError` is a no-op; a late result from an abandoned call does not undo a newer state; nothing happens after unmount; the storage adapter round-trips, chunks and rejects partial writes.
3. **Provider handlers (Jest, mocked libraries):** success, cancellation codes, denial, unavailable provider, a second tap and a duplicate or replayed authentication result (one attempt, one session), a missing or malformed ID token (no session is created and the attempt ends on Welcome), an unexpected error, for Google and Apple; the Apple name is stored once; no phone number or OTP is requested; a static check finds no phone sign-in or OTP call in application code. OAuth `state` validation does not apply: the native ID-token flows have no application redirect callback.
4. **Auth integration (local stack or the hosted test project, with test tokens where the provider allows, otherwise in the device smoke tests):** an ID token with a wrong nonce is rejected by Supabase when a nonce is in use; a returning identity signs in to the same user and creates no second account row; two first sign-ins for different new users each create exactly one row (concurrent inserts into `auth.users` produce one row per user and the primary key prevents a second).
5. **Device and provider smoke tests (only where the prerequisites in section 7 exist):** first sign-in and returning sign-in with a test Google and a test Apple identity on a physical iPhone and a development build; Google on an Android emulator or device. Unrun tests are never reported as passed.
6. The standing checks: install, `tsc`, lint, unit tests, both exports, expo-doctor.
