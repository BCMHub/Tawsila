Authoring card: TAW-8 (scope revision 2). Implementation card: TAW-7 (Critical lane), criteria revision 5 (AC4 amended 2026-10-24), AC1 to AC13. Author: Claude. This spec is gated against TAW-7's acceptance criteria (section 13), not against TAW-8's. It contains no implementation code; mechanisms are chosen in the plan.

Sources: the owner's draft v2.0 (2026-10-24), the owner's review findings of 2026-10-24, and read-only discovery saved in `.clh/evidence/TAW-8/discovery-rev5/` of the Tawsila checkout (Figma, neighbouring cards, providers, Google libraries, corrections). Status labels used below: **Owner decision** (a requirement), **Fact** (verified, with source), **Recommendation** (Claude, needs owner approval), **UNVERIFIED** (routed to a plan verification step, never assumed), **Blocker** (recorded, owner decides).

## 1. Purpose, decisions and boundaries

A new user creates or regains a Tawsila account with Google or Apple, and only then reaches the app. Sign-up asks for no phone number. A verified phone is required later, before the first ride post or request (TAW-5).

**Owner decisions:**
1. Google or Apple authentication is required before browsing; there is no guest, anonymous or phone sign-up.
2. Platform policy: iOS offers Google and Apple; Android offers Google only; Apple on Android is deferred.
3. Both providers sign in natively and exchange the provider ID token with `supabase.auth.signInWithIdToken`. Nonce validation is never disabled or weakened to suit a library.
4. The session is stored in `expo-secure-store` through a chunked adapter.
5. The minimal account row is created by a transactional trigger on `auth.users`; there is no registration function and no local registration marker.
6. Supabase's documented automatic linking of identities with the same verified email is accepted; the application adds no identity merging.
7. `needs_profile` is defined in section 4, and TAW-7 is tested without claiming TAW-4 exists.
8. TAW-4, TAW-5 and TAW-6 are not implemented here and are not modified here; their amendments need the owner's separate approval.

**Owner decisions D1 to D8** (2026-10-24) are recorded in section 12; D4 (the hosted test project) is awaiting the owner's authorization.

**Out of scope:** phone number and OTP at sign-up; email or password sign-in; payments, fares, subscriptions and ride quotas; logout; account deletion, Google Play's web deletion request and Apple credential revocation (see section 10); Figma design work (a separate design card); production deployment; store setup. The cross-card flow (stages D to H) is informative, in `2026-10-24-signup-onboarding-flow-informative.md`, and is not part of this gate.

**Constraints that stay:** the TAW-2 Egypt privacy and region gates are not waived; only test identities and a test Supabase project are used (sections 7 and 8); no external project, purchase or deployment is created by this spec.

## 2. Flows (stages A to C of the product flow)

**A. Welcome.** No valid session: show the provider buttons for the platform (Google on both, Apple on iOS only). One attempt at a time; while one is running the buttons are disabled.

**B. Provider authentication.**
- **Apple (iOS):** native `expo-apple-authentication` with name and email scopes, then `signInWithIdToken` for provider `apple`. **Fact:** the library is included in Expo Go on iOS (Supabase says to add `host.exp.Exponent` to the Apple Client IDs for Expo Go testing); the iOS Simulator offers limited testing; a physical iPhone is the verification device (https://docs.expo.dev/versions/latest/sdk/apple-authentication/, https://supabase.com/docs/guides/auth/social-login/auth-apple). Replay protection uses a nonce end to end: **Fact:** Supabase compares the SHA-256 hex of the raw nonce with the token's nonce claim and rejects a token when only one side has a nonce; the app therefore gives Apple the hash and Supabase the raw value. **UNVERIFIED:** whether `expo-apple-authentication` forwards the nonce unchanged; the plan verifies it on a device.
- **Apple name:** Apple returns the name only on the first authorization. The client then attempts to store it as user metadata. **That update is optional: its failure or absence never fails the sign-in, never signs the user out, and never blocks navigation** (the session already exists); it is reported without personal data and may be retried. Nothing is copied to `accounts`.
- **Google (iOS and Android):** native sign-in, then `signInWithIdToken` for provider `google` with the raw nonce, the hash having been given to Google. **Fact (discovery, 2026-10-24):** the free "Original" tier of `@react-native-google-signin/google-signin` (16.1.5) cannot supply a nonce (iOS generates its own, Android sends none), so a nonce-validated flow is impossible with it; its paid "Universal" tier adds a custom nonce and Credential Manager, its price is **UNVERIFIED** and its documentation lists support only up to Expo 57 and React Native 0.87. `react-native-nitro-google-signin` (2.3.0, MIT, one maintainer, needs `react-native-nitro-modules` and a development build) passes a caller-supplied nonce unchanged to Google on both platforms according to its source, supports Android Credential Manager, and lists React Native up to 0.87; compatibility with React Native 0.88 and Expo SDK 58 and the nonce round trip on real builds are **UNVERIFIED**.
  - **Owner decision D1:** `react-native-nitro-google-signin`, pinned, is the preferred native Google candidate, subject to a **bounded spike** on real iOS and Android development builds that proves: compatibility with the installed Expo, React Native and Supabase versions; the issued ID token carries the nonce and Supabase accepts it; the token audience matches an authorized client ID; Android Credential Manager works; and the licence is acceptable. **No paid dependency is authorized**, so the RNGS Universal tier is excluded.
  - **Blocker handling:** the free Original tier is excluded (no nonce). If the spike fails, the findings are reported and the owner's approval is required before switching to system-browser OAuth (`signInWithOAuth`, `expo-web-browser`, PKCE, an app scheme and a Supabase redirect allow-list entry, a single Google web client, not available in Expo Go); the spec changes only after that approval.
- **Cancellation, denial, unavailability, a second tap and an unexpected provider error** end the attempt and return to Welcome with no session change and no route change. Cancellation shows no error; real failures show a short non-sensitive retry message. No provider event alone opens a protected route.

**C. Account read.** With a valid session the app reads the user's own `accounts` row. If it is missing the app shows `account_provision_error` with a retry; it never creates the row from the client and never opens the tabs.

## 3. Data model and authorization

`public.accounts`:

| Column | Type | Rule |
|---|---|---|
| `user_id` | `uuid` primary key, references `auth.users(id)` on delete cascade | the Supabase user |
| `phone_e164` | `text` null | null until TAW-5; when present, `^\+(?=[1-9])[0-9]{8,15}$` |
| `phone_verified` | `boolean not null default false` | settable only by trusted server code (TAW-5) |
| `profile_completed_at` | `timestamptz` null | settable only by trusted server code (TAW-4) |
| `created_at` | `timestamptz not null default now()` | |

- Constraints: a verified row requires a non-null phone; a partial unique index on `phone_e164 where phone_verified` (verified numbers are unique; unverified numbers never grant anything).
- **Trigger:** `public.handle_new_user()` is `security definer` with an empty `search_path`, runs `after insert on auth.users`, and inserts the row. It does not swallow errors: **a failure fails the sign-up** (Supabase surfaces a generic "Database error saving new user"; the Supabase docs warn that a failing trigger blocks sign-ups, so it stays minimal and tested). It fires only when an `auth.users` row is created, so returning sign-ins and identity linking to an existing user do not touch it.
- **RLS:** enabled; one `select` policy on the own row; no insert, update or delete policy and no such privilege for `anon` or `authenticated`. `phone_verified` and `profile_completed_at` are therefore not client-writable; TAW-4 and TAW-5 add their own `security definer` functions.
- Nothing exposes `phone_e164`, provider tokens or provider email to other users, or copies provider email or name into a public profile.

## 4. Routing and session requirements

**States (derived, never persisted):** `signed_out`, `authenticating`, `account_provision_error`, `needs_profile`, `ready_to_browse`. `needs_phone_verification` is a contextual gate on the ride action (TAW-5), not a global state. Derivation: no session gives `signed_out`; a session without an own row gives `account_provision_error`; a row with `profile_completed_at` null gives `needs_profile`; a row with it set gives `ready_to_browse`. There is no local registration marker. The tabs open only in `ready_to_browse`, and a cold start never shows the tabs or signs the user out merely because the session or row read is slow.

**`needs_profile` seam and testing (replaces the earlier development bypass):** TAW-7 only reads `profile_completed_at`; nothing in TAW-7 sets it, so `needs_profile` is where a new user stops until TAW-4 delivers profile and consent and a trusted function that sets `profile_completed_at`. **Production routing always enforces the server-confirmed value; no build contains a bypass control, flag or route that skips it.** TAW-7 is tested independently through controlled test state: injected account fixtures in unit tests of the routing logic (both `needs_profile` and `ready_to_browse`), and, for manual testing against the test project, a documented test seed that sets `profile_completed_at` on a test account from the database side, never from the app. TAW-7 does not claim that browsing is production-ready.

**Session invariants (what must hold; the plan selects the simplest verified mechanism, and this spec mandates no counters, queues or timeout values):**
1. A stale authentication event or result cannot invalidate a newer valid session.
2. Genuine termination of the current session (an invalid or revoked refresh token, a deleted user) results in sign-out, exactly once.
3. Temporary network or refresh failures (network errors, HTTP 5xx, and a discarded refresh) never trigger sign-out by themselves.
4. Abandoned operations (timed out, cancelled or unmounted) cannot modify the current session, stored data or navigation state.
5. The Supabase SDK's actual session is authoritative; the app never keeps a signed-in state against it.
6. Stored session data stays consistent after interrupted writes (storage requirements below).

**Facts the plan relies on (auth-js 2.118, https://cdn.jsdelivr.net/npm/@supabase/auth-js@2.118.0/migrations/lockless-coordination.md):** coordination is lockless; a refresh whose rotated tokens were deliberately not stored because a concurrent sign-out changed storage returns `AuthRefreshDiscardedError`, a successful no-op; `refreshSession` must never be called inside a `TOKEN_REFRESHED` handler; `dispose()` does not abort in-flight fetches and is never called on the app-wide client; refresh runs only in the foreground (`startAutoRefresh` when active, `stopAutoRefresh` otherwise) and `detectSessionInUrl` is false.

**Session storage (chunked `expo-secure-store` adapter; reuse the earlier reviewed design where compatible):**
- Entries stay under the historical 2 KB platform limit; values are ASCII; adapter operations are serialized.
- Replacement is atomic from a reader's view: new chunks are written under a fresh generation and only then a small manifest pointing to them is written; reads follow the manifest only; an interrupted replacement leaves the previous session fully readable; a manifest whose chunks are missing or corrupt reads as no session and is cleaned up.
- Orphaned chunks (an unreferenced generation) are removed after a successful write and pruned when found; removing a session removes the manifest first and then every generation, so sign-out leaves nothing behind.
- Tests: interruption at every write boundary, corruption, missing chunk, orphan cleanup, concurrent calls, removal.

**iOS reinstall (owner decision D2):** a fresh installation must require authentication: credentials retained in the iOS Keychain must not restore an authenticated session after an uninstall and reinstall, while a normal application update keeps the existing valid session. **Fact:** on iOS, SecureStore data "will persist across app uninstallations when the app is reinstalled with the same bundle ID", though this is "not guaranteed"; on Android it does not survive uninstall (https://docs.expo.dev/versions/latest/sdk/securestore/). The mechanism that tells a fresh installation from an update is chosen and verified in the plan; it must not rely on data that survives uninstall, and a failure of the mechanism must fail toward requiring sign-in.

## 5. Identity linking and duplicates

**Confirmed (Fact):** Supabase automatically links identities that share an email (its documentation words this with "unverified" and "unconfirmed" caveats); manual linking is off by default (https://supabase.com/docs/guides/auth/auth-identity-linking). This default is accepted, and the application adds no linking or merging. **UNVERIFIED (not documented):** how Google, Apple and Apple private-relay addresses behave under it and whether it can be disabled. The plan therefore tests, against the test project with test identities: Google and Apple with the same verified email, Apple private relay, and different emails (separate accounts). The observed behaviour is recorded. A second account that later tries to verify a number already verified elsewhere is TAW-5's collision case.

## 8. Privacy and abuse

Provider ID tokens and OAuth tokens are never stored in application tables, logs or analytics; Supabase keeps what its own operation needs. No provider email or name is shown to other users or copied to a public profile. Only test identities are used until the Egypt privacy and region gates are passed. Abuse controls rely on Supabase Auth's rate limits and settings; there is no anonymous sign-up and no cleanup job; OTP and SMS abuse controls belong to TAW-5.

## 9. Tests and evidence

By blast radius, written before the implementation; mechanisms are the plan's choice:
1. **Database (pgTAP, local stack or the hosted test project):** the trigger creates exactly one row per new auth user in the same transaction; a forced failure of the row insert aborts the `auth.users` insert; returning sign-in and identity linking create no row; RLS lets a user read only their own row; direct insert, update and delete are denied; `phone_verified` and `profile_completed_at` cannot be written by the client; a verified row requires a phone; verified numbers are unique and unverified duplicates allowed; the E.164 check holds.
2. **Session, storage and routing (Jest):** each session invariant of section 4 with a test that fails if it is broken (stale event versus newer session, genuine termination, temporary failures, abandoned operations, discarded refresh, nothing after unmount); the storage adapter requirements (interruption at every write boundary, corruption, missing chunk, orphan cleanup, concurrent calls, removal leaves nothing); state derivation for every combination of session and row using injected fixtures; no tabs on a provider event alone; production routing contains no bypass; after an uninstall and reinstall with Keychain data still present the app requires sign-in and a normal update keeps the valid session (D2).
3. **Provider handlers (Jest, mocked libraries):** success, cancellation codes, denial, unavailable provider, a second tap, a duplicate or replayed authentication result (one attempt, one session), a missing or malformed ID token (no session, back on Welcome), an unexpected error, for Google and Apple; **a failing Apple name update leaves the session and navigation unaffected**; no phone number or OTP is requested; a static check finds no phone sign-in or OTP call in application code. OAuth `state` validation does not apply to native ID-token flows.
4. **Auth integration (local stack or test project):** an ID token with a wrong nonce is rejected; a returning identity signs in to the same user and creates no second row; two first sign-ins for different users each create exactly one row; the identity-linking scenarios of section 5.
5. **Device and provider smoke tests (only where section 7 prerequisites exist):** first and returning sign-in with test Google and Apple identities on a physical iPhone and a development build; the Google spike; Google on an Android emulator or device. Unrun tests are never reported as passed.
6. The standing checks: install, `tsc`, lint, unit tests, both exports, expo-doctor.
