# TAW-7 Account sign-up: design spec

Authoring card: TAW-8. Implementation card: TAW-7 (Critical lane: auth/session and account creation), criteria revision 4. Author: Claude. This spec is gated against TAW-7's acceptance criteria AC1 to AC12 (section 12), not against TAW-8's.

## 1. Purpose and boundaries

A new user registers with a mobile number and gets an authenticated session so they can browse the app. Registration sends no OTP or SMS and uses no SMS provider, so there is no SMS cost at this stage. The number is stored as **unverified**. Phone OTP stays deferred to the first ride post or request (MVP lines 231 and 795, owned by TAW-5).

Owner decisions of 2026-10-21 that this spec takes as settled (recorded on the TAW-7 card, revision 3):
1. **Identity:** an anonymous Supabase session is created at registration; the phone number is saved as an unverified field of the user's account record. Verifying the phone later (TAW-5) links it as the recoverable identity.
2. **Duplicates:** the same unverified number may be claimed by several accounts; uniqueness applies only among verified numbers.
3. **Country code:** a country selector is kept and defaults to +20 (Egypt).
4. **Sign in:** the returning-user flow is out of scope (TAW-5).
5. **Android evidence:** Android is proven by `expo export --platform android` only; emulator or device verification belongs to TAW-6 (as for TAW-3).

Out of scope: OTP, SMS, identity linking, recovery and logout (TAW-5); name, photo, 18+ confirmation, Terms and Privacy acceptance, and community (TAW-4); email; Apple/Google sign-in; payments, fares, subscriptions, push, account deletion, production deployment, store setup.

Constraints from existing decisions: TAW-2 selected Supabase with PostgreSQL and requires the server to verify state ("UI-only gating is insufficient"); its Egypt privacy and region gates are not waived, so only a test project with synthetic data is used (AC6, AC11).

## 2. Approach

Client: Expo app (existing shell in `apps/mobile`) using `@supabase/supabase-js`. Backend: a Supabase **test** project, defined as code in `supabase/` (migrations, config) so it can be recreated.

Registration sequence (one user action, "Continue" on the phone screen):
1. The client validates the number locally (section 5) and shows an inline error if invalid.
2. If no session exists, the client calls `auth.signInAnonymously()`. If a session already exists (retry after failure), it is reused; no second user is created.
3. The client calls the database function `register_phone(p_phone text)`. The function runs as `security definer`, reads the caller from `auth.uid()` (it rejects a null caller), increments and checks the registration rate-limit counters (section 8), validates and normalizes the number server-side with the same rules, and then writes the caller's row in one atomic statement:
   `insert into public.accounts (user_id, phone_e164) values (auth.uid(), v_phone) on conflict (user_id) do update set phone_e164 = excluded.phone_e164 where public.accounts.phone_verified = false;`
   It then reads the caller's own row and returns exactly one of: `{ ok: true }` (the row now holds this number, including an identical retry), `{ ok: false, reason: 'invalid_number' }`, `{ ok: false, reason: 'rate_limited' }`, or `{ ok: false, reason: 'already_verified' }` (the caller's own account is already verified with a different number; TAW-5 owns changing a verified number). No reason depends on whether any other account holds the same number (AC4). Because an unverified row is outside the partial unique index (section 3), the write can never raise a uniqueness error.
4. On success the client records a local `registered` marker (a non-sensitive boolean in secure storage) and routes to the tabs (section 6).

Alternatives considered and rejected: an Edge Function that creates the user and the row atomically (more moving parts and a second runtime; the anonymous user without a row is cleaned up instead, section 8); a unique constraint on unverified numbers (lets an attacker block a real person's number, and reveals which numbers are registered; rejected by the owner).

## 3. Data model and authorization (AC2, AC3, AC4, AC7, AC11)

`public.accounts`:
| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` primary key, references `auth.users(id)` on delete cascade | the anonymous user |
| `phone_e164` | `text not null` | normalized, `+` and 8 to 15 digits |
| `phone_verified` | `boolean not null default false` | only trusted server code may set it true |
| `created_at` | `timestamptz not null default now()` | |

- `public.registration_limits (key text, window_start timestamptz, attempts integer not null, primary key (key, window_start))` holds the atomic counters of the limiter (section 8): one row per key (`u:<user_id>` or `ip:<address>`) per hour. It has row-level security enabled and no policy, so clients can neither read nor write it; only `register_phone` touches it.
- A **partial unique index** `unique (phone_e164) where phone_verified` enforces uniqueness among verified numbers only (AC4). TAW-5 relies on it.
- Row-level security is enabled with **no** insert, update or delete policy for the `authenticated` role, and one select policy: a user reads only their own row (`user_id = auth.uid()`). Writes happen only through `register_phone`, which can set `phone_e164` on an unverified row but never `phone_verified`, and which never changes the number of a verified row (so a verified account cannot silently become "verified" for a different number). A client trying to update `phone_verified` directly is rejected (AC3, tested in AC8).
- No policy and no view exposes `phone_e164` to other users (AC2, AC11). A later public profile projection (TAW-4) must not include it.
- `register_phone` is callable only by `authenticated` users who are anonymous or not; it revokes `public` execute. It uses a fixed `search_path` and no dynamic SQL.
- Hand-off (AC7): TAW-7 delivers the account record above and no profile fields. TAW-4 adds profile data, 18+ and consent records and community in its own tables keyed by `user_id`. TAW-5 adds OTP, sets `phone_verified` through a trusted function, links the verified phone to the anonymous user, and adds recovery, sign-in and logout.

## 4. Session and storage (AC1, AC3, AC6)

- The anonymous session (access and refresh tokens) is stored with `expo-secure-store` (Keychain on iOS, encrypted storage on Android) through a storage adapter given to the Supabase client. If a stored value exceeds the platform limit of the secure store, the adapter splits it into chunks; the plan verifies the limit on both platforms before implementation.
- `autoRefreshToken` is on and refresh is tied to app foreground state, as recommended for React Native by the Supabase docs (the plan confirms against the current docs).
- Known trade-off, accepted by the owner: signing out or losing the device loses an anonymous account until the phone is verified. TAW-7 provides no logout.
- **Registration state** (used by routing, section 6). A user is *registered* when their own `accounts` row exists. The local marker is bound to a user: the app stores `registered:<user id>` (a non-sensitive value in secure storage) after a confirmed registration. Precedence on launch: **the session decides first.** (a) No persisted session: show Welcome and ignore any marker. (b) A session exists: trust a marker only if it names the same user id as the session; then the tabs open at once and a background own-row read confirms. Without a matching marker, show the Phone screen and first read the user's own row, because a lost response may have succeeded on the server: a found row sets the marker and routes to the tabs, a missing row leaves the user on the Phone screen with the existing session reused for the next attempt. (c) Registered: the tabs.
- **Session loss.** A temporary failure (network down, timeout, server 5xx) never clears anything: the app keeps its state and shows the offline or failure pattern. A **terminal** failure is a refresh that permanently fails (an invalid or revoked refresh token, a deleted user) or an authorization error (401 or an invalid JWT) on the confirming read, or a `SIGNED_OUT` event from the auth client that the app did not request. On a terminal failure the app first tries one session refresh; if that also fails terminally it clears the stored session and the marker, and shows Welcome; registering again creates a new anonymous user and account. An authorization error is never interpreted as "no row".
- Configuration: `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` come from the environment (a committed `.env.example` with placeholders, a git-ignored `.env`). The anon key is public by design but is still not committed. The service-role key never appears in the app, in tests that ship, or in the repository (AC6).

## 5. Phone input and validation (AC1, AC5)

- Format: E.164, `+` then 8 to 15 digits. The server applies the same rule as the client.
- Egypt (+20): after the country code the national number is 10 digits and starts with 10, 11, 12 or 15 (mobile ranges); a leading 0 typed by the user is removed. Other countries are validated only for E.164 length.
- No third-party phone library; the rules live in one shared function in the app and one SQL function that tests compare against a shared set of fixture numbers.
- The country list is bundled static data (initially Egypt +20 first, then Saudi Arabia +966 and the United Arab Emirates +971); extending it is data-only.

## 6. Screens and design (AC5, AC9)

Source: Figma Onboarding `5:4`, section "Onboarding · Sign up" `14:288`; frames **01 Welcome `14:2`** and **02 Phone number `14:80`** (393 x 852). Frame 03 Verification code (`14:150`) and 04 Create profile (`14:225`) are not built here (OTP is deferred; profile is TAW-4).

- **Welcome:** wordmark, headline, bullets and a "Get started" button as drawn. The footer link "Already have an account? Sign in" is hidden (owner decision; returning-user sign-in belongs to TAW-5).
- **Phone number:** nav bar with back, title and subtitle, a country field (default +20) with a picker, a number field (numeric keyboard), a primary "Continue" button.
- **Deviations from Figma** (recorded in `DESIGN_NOTES.md` by TAW-7 and handed to the designer): the OTP step is omitted; the country defaults to +20 instead of +966; the subtitle "We'll text you a 6-digit code" is replaced by copy that does not promise a text message; the disclaimer sentence "By continuing you agree to the Terms and Privacy Policy" is removed because consent is captured with a recorded acceptance in TAW-4. Exact replacement copy is part of the plan and goes through `src/strings.ts`.
- **States** (the Figma sign-up frames draw none, so the existing app patterns are used): invalid number (inline error text under the field in `system/red`, associated to the field for screen readers), loading ("Continue" disabled with a progress indicator), failure (a generic error message with a retry), offline (the existing `ErrorState` pattern or an inline banner with the same copy; the plan chooses one and records it), cancel (back returns to Welcome without creating anything; an anonymous user created before a failed registration stays, section 8).
- Accessibility: labels and roles on every control, error text announced, Dynamic Type up to the largest accessibility size without clipping, WCAG AA contrast in both themes (the shell's tests already assert 4.5:1 for token pairs).
- Routing: an `(onboarding)` route group holds Welcome and Phone. The root layout uses the three states of section 4: no session shows Welcome; a session without a confirmed account row shows the Phone screen (never the tabs); registered shows the tabs. Navigation to the tabs happens only after `{ ok: true }` or a confirmed own row, never on the session event alone. The first render uses only local state (stored session and `registered` marker) and does not wait for the network.

## 7. Privacy (AC2, AC11)

An unverified number is personal data. It is stored once (the `accounts` row), never copied to logs, analytics or error reports (error messages and the logger must not include it), never returned to other users, and never labelled "verified" anywhere in the app. The only reader is its owner. Production data stays blocked until the Egypt privacy and region reviews of TAW-2 are done; development and tests use synthetic numbers only (for example the reserved test ranges), never real numbers.

## 8. Abuse and cleanup (AC12)

- **Anonymous sign-ins (Auth endpoints):** the test project enables anonymous sign-ins and sets the per-IP hourly limit for them in `supabase/config.toml` (value chosen in the plan; Supabase's documented Auth rate limits apply to Auth endpoints only). Phone sign-in is not enabled, so no SMS can be triggered.
- **Registration (`register_phone`), server-enforced and atomic:** every call first increments two counters, before any validation, with a single atomic statement per key: `insert into public.registration_limits (key, window_start, attempts) values (v_key, date_trunc('hour', now()), 1) on conflict (key, window_start) do update set attempts = public.registration_limits.attempts + 1 returning attempts;`. The row lock taken by the conflict update serializes concurrent callers on the same key, so two concurrent calls cannot both observe the same count. The keys are `u:<user id>` (limit 5 per hourly window) and `ip:<address>` (limit 20 per window; the address is the first `x-forwarded-for` value of the request headers, best effort). If either returned count exceeds its limit the function stops and returns `rate_limited`; the counters are incremented even for invalid numbers, so a client cannot probe validation for free. The limits are configuration constants set in the plan and tuned later. The limiter therefore holds for direct RPC calls that bypass the app. Counter rows older than 24 hours are deleted by the function's housekeeping step. A client-side guard that disables "Continue" while a request is in flight is only a convenience.
- **Cleanup policy (documented, job deferred):** the activity signal is the most recent `refreshed_at` of the user's rows in `auth.sessions`. The plan must confirm that this column exists and is updated on token refresh in the current Supabase schema; **if it cannot be confirmed, or a user has no session timestamp, the cleanup deletes nothing for that user** (there is no fallback to `last_sign_in_at`, which does not record refresh activity). Deletable: an anonymous user without an `accounts` row created more than 24 hours ago, and an anonymous user with an unverified `accounts` row whose latest session activity is older than 30 days. Never deleted: any user with `phone_verified = true`, any user with a linked identity (that is, no longer anonymous), and any user active within the window. The SQL and its test cases (active, newly linked, verified, stale, null session timestamp, signal unavailable) are written in TAW-7; the scheduler is a recorded follow-up. TAW-7 documents the policy and the SQL; building the scheduler is a recorded follow-up card proposal, not part of TAW-7.
- **CAPTCHA:** Supabase can require CAPTCHA for anonymous sign-ins, but a challenge in a React Native app needs a vendor and a native or webview flow. It is deferred and recorded as an accepted risk: before public launch the abuse controls must be re-reviewed. The owner approves this deferral with the document approval.

## 9. Testing by blast radius (AC8)

Highest risk first, written before the implementation (test-first):
0. **Registration state and recovery:** the marker is ignored without a session or for a different user id; three separate session-loss tests: (i) an authorization error on the own-row read followed by a successful refresh and a retried read preserves the session and the marker and shows the result of the retry; (ii) a terminal refresh failure (invalid or revoked refresh token, deleted user, or an unrequested `SIGNED_OUT`) clears the session and the marker and shows Welcome; (iii) a temporary failure (network down, timeout, 5xx), including a temporary refresh failure, preserves the session and the marker and shows the offline or failure pattern; a failure between anonymous sign-in and `register_phone`, and an app restart in that window, leave the user on the Phone screen and never on the tabs; a retry reuses the existing session; a lost response that actually succeeded is reconciled by the own-row read; offline during either call shows the offline state and keeps the phone screen.
1. **Database and authorization** (against a local Supabase stack or the test project, using synthetic data): `register_phone` creates the row with `phone_verified=false`; invalid numbers are rejected server-side; a client cannot insert, update or delete `accounts` rows directly; a client cannot set `phone_verified`; a user cannot read another user's row; two accounts can hold the same unverified number and the responses are identical; two accounts cannot hold the same verified number (the partial unique index; set by a service-role test fixture only); a verified account cannot change its number through `register_phone` (returns `already_verified`) while an identical retry returns ok; the limiter rejects the sixth attempt of a user within an hour and the twenty-first from one address, including for direct RPC calls and for invalid numbers, holds under concurrent calls at both thresholds (the number of accepted calls never exceeds the limit), and recovers after the window; a concurrent double call with the same number leaves one row.
2. **Auth service** (unit, mocked Supabase client): anonymous sign-in is reused when a session exists; failure and offline map to the right error states; the phone number is never passed to any logger; no call to any phone-OTP or SMS API exists in the code (static check).
3. **Validation** (unit): shared fixture numbers produce the same result on the client function and the SQL function.
4. **UI** (jest-expo and Testing Library): Welcome has no Sign in link; phone screen shows the inline error, loading, failure and offline states; accessibility labels; routing by session.
5. **Device**: iOS Simulator run with screenshots against Figma 14:2 and 14:80 (design and device gates of the product card); Android proven by `expo export --platform android` only, by owner decision (emulator or device verification belongs to TAW-6, as for TAW-3). The existing checks (`npm ci`, `tsc --noEmit`, `expo lint`, `npm test`, both exports, expo-doctor) stay green.

Precondition to confirm in the plan: whether the owner's Mac can run the local Supabase stack (Docker). If not, the database tests use the hosted test project with a dedicated schema and synthetic data.

## 10. Risks and open items

- **Account loss:** signing out or a lost device loses the anonymous account until the phone is verified (accepted).
- **Number claiming:** anyone can claim someone else's number unverified. Mitigations: it is never shown, never trusted, never unique, and the real owner's later OTP wins uniqueness. Accepted by the owner's duplicate decision.
- **Spam accounts:** Auth rate limits and the server-enforced registration limiter are configured; CAPTCHA is deferred (section 8).
- **Android UI is not verified on a device in this card** (owner decision); layout, keyboard and accessibility on Android are checked in TAW-6.
- **Region and privacy:** test project and synthetic data only; production blocked by the TAW-2 gates.
- **Figma:** the design needs a designer update (no OTP step, +20, copy changes, states). Until then the deviations in section 6 stand.
- **Library assumptions to verify in the plan against current official docs:** supabase-js behaviour with Expo SDK 58 and React Native 0.88 (including whether a URL polyfill is still needed), anonymous sign-in rate-limit settings, secure-store value size limits.
