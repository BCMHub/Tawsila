## 1. Purpose and boundaries

A phone-verified driver with an approved car posts a ride on the pilot route (direction, date, departure time, flexibility, seats, optional pickup note and notes), once or every weekday (Sunday to Thursday). Any signed-in user with a completed profile sees future rides with free seats by direction and day, opens a ride, and shares a ride link to WhatsApp. The link opens the ride in the installed app and shows its current state.

In TAW-29: sections 3–12. Not in TAW-29:

- Seat requests, accept and decline, seat allocation, cancelling one day, chosen days or a whole series, and the rider's every-weekday join (TAW-30). TAW-29 keeps `seats_taken` at 0 and leaves the status columns ready for TAW-30.
- Chat and in-chat ride offers (TAW-31). Ratings, reports and blocks (TAW-32).
- The phone OTP flow and the TAW-26 verification screens (TAW-5).
- Push notifications, drafts, editing a posted ride, and deferred deep links (returning a newly installed user to the shared ride).
- Android (D10) and Arabic/RTL.

## 3. Data model (one schema migration plus one data migration)

All new tables live in `public`, have RLS enabled and **no policies for client roles**, except the two configuration tables. Every user write goes through the security-definer functions of section 5.

### 3.1 Configuration data (AC2)

| Table | Columns and constraints |
|---|---|
| `places` | `id uuid pk default gen_random_uuid()`, `name text not null unique` (trimmed, 1–60 characters), `area_label text` (null or trimmed, 1–60; shown under the place name, for example "Fifth Settlement"), `active boolean not null default true`, `sort_order int not null default 0` |
| `routes` | `id uuid pk`, `place_a_id uuid not null references places`, `place_b_id uuid not null references places`, `check (place_a_id <> place_b_id)`, `unique (place_a_id, place_b_id)`, `duration_minutes smallint not null check (duration_minutes between 1 and 600)` (shown as "about N min"), `active boolean not null default true`, `sort_order int not null default 0` |
| `car_types` (TAW-4, altered) | adds `passenger_seats smallint not null default 4 check (passenger_seats between 1 and 8)`: the most seats a driver may offer in a car of that type |

Direction is `a_to_b` or `b_to_a` on a route. The app labels it "To <destination place name>".

The pilot rows are inserted by a separate **data migration**: places "10th of Ramadan City" (area label null) and "New Cairo" (area label "Fifth Settlement"), and the route between them with `duration_minutes = 50`. The inserts are idempotent (`on conflict do nothing` on the unique keys) and use fixed UUIDs so tests can refer to them. Changing or adding a route is a row change by an admin (runbook, section 6.3). It needs no app release, and no route, place or duration appears in app code. A test asserts that the mobile source contains no pilot place name (section 13).

### 3.2 Rides

| Table | Columns and constraints |
|---|---|
| `ride_series` (what the driver posted) | `id uuid pk`, `owner_id uuid not null references accounts(user_id) on delete cascade`, `request_id uuid not null`, `unique (owner_id, request_id)`, `route_id uuid not null references routes`, `direction text not null check in ('a_to_b','b_to_a')`, `first_date date not null`, `departure_time time(0) not null` (the driver's requested local Cairo time, whole minutes below 24:00: `check (departure_time < '24:00' and extract(second from departure_time) = 0)`), `flex_minutes smallint not null check in (0, 5, 10, 15, 30)`, `seats_offered smallint not null check between 1 and 8`, `pickup_note text` (null or trimmed, 1–80 characters), `notes text` (null or trimmed, 1–200), `repeat text not null check in ('once','weekdays')`, `status text not null default 'active' check in ('active','cancelled')`, `cancelled_at timestamptz`, `check ((status = 'cancelled') = (cancelled_at is not null))`, `created_at timestamptz not null default now()`. Immutable publish result, used for replays (section 5.2 step 4): `published_ride_id uuid not null` (the first ride, deferrable foreign key to `rides`) and `published_ride_count smallint not null check (published_ride_count >= 1)`. No function updates these two columns or the input columns after insert; only `status` and `cancelled_at` change. |
| `rides` (one row per day; what riders see and links point to) | `id uuid pk`, `series_id uuid not null references ride_series on delete cascade`, `owner_id uuid not null` (copied from the series, for indexes), `route_id uuid not null`, `direction text not null`, `ride_date date not null`, `departs_at timestamptz not null`, `seats_offered smallint not null`, `seats_taken smallint not null default 0 check (seats_taken between 0 and seats_offered)`, `status text not null default 'scheduled' check in ('scheduled','cancelled')`, `cancelled_at timestamptz` (same pairing check), `share_code text not null unique check (share_code ~ '^[0-9A-HJKMNP-TV-Z]{8}$')`, `created_at timestamptz not null default now()`, `unique (series_id, ride_date)` |

**No column in any TAW-29 table holds a price, fare, cost, amount or currency (AC3).** No input of any function accepts one, and no screen field asks for one. The `notes` and `pickup_note` texts are free text. The client hint "Keep it short. Don't add phone numbers or prices." (P1b) stays, and the server rejects phone-number patterns (section 5.2). Prices in free text are not machine-detected: Proposal. A pilot report from TAW-32 is the remedy.

**Departed** is derived, never stored: `departs_at <= now()`. **Full** is `seats_taken >= seats_offered`. A ride's displayed state:

- `cancelled` when `status = 'cancelled'` or its series is cancelled.
- else `withdrawn` when the owner is no longer eligible to post, that is `taw29_post_eligible(owner)` is false (phone no longer verified, or the car review no longer approved at the current revision, section 8). The ride row is unchanged; it reappears if the owner becomes eligible again.
- else `departed` when it has departed.
- else `full` when it is full.
- else `available`.

Copied columns (`owner_id`, `route_id`, `direction`, `seats_offered`) are written only by the definer functions, which copy them from the series. A pgTAP test asserts they match the series for every generated row.

Indexes: `rides (route_id, direction, departs_at) where status = 'scheduled'`, `rides (owner_id, departs_at)`, `ride_series (owner_id, created_at)`.

The car shown on a ride is the owner's **current** `vehicles` row; no snapshot is taken.

**Facts (TAW-4 migration):**

- `submit_car` raises `already_approved` while the car item is approved at its current revision (lines 258 and 298; tested in `taw4_eligibility.test.sql` and `taw4_review.test.sql`), so an approved owner cannot change the car through the app.
- `review_item` (service role) can set an approved item to `rejected`. After that, `submit_car` accepts a new submission, which updates `vehicles` and starts a new pending revision.

**Invariant used by TAW-29.** While `taw29_post_eligible(owner)` is true (car item approved at the current revision), the current `vehicles` row is the approved one. It can only differ through a direct admin SQL edit of `vehicles`, which the runbook forbids for TAW-29 test data. When the owner is not eligible (car rejected, resubmitted and pending, or phone unverified), every ride of that owner has the state `withdrawn`:

- `list_rides` does not return it;
- `get_ride` and `resolve_shared_ride` return the state, and the app shows D4b.

**Redaction does not depend on the displayed state.** Whenever `taw29_post_eligible(owner)` is false, every reader returns `car_label` null and `owner_phone_verified` false, **in every state**, including `cancelled` rides and rides of a cancelled series (where `cancelled` takes precedence as the displayed state).

So no rider ever sees a car that is not approved. Changing an approved car is not in TAW-29 (P1b "Change" is disabled, section 11.2).

## 4. Time, dates and the 14-day window

- All ride dates and times are **Africa/Cairo** local time. `departs_at = (ride_date + departure_time) at time zone 'Africa/Cairo'`. Egypt observes daylight saving time (**Fact**: the zone has rules since 2023), so a weekday series keeps the same wall-clock time across a change.
- **Transition days follow Postgres' documented `AT TIME ZONE` rules unchanged**; the spec adds no rule of its own:
  - a local time that occurs twice (the fall-back hour) takes the offset in force just **after** the transition (standard time, the **later** instant);
  - a local time that does not exist (the skipped hour) takes the offset in force just **before** it, so it lands one hour later on the wall clock.

  Egypt's rules (tzdata) put the fall-back at the end of the last Thursday of October (24:00 → 23:00) and the spring-forward at the start of the last Friday of April (00:00 → 01:00). Concrete expectations, asserted by tests:
  - `2026-10-29` (a Thursday, so valid for weekdays) at `23:30` → `2026-10-29 21:30:00+00` (the later of 20:30 and 21:30 UTC).
  - `2027-04-30` (a Friday, one-off only) at `00:30` → `2027-04-29 22:30:00+00`, displayed back as 01:30 local.
  - A weekdays series at 07:00 across either change keeps 07:00 local, which is 04:00 UTC in daylight saving time (UTC+03) and 05:00 UTC in standard time (UTC+02).

  The dates come from tzdata and are **UNVERIFIED** until the plan's first test pins them against the local database (V5). If tzdata differs, the tests take the database's transition dates and the rule above still holds.
- The app offers departure times in 5-minute steps; the server accepts any whole minute.
- "Today" means `(now() at time zone 'Africa/Cairo')::date`. The **window** is today plus the next 13 days (14 dates), from `ride_window_days()` = 14 (Owner, O3).
- A ride may be posted for a date inside the window whose `departs_at` is after `now()`.
- Weekdays are Sunday to Thursday (`extract(dow) in (0,1,2,3,4)`). A weekdays series must start on a weekday.
- The app formats every date and time in Africa/Cairo, whatever the device time zone. Whether Hermes `Intl.DateTimeFormat` supports `timeZone: 'Africa/Cairo'` on iOS is **UNVERIFIED** (V4). If not, a small formatter based on the server-provided `departs_at` and local fields returned by the API is used (section 5.3 returns `ride_date` and `departure_time` as local values, so the app never converts on its own).

## 5. Server functions

Every function is `security definer`, `set search_path = ''`, and has a schema-qualified body. It raises `raise exception '<code>'` codes in TAW-4 style. Privileges are listed in section 14.

### 5.1 Gate functions

- `public.is_phone_verified() returns boolean`, `stable`: the caller's `accounts.phone_verified`; false when there is no row or no caller.
- `public.require_phone_verified() returns void`: raises `phone_unverified` unless `is_phone_verified()`.

Both use exactly the names, signatures, semantics and grants of the TAW-5 spec section 3, because TAW-29 ships first. **Handoff to TAW-5:** its migration must `create or replace` them with the same contract, and its plan must not create them twice (recorded on TAW-5 by the plan, section 16).

- `public.can_publish() returns text`, `stable`: `'ok'`, `'phone_unverified'`, `'car_not_approved'` or `'profile_incomplete'`, checked in that order after the caller exists. It lets the app show the right message before the flow (AC1). It authorises nothing; `publish_ride` re-checks everything.

### 5.2 `publish_ride` (AC1, AC3, AC5)

`public.publish_ride(p_request_id uuid, p_route_id uuid, p_direction text, p_date date, p_time time, p_flex_minutes int, p_seats int, p_pickup_note text, p_notes text, p_repeat text) returns jsonb`

The function runs these steps in order. The first failure raises its code and writes nothing.

**Argument contract.**

- Required (never null): `p_request_id`, `p_route_id`, `p_direction`, `p_date`, `p_time`, `p_flex_minutes`, `p_seats`, `p_repeat`.
- Nullable: `p_pickup_note`, `p_notes`. Null, or empty after trimming, means no note.
- Every set-membership check is written null-safe (`coalesce(x in (...), false)` or an explicit `is null` test). A null never reaches a table constraint, so the caller always gets one of the codes below, never a generic constraint error.

1. `auth.uid()` is null → `not_authenticated`.
2. Any required argument is null → `missing_argument`. This reveals nothing about the caller.
3. Lock the caller's `accounts` row `for update` (missing → `account_missing`), then the caller's `verification_items (user_id, 'car_owner')` row `for share` if it exists. This is the **lock order** of section 8.1. It serialises one user's publishes with each other, with the weekday extension and with an admin's change of `phone_verified` or the car review. Idempotency, limits and the gate decision are therefore race-free, and steps 5–6 are the **authorisation point**.
4. **Idempotency.** Inputs are normalised exactly as step 10 does (texts trimmed, empty to null; null-safe comparison with `is not distinct from`). If a series with `(owner_id, request_id)` exists:
   - all stored inputs equal the normalised inputs → return `{series_id, ride_id: published_ride_id, share_code of that ride, ride_count: published_ride_count, replayed: true}`. These values are immutable, so a replay after extension, cancellation or departure returns exactly the original **publish result**. The publish result is the four fields `series_id`, `ride_id`, `share_code` and `ride_count`; the `replayed` flag is not part of it. There are no new rows and no event;
   - otherwise → `request_conflict`.

   A replay creates nothing, so it is answered before the gate.
5. `public.require_phone_verified()` → `phone_unverified`. The gate runs before any validation, so an unverified caller learns nothing else.
6. `public.can_post_rides()` false → `car_not_approved`.
7. The route exists and is active, and both places are active → `invalid_route`. `p_direction` in the set → `invalid_direction`.
8. `p_repeat` in the set → `invalid_repeat`. `p_flex_minutes` in the set → `invalid_flexibility`. `p_time` must be whole minutes and `>= '00:00'` and `< '24:00'` (Postgres accepts `24:00:00`, which would mean the next date) → otherwise `invalid_time`. The column has the same check: `check (departure_time < '24:00' and extract(second from departure_time) = 0)`.
9. `p_seats` between 1 and the caller's car type `passenger_seats` → `invalid_seats`.
10. Texts are trimmed; empty becomes null. Lengths are checked → `invalid_pickup_note` or `invalid_notes`. Then the **contact filter** `public.taw29_has_contact(text) returns boolean` (internal, immutable) runs on each text:
   1. **Base form:** Unicode NFKC (which also maps full-width letters and digits), then lower case, then Arabic-Indic `٠–٩` (U+0660–0669) and Extended Arabic-Indic `۰–۹` (U+06F0–06F9) translated to ASCII digits, the same translation as TAW-4's `plate_normalized`. These are the only digit scripts covered (plus those NFKC maps to ASCII, such as full-width digits). Other scripts are out of scope.
   2. **E-mail and link check** on the base form, punctuation kept: rejected if it matches `[a-z0-9._%+-]+@[a-z0-9-]+(\.[a-z0-9-]+)+`, `https?://`, `www\.`, `wa\.me/` or `t\.me/`.
   3. **Digit check** on a separate compacted copy of the base form, with spaces, dots, dashes, slashes, parentheses, `+` and tatweel removed: rejected if it contains a run of 7 or more digits.
   4. Any rejection → `contact_details_not_allowed`.

   This is a best-effort control (section 12).
11. Dates:
    - `p_date` before today, or `departs_at <= now()` → `in_past`;
    - `p_date` after the window → `beyond_window`;
    - weekdays and `p_date` not Sunday to Thursday → `invalid_weekday`.
12. **Limits** (Proposal, values in `ride_limits()`):
    - at most **10 series** created by the caller in the last rolling 24 hours (replays excluded) → `rate_limited`;
    - at most **3 active weekdays series** per caller → `too_many_series`.
13. **Duplicates:** any generated date on which the caller already has a `scheduled` ride on the same route and direction departing within ±60 minutes → `duplicate_ride`.
14. Insert the series. Insert its rides: `once` → one row for `p_date`; `weekdays` → one row for each weekday date from `p_date` to the end of the window whose `departs_at > now()`. Each row gets a share code (section 9.1).
15. Insert one `ride_posted` event (`series_id`, `ride_id` = first ride, `repeat`, `ride_count`).
16. Return `{series_id, ride_id, share_code, ride_count, replayed: false}`. `ride_id` and `share_code` are those of the first ride. Step 14 stores `ride_id` and `ride_count` as `published_ride_id` and `published_ride_count`.

### 5.3 Reading rides (AC4, AC6)

The **ride projection** is the only shape any reader returns:

- `ride_id`, `share_code`, `route_id`, `direction`;
- `from_name`, `from_area`, `to_name`, `to_area`, `duration_minutes`;
- `ride_date`, `departure_time`, `departs_at`, `flex_minutes`. `departure_time` is the **effective** Cairo wall-clock time, `(departs_at at time zone 'Africa/Cairo')::time`, so a requested skipped time (00:30 on the spring-forward day) is returned as 01:30. `ride_date` is the row's date, which always equals `(departs_at at time zone 'Africa/Cairo')::date` because times are below 24:00 (step 8) and a skipped time moves forward within the same date. A pgTAP test asserts both equalities for every generated ride. The driver's requested time stays in `ride_series.departure_time`;
- `seats_offered`, `seats_left`, `repeat`, `pickup_note`, `notes`, `created_at`, `state`, `is_own`;
- `owner_display` = first name plus the first letter of the last name and a dot (for example "Ahmed M."), `owner_initials`, `owner_member_since` (month and year of `accounts.created_at`), `owner_phone_verified`;
- `car_label`, built **only from catalogue names**, never from TAW-4 free text (`brand_other`, `model_other` are validated only for length and could hold anything):
  - catalogue brand and catalogue model → "<brand> <model> · <type name>" (for example "Hyundai Elantra · Sedan");
  - catalogue brand, free-text model → "<brand> · <type name>";
  - free-text brand → "<type name>" only.

The projection **never** includes the owner's user id, last name, phone number, plate, community, car year or any TAW-4 free-text value. `ride_date` and `departure_time` are returned as effective local values. The app displays them as given and never converts time zones, so the fallback formatter of section 4 (V4) and the `Intl` path show the same value. Jest covers both paths, including the 01:30 case.

All readers require a caller: no `auth.uid()` → `not_authenticated`. The caller also needs a completed profile (`profile_completed_at` not null) → otherwise `profile_incomplete`. `anon` cannot execute them.

**`public.list_rides(p_route_id uuid, p_direction text, p_day date default null, p_after_departs_at timestamptz default null, p_after_id uuid default null, p_limit int default 30) returns setof jsonb`**

Returns rides where all of these hold:

- `route_id = p_route_id` and `direction = p_direction`;
- `status = 'scheduled'` and the series is `active`;
- `departs_at > now()`;
- `seats_taken < seats_offered`;
- the owner is currently eligible to post (`taw29_post_eligible(owner)`: phone verified and car approved at the current revision), so rides of a `withdrawn` owner are never listed and `owner_phone_verified` is always true in the list;
- if `p_day` is given, `ride_date = p_day`; if not, `ride_date` is anywhere in the window.

Results are ordered by `(departs_at, id)` and paged by keyset after `(p_after_departs_at, p_after_id)`: the next page starts strictly after that pair.

Argument contract:

- `p_route_id` and `p_direction` are required → `missing_argument` when null.
- `p_day` null means the whole window.
- The two cursor arguments are both null (first page) or both non-null → otherwise `invalid_cursor`.
- `p_limit` null means 30; outside 1–50 → `invalid_limit`.

Error codes:

- `p_day` outside the window → `invalid_day`;
- an inactive or unknown route → `invalid_route`;
- a direction outside the set → `invalid_direction`.

The caller's own rides are included and flagged `is_own` (Proposal: drivers see their ride as riders do).

**`public.get_ride(p_ride_id uuid, p_source text) returns jsonb`** (`p_source` in `list` or `published`)

- Returns the projection for any ride (any state), so the detail screen can show D4-style states.
- A null or unknown id → `ride_not_found`. A null or unknown `p_source` → `invalid_source`.
- It logs `ride_viewed` (section 10) unless the caller owns the ride.

**View logging never fails a read.** Both `get_ride` and `resolve_shared_ride` write the view through `public.taw29_log_view(...)` (internal). It runs the insert inside its own PL/pgSQL `begin … exception when others then … end` block, a subtransaction:

- a conflict on the unique index is avoided by `on conflict do nothing`;
- any other insert error is caught, the subtransaction is rolled back, and a warning (`raise warning 'taw29_view_log_failed'` with the SQLSTATE only, no user data) is emitted;
- the read then returns normally.

`ride_posted` is the opposite: it is written in the publish transaction without exception handling, so a failed event fails the publish and no series exists without its event (section 10). Tests inject a failure for both cases (section 13).

**`public.resolve_shared_ride(p_code text) returns jsonb`**

- Normalises the code: trims it, upper-cases it and maps `O→0`, `I→1`, `L→1`.
- A null code, an invalid format or an unknown code → `{state: 'not_found'}`, the same response in each case.
- Otherwise it returns `{state, ride: projection}`, where `state` is `available`, `full`, `departed`, `cancelled` or `withdrawn` (section 3.2).
- It logs `ride_viewed` with source `link` unless the caller is the owner.

## 6. Authorisation, manual verification and the launch gate (AC1, AC8)

### 6.1 Server-side rule

Publishing is possible only through `publish_ride`, which calls `require_phone_verified()` and `can_post_rides()` (steps 5–6, under the locks of step 3) before any write. Client roles have no table privilege on `ride_series`, `rides` or `pilot_events` (section 14). There is therefore no write path without the gate.

The app's checks (`can_publish()` at entry, error mapping at publish) only choose the message. They authorise nothing.

### 6.2 What the user sees

When "Post a ride" is tapped (from the D1 floating button, the D3 button or the D4 links), the app calls `can_publish()`:

- `phone_unverified`: a not-verified message screen built with the existing `States` component. The copy is in section 11.4. There is no Figma frame for it; the TAW-26 screens arrive with TAW-5.
- `car_not_approved`: the existing TAW-4 car status route `(verify)/status`.
- `ok`: P1a.

If `publish_ride` later raises `phone_unverified` or `car_not_approved` (the flag changed mid-flow), the same screens show. The draft in memory is discarded; there are no drafts.

### 6.3 Manual admin path and runbook (until TAW-5 is DONE)

The implementation adds a "Pilot test accounts and rides" section to `supabase/README.md`:

- **Verify a test account.** In the Supabase dashboard SQL editor (database owner role) or with service-role SQL:

  ```sql
  update public.accounts set phone_e164 = '<+20 test number>', phone_verified = true where user_id = '<uuid>';
  ```

  - Only for internal test accounts named in the evidence log outside the repository (no user ids or numbers are committed).
  - Each test account needs a distinct number (the verified-number unique index).
  - Undo with `phone_verified = false`.
- **Approve a test car:** the existing TAW-4 `review_item` (service role).
- **Change the pilot route** (AC2): update or insert `places` and `routes` rows. Deactivating a route hides its rides from `list_rides` and blocks new posts on it.
- **Stop a series until TAW-30:** in one transaction (SQL editor), first `update ride_series set status = 'cancelled', cancelled_at = now()` for that series (lock 3 of section 8.1), then set its rides with `departs_at > now()` to `status = 'cancelled', cancelled_at = now()`. Existing links then show D4b.

No function and no client path sets `phone_verified`. TAW-29 adds no privilege on `accounts`.

### 6.4 Launch gate (AC8)

The public pilot does not open until TAW-5 is DONE. This is a **procedural, owner-run gate** (there is no CI/CD or store pipeline in the repository). The runbook states it as a release checklist item, together with: "manual verification is for internal test accounts only; before the public pilot, every manually verified account is listed and either re-verified through TAW-5 or set back to unverified". TAW-29 does not claim a technical enforcement of AC8. The TAW-29 card evidence records that the gate is open only for internal testing.

## 7. List rules (AC4)

The rules are those of `list_rides` (section 5.3). They are enforced in SQL, not in the app. D1 controls:

- The route pill shows the single active route (several active routes would show a picker; the pilot has one).
- The direction segment ("To New Cairo" / "To 10th of Ramadan") sets `p_direction`.
- The day chips "All", "Today", "Tomorrow" and "Pick a date" set `p_day`. "Pick a date" offers only the window's dates.
- Pull-to-refresh reloads the list. A list item that has meanwhile become full, cancelled or departed is shown in its D2/D4 state when opened.
- D3 shows when the list is empty for the chosen direction and day. "Try another day" opens the day picker; "Post a ride" starts posting.

## 8. Weekday series (AC5)

- P1a "Repeat": "One ride" → `once`; "Weekdays" → `weekdays`.
- `public.extend_weekday_series() returns int` creates the missing rides (count returned) for each `active` weekdays series. It runs as the database owner from `pg_cron`. `auth.uid()` is null there, so **it never calls `can_post_rides()` or `is_phone_verified()`**, which read `auth.uid()`. It uses the internal `public.taw29_post_eligible(p_user uuid) returns boolean`: `accounts.phone_verified` **and** the exact TAW-4 condition of `can_post_rides()` for that user. A pgTAP test asserts it equals `is_phone_verified() and can_post_rides()` evaluated as that user for every fixture state (verified or not; role rider, car_owner or both; car pending, approved, rejected or stale revision; no car).
- Scheduling: `pg_cron` job `taw29-extend-weekday-series`, hourly at minute 7. The job is created by the migration (`create extension if not exists pg_cron`). Hourly means a new window day appears within an hour after Cairo midnight. That the extension and job can be created this way on the local stack and the hosted project is **UNVERIFIED** (V3). If the hosted project refuses, the plan's fallback is the dashboard's cron integration, which is an owner-run step.
- No end date (Owner, O3). A series stops only when cancelled (TAW-30, or the runbook until then).

### 8.1 Locking, authorisation point and concurrency

**Lock order** for every writer of ride data, always in this order and never in reverse:

1. the owner's `accounts` row (`for update`);
2. the owner's `verification_items (user_id, 'car_owner')` row (`for share`);
3. the `ride_series` row (`for update`);
4. `rides` rows.

`publish_ride` takes 1–2 (section 5.2 step 3) and creates 3–4. TAW-4's `set_role` and `complete_profile` lock the `accounts` row `for update` first (**Fact**, migration), so a role change is serialised by lock 1 too.

**Extension.** The function first takes `pg_try_advisory_xact_lock(hashtext('taw29-extend-weekday-series'))`. If another run holds it, it returns 0 at once, so overlapping runs never interleave. Then, for each candidate series id (read without locks), in id order:

- take locks 1, 2 and 3 in order;
- re-read the series and skip it unless it is still `active` and `repeat = 'weekdays'`;
- skip it unless `taw29_post_eligible(owner)` is true. This is the **authorisation point**, evaluated under locks that an admin's `update accounts set phone_verified …` (row lock on 1) and TAW-4 `review_item` (update of 2) must wait for;
- insert each missing weekday date in the window on or after `first_date` whose `departs_at > now()`, with `on conflict (series_id, ride_date) do nothing`, so it is idempotent and a day kept with status `cancelled` (TAW-30) is never recreated;
- **skip** (not fail) any date on which the owner already has another `scheduled` ride on the same route and direction within ±60 minutes, so a series that paused while its owner was ineligible cannot create duplicates with rides posted meanwhile. Limits do not apply to extension.

The whole run is one transaction. The pilot has few series, so lock hold times are short (Proposal; the plan measures one run).

**Semantics of the authorisation point** (accepted, like TAW-5's rule):

- A revocation (`phone_verified` set false, car review set rejected) that commits **before** extension locks the owner stops new days from that run on.
- One that commits **after** the check waits for the extension transaction. The days it created stay, as do rides published before a revocation. Existing rides are not withdrawn automatically; the runbook's "stop a series" does that.
- Every ride of an owner who is no longer eligible becomes `withdrawn` at read time: it is hidden from `list_rides`, and links show D4b (sections 3.2 and 5.3).

**Cancellation** (runbook now, TAW-30 later) locks 3 then 4, a suffix of the order, so it cannot deadlock with extension or publish. Extension re-reads the series status under lock 3, so it never adds days to a series cancelled before it got the lock. If cancellation commits after, it cancels those days too, because it updates all future rows of the series under lock 3. The runbook statement does both updates in one transaction, series first.

**Concurrency tests** (`supabase/tests/taw29/concurrency.sh`, two `psql` sessions on the local stack, paused with `pg_sleep` or advisory locks, as TAW-7's `first-signin.sh` does). Expected outcomes:

1. Extension vs admin revocation of `phone_verified`, both orders: revoke-first → no new days; extension-first → revocation waits, and the days exist.
2. Extension vs `review_item` rejecting the car, both orders, with the same results.
3. Extension vs runbook cancellation, both orders: no `scheduled` future ride of the series remains after both commit.
4. Two overlapping extension runs: the second returns 0, and the row count equals one run's.
5. Extension vs `publish_ride` by the same owner at the same time and direction: no pair of `scheduled` rides of that owner within ±60 minutes exists afterwards.
6. Two concurrent publishes with the same `request_id`: one series and one event; both responses have equal publish results (section 5.2 step 4), one with `replayed: false` and the other with `replayed: true`.

## 9. WhatsApp link (AC6)

### 9.1 Share code

- 8 characters from Crockford base32 (`0-9 A-H J K M N P-T V-Z`, 40 bits), generated from `extensions.gen_random_bytes`.
- A new code is drawn on a unique collision, up to 5 attempts, then `share_code_unavailable`.
- Each ride (day) has its own code. P2/P3 share the first ride of the series.
- Codes are not secret from signed-in users (the list returns them). They only stop a link from revealing anything to someone without the app and a completed profile.

### 9.2 Message (P3)

Built on the device from the projection, in English:

```
Tawsila · ride offer
<from> → <to>
<Ddd d Mmm> · leaves around <h:mm AM>[ · weekdays]
<n> seat(s) offered
<SHARE_LINK_BASE_URL>/r/<share_code>
```

- It contains no name, phone number, pickup note, notes, car or plate. A unit test asserts this for a fixture holding all of them.
- "Open WhatsApp" opens `https://wa.me/?text=<urlencoded message>`.
- If opening fails, the system share sheet (`Share.share`) is used with the same text.
- P2 "Share on WhatsApp" and D2 "Share on WhatsApp" open P3.

### 9.3 Link base URL and universal link (Owner, O2)

- `EXPO_PUBLIC_SHARE_LINK_BASE_URL` (for example `https://tawsila.app`) is configuration in `apps/mobile/.env`.
- `app.json` becomes `app.config.ts` that adds `ios.associatedDomains: ['applinks:<host>']` only when the variable is set to an `https` URL.
- When the variable is unset (development), the message uses `tawsila://r/<code>`, and the share sheet shows "Development link" so it is never mistaken for a release link.
- **Release requirement:** an internal-test build that is handed to testers has the https base URL set (runbook checklist).

TAW-29 delivers, under `web/share/`:

- `.well-known/apple-app-site-association`: `{"applinks":{"details":[{"appIDs":["<TEAM_ID>.com.designmasr.tawsila"],"components":[{"/":"/r/*"}]}]}}`. `<TEAM_ID>` is filled in by the owner at deployment because the team id is the owner's.
- `r/index.html`: a static fallback page ("Open this ride in the Tawsila app. Tawsila is in internal testing."). It has no ride data and no tracking.

The owner-run steps, none authorised by TAW-29:

1. Choose or buy the domain.
2. Host `web/share/` on it, serving the association file over https as `application/json` without redirects.
3. Fill in the team id.
4. Enable Associated Domains for the app id.
5. Rebuild the dev client.

Until they are done, AC6's "opens the installed app from WhatsApp" is verified with the scheme link (V1) and stays **pending V2** for the universal link.

Whether Supabase's default domain could host the page was not relied on: the owner chose their own domain. No claim about Supabase HTML hosting is made.

### 9.4 Opening a link

The expo-router route `app/r/[code].tsx` serves both `https://<host>/r/<code>` (universal link) and `tawsila://r/<code>`.

- Signed out, or profile incomplete (app installed): the incoming link is **kept and resumed**. `src/app/+native-intent.tsx` (expo-router's `redirectSystemPath`) recognises `/r/<code>` (https or `tawsila://`) and stores the code in a `pendingSharedRide` holder (in memory, with the time it arrived) before routing continues. The existing guard shows sign-in or onboarding. When the auth state becomes `ready_to_browse`, `AuthRoutes` replaces the route with `/r/<code>` once and clears the holder.
  - The holder is cleared on sign-out, when the app process ends (it is in memory only), and after 30 minutes (Proposal).
  - A newer link replaces an older one.
  - Not in TAW-29: **deferred** deep links, which return a user to the ride after they *install* the app.
- Signed in with a completed profile: it calls `resolve_shared_ride` and shows:

| `state` | Screen | Actions |
|---|---|---|
| `available` | D2 Ride detail | Request a seat (disabled, O4), Share on WhatsApp |
| `full` | D4a "This ride is full. <owner first name> has no seats left on <Ddd d Mmm>. Other rides on the same day are listed on the Rides tab." | "See rides on <Ddd d Mmm>" → Board with that direction and day; "Post a ride" |
| `departed`, `cancelled`, `withdrawn` | D4b "This ride is no longer available. It was cancelled or has already left. Shared links always show the latest status." | "See current rides" → Board with that direction, All; "Post a ride" |
| `not_found` | D4b without the ride card | as above, Board with the default direction |
| network or server error | the existing error state with Retry | — |

The state always comes from the server at open time. Nothing is cached.

## 10. Events for the pilot measures (AC7)

- **`ride_posted`:** one row per successful, non-replayed publish, written inside the `publish_ride` transaction. It has `repeat` and `ride_count`, and it rolls back if the publish fails.
- **`ride_viewed`:** written by `get_ride` (source `list` or `published`) and `resolve_shared_ride` (source `link`, including `full`, `departed` and `cancelled` states, which the pilot measures as link reach), with the state at view time.
  - Not written when the viewer owns the ride or for `not_found`.
  - At most one per user, ride and Cairo day (unique index, `on conflict do nothing`).
- No client role can read or write `pilot_events`. The owner reads it with SQL for the pilot measures. Retention: kept for the pilot; rows go with the account (`on delete cascade`). Account deletion is a later card.

## 12. Privacy and security

- No **system-provided** field discloses the owner's user id, last name, phone number, plate, community or TAW-4 free text. The privacy notices of P1c and D2 state this.
- The two driver-written fields (`pickup_note`, `notes`) are the only free text riders see. The contact filter (section 5.2 step 10) blocks e-mail addresses, links and digit runs written in ASCII, Arabic-Indic, Extended Arabic-Indic or full-width digits (no other scripts). A driver can still disclose details in words (for example spelling a number out, or describing their home). That residual risk is accepted for the internal pilot, and the remedy is a report (TAW-32). The spec makes no absolute claim beyond this.
- The share message carries route, day, time and seats only (section 9.2).
- No client role reads ride tables directly, so RLS mistakes cannot leak columns. The projection is the single disclosure surface. pgTAP asserts its exact key set **and** its values against private-data fixtures: a vehicle whose `brand_other` and `model_other` hold a phone number and a plate, a plate, a last name and a community, none of which may appear anywhere in the serialised projection, the event rows or the share message.
- `publish_ride` serialises per user and is idempotent. Limits are Proposals.
- Logs: the app never logs RPC payloads, share codes or notes (a test, following the TAW-4 `noLogging` pattern).

3. requires at least the catalogue assertion for that cell to fail, plus, for cells that have one, the behavioural assertion;
4. rolls back.

It also runs these structural mutations:

- disable RLS on `places` and on `routes`;
- replace the active-only policy with `using (true)`;
- remove `security definer` from `publish_ride`;
- set `publish_ride`'s `search_path` to `public`;
- grant `update (passenger_seats)` on `car_types` to `authenticated`.

The script exits non-zero if any mutation leaves the tests green, and it prints the number of mutations and of detected failures. Its output is stored in the card evidence.

## 14. Least-privilege check (CLH template)

Roles checked: `PUBLIC`, `anon`, `authenticated`, `service_role`, and owner = the database owner role (migrations, SQL editor, `pg_cron`). Table privileges checked: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER` and `MAINTAIN` (Postgres 17, `major_version = 17` in `supabase/config.toml`). Function privilege: `EXECUTE`. Every new table starts with `revoke all … from public, anon, authenticated, service_role`, and every new function with `revoke all on function … from public, anon, authenticated, service_role`.
