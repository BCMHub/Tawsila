## 1. Purpose and boundaries

A phone-verified rider with a completed profile requests seats on a posted ride, for that one day or, on a weekday series, for every weekday from that day on. The driver sees the requests and accepts or declines each one. The server allocates seats so that no ride day is ever overbooked. The rider can withdraw a pending request. Either side can cancel one day, chosen days or the whole series, with a reason; nobody is penalised. Pending requests expire at departure and when their day is cancelled. Both sides see current status in the app (My trips, the ride, the request).

In TAW-30: sections 3–12. Not in TAW-30:

- Push notifications (separate PROPOSED card, Owner; needs a paid Apple Developer account).
- Chat, a pickup agreement in chat and in-chat ride offers (TAW-31). Completion, no-shows, ratings, reports and blocks (TAW-32).
- The phone OTP flow and the TAW-26 verification screens (TAW-5).
- Editing a request after it is sent; waitlists; a weekdays member adding back a single day they cancelled while still a member (they may leave and request again, R9d: "You can request to join again later").
- Self-service account deletion (a later card; section 3.5 gives the admin path).
- Android (D10) and Arabic/RTL.

## 2. Decisions and inherited facts

**Owner decisions (TAW-30 scope revision 3, 2026-11-21):**

- **O1 Push.** No push in TAW-30; status is shown in the app (AC5).
- **O2 Every-weekday request.** One request for the whole series. Accepting is all-or-nothing on seats; the rider then holds the seat on every upcoming day from their first day on, including days the weekday job adds later, until they cancel days or leave (AC8).
- **O3 Expiry.** A pending request expires at departure and when its day (or the series) is cancelled. A request asking for more seats than are left cannot be accepted (R6) and stays pending (AC4).
- **O4 Later-card items** on R1–R9f follow the TAW-29 O4 rule (AC10, section 11.2).

## 3. Data model (one schema migration)

New tables live in `public`, have RLS enabled and **no policies**, and **no privilege for any API role** (`anon`, `authenticated`, `service_role`); section 14. Every read and write goes through the `security definer` functions of section 5. No column, argument or screen field holds a price, fare, cost, amount or currency (AC6).

### 3.1 `seat_requests`

| Column | Constraint |
|---|---|
| `id` | `uuid` pk default `gen_random_uuid()` |
| `rider_id` | `uuid not null references accounts(user_id) on delete no action` (3.5) |
| `client_request_id` | `uuid not null`; `unique (rider_id, client_request_id)` |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `anchor_ride_id` | `uuid not null references rides on delete cascade`: the day the rider asked for; for `weekdays`, the first day |
| `anchor_date` | `date not null` (copied from the anchor ride) |
| `kind` | `text not null check in ('one_day','weekdays')` |
| `seats` | `smallint not null check between 1 and 8` |
| `pickup_text` | `text`, null or trimmed 1–80: the rider's pickup suggestion; null means the driver's pickup note |
| `message` | `text`, null or trimmed 1–200 |
| `status` | `text not null default 'pending' check in ('pending','accepted','declined','withdrawn','expired','cancelled')` |
| `expired_cause` | `text check in ('departed','ride_cancelled')`; not null exactly when `status = 'expired'` |
| `decided_at` | `timestamptz`; not null exactly when `status in ('accepted','declined','cancelled')` |
| `closed_at` | `timestamptz`; not null exactly when `status in ('declined','withdrawn','expired','cancelled')` |
| `closed_by_side` | `text check in ('rider','owner','system')`; not null exactly when `closed_at` is not null |
| `created_at` | `timestamptz not null` (the decision time, 5.0) |

Table checks state each "exactly when" pairing. Input columns never change after insert. Status moves only forward: `pending → accepted | declined | withdrawn | expired`, `accepted → cancelled`; a test asserts no function performs another transition. Every update that changes `status` sets every column the target status requires in the same statement.

Indexes: `(series_id, status)`, `(anchor_ride_id) where status = 'pending'`, `(rider_id, created_at)`, and the backstop unique index `(rider_id, anchor_ride_id) where status in ('pending','accepted')`.

### 3.2 `seat_holds` (one row per request and day)

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `request_id` | `uuid not null references seat_requests on delete cascade` |
| `ride_id` | `uuid not null references rides on delete cascade` |
| `seats` | `smallint not null check between 1 and 8` (copied from the request) |
| `status` | `text not null default 'held' check in ('held','cancelled')` |
| `cancellation_id` | `uuid references cancellations(id)`; not null exactly when `status = 'cancelled'` |
| `cancelled_at` | `timestamptz`; not null exactly when `status = 'cancelled'` |
| `created_at` | `timestamptz not null` |

`unique (request_id, ride_id)`; index `(ride_id) where status = 'held'`. A cancelled hold sets `status`, `cancelled_at` and `cancellation_id` in one statement.

**Seat invariant (AC2).** For every ride, `rides.seats_taken = coalesce(sum(seats) of its 'held' holds, 0)`. Only the functions of section 5, `extend_weekday_series` and `taw30_release_user` (3.5) change holds or `seats_taken`, always together, under the series lock (8.1). The TAW-29 check `seats_taken between 0 and seats_offered` is the last line of defence. pgTAP asserts the invariant for every ride after every scenario (section 13).

### 3.3 `cancellations` (AC3)

One row per cancelled ride day per action; a zero-day leave or stop (5.5–5.6, weekdays only) has one row with `ride_id` null.

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `action_id` | `uuid not null`: shared by the rows of one user action |
| `actor_id` | `uuid not null references accounts(user_id) on delete no action` (3.5) |
| `actor_side` | `text not null check in ('rider','owner')` |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `ride_id` | `uuid references rides on delete cascade`; null only with `scope = 'all'` |
| `request_id` | `uuid references seat_requests on delete cascade`; not null exactly when `actor_side = 'rider'` |
| `scope` | `text not null check in ('one_day','chosen_days','all')` |
| `reason` | `text not null`; rider: `change_of_plans`, `found_another_ride`, `owner_changed_plan`, `something_else`; owner: `change_of_plans`, `car_not_available`, `not_enough_riders`, `something_else` (a check ties each set to `actor_side`) |
| `created_at` | `timestamptz not null` (the action's decision time) |

Unique `(action_id, ride_id)`; a partial unique index `(action_id) where ride_id is null`. Each cancelled hold points to **its own day's** row; rows of one action share only `action_id`. No free text; no penalty, fee, score or counter is derived (AC3).

Withdrawing a **pending** request (R2 "Cancel request") is not a seat cancellation: it records actor (`closed_by_side = 'rider'`) and time (`closed_at`) on the request, with no reason (no sheet in the approved design; Proposal), and logs `request_withdrawn`.

### 3.4 `pilot_events` (TAW-29 table, changed; AC7)

The migration reads the actual names of the two TAW-29 checks from `pg_constraint` (V8), drops **both**, and adds:

- Columns (nullable): `request_id uuid references seat_requests on delete set null`, `request_kind text`, `seats smallint`, `scope text`, `reason text`, `day_count smallint`, `cause text`.
- A new `event_type` check with the two TAW-29 types and `request_created`, `request_accepted`, `request_declined`, `request_withdrawn`, `seat_cancelled`, `ride_cancelled`, `request_expired`.
- A new table check: the two TAW-29 branches exactly as before, each additionally requiring the seven new columns to be null; plus one branch per new type:

| `event_type` | `user_id` | Non-key columns that must be set | All other optional columns |
|---|---|---|---|
| `request_created` | rider | `request_kind`, `seats` | null |
| `request_accepted` | owner | `request_kind`, `seats`, `day_count` | null |
| `request_declined`, `request_withdrawn` | owner / rider | — | null |
| `seat_cancelled` | rider | `scope`, `reason` (rider set), `day_count` | null |
| `ride_cancelled` | owner | `scope`, `reason` (owner set), `day_count` | null |
| `request_expired` | rider | `cause` | null |

Value checks: `request_kind in ('one_day','weekdays')`, `seats between 1 and 8`, `scope in (…)`, `day_count >= 0`, `cause in ('departed','ride_cancelled')`.

Key columns (`series_id`, `ride_id`, `request_id`) are not in the check, because `on delete set null` may null them later. Writers always set `series_id`; `request_id` for every type except `ride_cancelled`; `ride_id` = the anchor, or the first affected day, or null for a zero-day action. pgTAP asserts this per type. Every writer sets `event_day = (v_now at time zone 'Africa/Cairo')::date` and `occurred_at = v_now`. Events hold no names, phone numbers, pickup text or messages. Each is inserted inside its action's transaction, without exception handling, so a failed event fails the action. `pilot_events_one_daily_view` is unchanged.

**Grant change (F25).** The migration **revokes `SELECT` on `pilot_events` from `service_role`**. Events now link a rider's `user_id` to request ids, and no API role needs raw event rows: the pilot measures are read by the owner with SQL (TAW-29 spec 10). This tightens a TAW-29 control; the TAW-29 expected-privilege row and behavioural test for `service_role` `SELECT` on `pilot_events` are updated to "none" (13, regression).

### 3.5 Account deletion contract (pilot; F18)

The rider and actor references use `on delete no action`, which Postgres checks at the end of the deleting statement, after its cascades. So rows that the user's own series take with them (other riders' requests, holds and cancellations on that series) do not block deletion, while the user's requests on **other** owners' series do, and deletion fails cleanly instead of leaving a surviving ride with a wrong `seats_taken`. Admins delete such a user in two steps (runbook, 6.3):

1. `select public.taw30_release_user('<uuid>');` (owner-only). It takes locks in the order of 8.1 for every series the user touches (as owner or rider): accounts `for share`, series, rides, requests. Then, at `v_now`: every `held` hold of the user on a not-departed day → `cancelled` with an owner-side or rider-side cancellation row (`reason = 'something_else'`, `scope = 'all'`) and `seats_taken` reduced; every effective-`pending` request of the user → `withdrawn` (`closed_by_side = 'system'`); every active membership → `cancelled`; if the user owns active series, each is stopped exactly as `cancel_my_ride(…, 'all', …)` would; events as those functions write them. Then it deletes the user's `seat_requests` on series the user does not own (cascading their holds and rider-side cancellation rows; the holds are already `cancelled`, so no surviving ride's `seats_taken` changes), and checks the seat invariant for every touched ride (raising `seat_invariant_violated` if it fails). Owner-side cancellation rows and everything on the user's own series go with the series in step 2.
2. Delete the user (dashboard or `auth.users`); the existing cascade removes `accounts`, the user's series and rides (with the other riders' requests and holds on them, which vanish with the rides) and events.

Step 1 is the only path that deletes TAW-30 rows of a living ride. pgTAP covers it with live holds, pending requests, memberships and owned series. `closed_by_side = 'system'` is used for these withdrawals.

## 4. Time, membership and states

- **Decision time.** Every writer (client function, `extend_weekday_series` per series, `expire_seat_requests` per batch, `taw30_release_user`) captures `v_now := clock_timestamp()` **after** acquiring the locks for the rows it is about to change, and uses `v_now` — never `now()` — for departure comparisons and stored times. Readers use one `clock_timestamp()` per call.
- A ride day is **open for seats** at time t when: `rides.status = 'scheduled'`, the series is `active`, `departs_at > t`, and `taw29_ride_offerable(owner, seats_offered)`.
- **Active membership:** a request with `kind = 'weekdays'` and `status = 'accepted'`, whether or not it has a future `held` hold.
- **Member days** of a weekdays request at time t: the series' rides with `ride_date >= anchor_date`, `status = 'scheduled'`, `departs_at > t`. Acceptance (5.4) and the weekday job (8.3) use exactly this predicate.
- **Effective request state** — one function, `taw30_request_state(p_request, p_at)`, used by every reader and writer (F6). For stored `pending`: let `t_dep` = the anchor's `departs_at` if `<= p_at`; let `t_can` = the earliest of the anchor's `cancelled_at` and the series' `cancelled_at` that is `<= p_at`. If neither → `pending`. Else → `expired`, with the **earlier** trigger's values: `departed` (`closed_by_side = 'system'`, `closed_at = t_dep`) or `ride_cancelled` (`closed_by_side = 'owner'`, `closed_at = t_can`); on a tie, `ride_cancelled`. For any other stored status: the stored values. Writers that store an expiry (5.6, 8.4) store exactly the function's result, so the outcome is the same whichever writer runs first.
- **Held day state** (rider), in precedence: `cancelled` (hold cancelled; `by` = the cancellation's `actor_side`) > `departed` (`departs_at <= t`) > `unavailable` (the ride's TAW-29 state is `withdrawn`) > `confirmed`.

## 5. Server functions

### 5.0 Common rules

- All functions are `security definer`, `set search_path = ''`, schema-qualified, raise `raise exception '<code>'`, and check set membership null-safely.
- **Client functions** (the ten of section 14 with `authenticated` `EXECUTE`): first `not_authenticated` (no `auth.uid()`), except `can_request()`, which returns `'phone_unverified'` without a caller; then `missing_argument` (any required argument null). They take **no argument that names a user** and act only for `auth.uid()`.
- **Owner-only functions** (helpers, the job functions, `taw30_release_user`): not executable by any API role; they take explicit ids, never read `auth.uid()`, and validate their arguments (`missing_argument`).
- Locks follow section 8.1; after the locks, `v_now` (section 4).
- A refusal writes nothing.

### 5.1 `public.can_request() returns text` (stable)

`'phone_unverified'` unless `is_phone_verified()`; else `'profile_incomplete'` unless `can_request_rides()`; else `'ok'`. Authorises nothing.

### 5.2 `public.request_seat(p_client_request_id uuid, p_ride_id uuid, p_kind text, p_seats int, p_pickup_text text, p_message text) returns jsonb` (AC1, AC8)

Required: `p_client_request_id`, `p_ride_id`, `p_kind`, `p_seats`. Texts: null or empty after trimming means none.

1. `not_authenticated`; `missing_argument`.
2. Locks (8.1): the caller's `accounts` row `for share` (missing → `account_missing`); read the ride (unknown → `ride_not_found`) and lock its `ride_series` `for share`; the caller's rider advisory lock (level 6). Then `v_now`.
3. `require_phone_verified()` → `phone_unverified`; `can_request_rides()` false → `profile_incomplete`. The gate runs before the replay check, so a revoked rider gets no replay (F15).
4. **Idempotency.** Inputs normalised as step 7. If `(rider_id, client_request_id)` exists: when its `anchor_ride_id`, `kind`, `seats`, `pickup_text` and `message` are all `is not distinct from` the normalised inputs → `{request_id, state: <effective state>, replayed: true}`; otherwise `request_conflict` (including the same key used on another ride or series).
5. Caller owns the series → `own_ride`. The anchor must be open for seats at `v_now` and not full → `ride_unavailable`.
6. `p_kind` in the set → `invalid_kind`; `weekdays` on a `once` series → `invalid_kind`. `p_seats` between 1 and `seats_offered` → `invalid_seats`; `p_seats > seats_offered - seats_taken` of the anchor → `not_enough_seats`.
7. Texts trimmed, empty to null; lengths → `invalid_pickup_text` / `invalid_message`; `taw29_has_contact` → `contact_details_not_allowed`.
8. **Limits** (Proposal, `request_limits()`; F26): let n = the caller's requests with `created_at > v_now - interval '24 hours'` (replays create none). n ≥ 20 → `rate_limited` (the 21st is refused). 5 or more of the caller's requests in effective state `pending` at `v_now` → `too_many_pending`. Both counts run under the rider advisory lock, so concurrent sends on different series cannot both pass a boundary.
9. A request by the caller anchored on this ride was `declined` → `already_declined` (Proposal).
10. **Open requests** (Proposal): refused with `already_requested` when the caller has, in this series, an active membership, or a request in effective state `pending`, or (`one_day`) an `accepted` one-day request anchored on this ride, or (`weekdays`) any `accepted` one-day request whose day has not departed.
11. Insert the request (`pending`, `anchor_date`, `created_at = v_now`); insert `request_created`. Return `{request_id, state: 'pending', replayed: false}`.

A request reserves no seat; seats are allocated only on acceptance.

### 5.3 `public.withdraw_request(p_request_id uuid) returns jsonb` (R2 "Cancel request")

Locks: caller's `accounts` `for share`; the request's `ride_series` `for share`; the request (level 5). `v_now`. Missing or not the caller's → `request_not_found`. Effective state not `pending` → `request_not_pending`. Set `withdrawn`, `closed_at = v_now`, `closed_by_side = 'rider'`; insert `request_withdrawn`. Return the request view (5.7).

### 5.4 `public.decide_request(p_request_id uuid, p_decision text) returns jsonb` (AC2, AC4, AC8; R4–R6)

1. `not_authenticated`; `missing_argument`; `p_decision` not in `accept`, `decline` → `invalid_decision`.
2. Read the request and series without locks. Missing, or the caller does not own the series → `request_not_found` (same response).
3. Locks (8.1): the owner's and rider's `accounts` `for share` in `user_id` order; the owner's car `verification_items` `for share`; `ride_series`; for `accept`, the series' rides with `ride_date >= anchor_date` in `(ride_date, id)` order; the request. Then `v_now`.
4. Effective state not `pending` → `request_not_pending`.
5. **Decline:** `declined`, `decided_at = closed_at = v_now`, `closed_by_side = 'owner'`; insert `request_declined`; return `{result: 'declined', request: <view>}`.
6. **Accept:**
   1. Series `active` and `taw29_ride_offerable(owner, seats_offered)` → else `ride_unavailable`.
   2. Rider `accounts.phone_verified` (under the share lock) → else `requester_unavailable` (Proposal; existing holds of a revoked rider stay, as TAW-29's revocation semantics).
   3. **Target days:** `one_day` → the anchor; `weekdays` → the member days at `v_now` (4); the anchor is always one (step 4).
   4. **All-or-nothing check (O2), no writes on failure:** each target day has `seats_offered - seats_taken >= seats`; for `weekdays`, also `seats + sum(seats of the series' active memberships) <= seats_offered` (so every day the job adds later fits all members, 8.3). On failure return, **without raising**, `{result: 'seats_unavailable', request: <view>, limit: {kind: 'day', ride_id, ride_date, seats_left}}` for the earliest short day, or `{…, limit: {kind: 'members', seats_left: seats_offered - sum(members)}}`. Nothing is written; the request stays `pending` (AC4, R6).
   5. Insert one `held` hold per target day (`created_at = v_now`); add `seats` to each day's `seats_taken`.
   6. `accepted`, `decided_at = v_now`; insert `request_accepted` (`day_count` = target days); return `{result: 'accepted', request: <view>}`.

### 5.5 `public.cancel_my_seat(p_request_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (rider; AC3; R9a, R9c, R9d)

1. `not_authenticated`; `missing_argument` (request, scope, reason); `p_scope` not in `one_day`, `chosen_days`, `all` → `invalid_scope`; reason not in the rider set → `invalid_reason`.
2. Read the request; missing or not the caller's → `request_not_found`.
3. Locks: caller's `accounts` `for share`; `ride_series`; the series' rides with `ride_date >= anchor_date` in `(ride_date, id)` order; the request. `v_now`.
4. Status not `accepted` → `request_not_cancellable`.
5. **Cancellable days** = the request's `held` holds whose ride `departs_at > v_now`. **Affected days**:
   - `one_day`: `p_ride_ids` has exactly one non-null element, a cancellable day;
   - `chosen_days`: `p_ride_ids` non-empty, no nulls, no duplicates, each cancellable (weekdays requests only);
   - `all`: `p_ride_ids` null; all cancellable days.
   Any violation → `invalid_days`, nothing changed. **Zero affected days** is allowed only for `all` on an active membership (leaving a membership whose current days are all cancelled or departed; F28); for a one-day request with no cancellable day → `invalid_days` (its departed hold stays as history).
6. One `action_id`. Per affected day: insert that day's `cancellations` row (`created_at = v_now`); the hold → `cancelled`, `cancelled_at = v_now`, `cancellation_id` = that row; `seats_taken -= seats`. With zero affected days, one row with `ride_id` null.
7. The request → `cancelled` (`closed_at = v_now`, `closed_by_side = 'rider'`; `decided_at` kept) when the scope is `all`, or when it is a one-day request. A weekdays request cancelled for `one_day`/`chosen_days` stays an active membership (O2).
8. Insert `seat_cancelled` (`day_count`; `ride_id` = first affected day or null). Return the request view.

### 5.6 `public.cancel_my_ride(p_series_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (owner; AC3, AC4; R9b, R9e, R9f)

1. `not_authenticated`; `missing_argument`; `invalid_scope`; reason not in the owner set → `invalid_reason`.
2. Series missing or not the caller's → `series_not_found`.
3. Locks: caller's `accounts` `for share`; `ride_series`; all the series' `scheduled` rides in `(ride_date, id)` order; the series' requests with status `pending` or `accepted` in `id` order. `v_now`.
4. Series `cancelled` → `series_not_active`.
5. **Cancellable days** = the series' rides with `status = 'scheduled'` and `departs_at > v_now`. Affected days per scope as 5.5 step 5. A `once` series accepts only `all`, and only with its day cancellable (a departed once ride cannot be cancelled → `invalid_days`; F28). Zero affected days is allowed only for `all` on a `weekdays` series (stopping a series whose generated days have all departed).
6. One `action_id`. Per affected day: its `cancellations` row (`request_id` null, `created_at = v_now`); ride → `cancelled`, `cancelled_at = v_now`; its `held` holds → `cancelled`, `cancelled_at = v_now`, `cancellation_id` = that row (F29); `seats_taken = 0`. With zero affected days, one row with `ride_id` null.
7. Scope `all`: the series → `cancelled`, `cancelled_at = v_now`.
8. For each locked `pending` request: compute `taw30_request_state(request, v_now)` after steps 6–7; when it is `expired`, store exactly that result and insert `request_expired`.
9. Accepted requests: scope `all` → each → `cancelled` (`closed_at = v_now`, `closed_by_side = 'owner'`); otherwise, each accepted one-day request whose day was affected → `cancelled` likewise (F29). Active memberships survive a partial cancellation and keep their other days.
10. Insert `ride_cancelled` (`day_count`; `ride_id` = first affected day or null). Return `{series_id, series_status, cancelled_ride_ids}`.

## 8. Concurrency, the weekday job and expiry

### 8.1 Lock order (replaces TAW-29 8.1 for all ride and seat writers)

**Levels**, acquired by every writer in increasing order, each only as needed:

1. `accounts` rows. TAW-30 writers take them **only `for share`**, several in `user_id` order, all before any level-2+ lock.
2. The series owner's car `verification_items` row `for share`.
3. `ride_series` rows (`for no key update`; `request_seat` and `withdraw_request` take `for share`).
4. `rides` rows (`for no key update`, `(ride_date, id)` order).
5. `seat_requests` rows (`for no key update`, `id` order; queries lock with `for no key update of <the seat_requests alias>` so no joined table is locked).
6. The rider advisory lock `pg_advisory_xact_lock(hashtext('taw30-rider'), hashtext(<rider uuid>::text))` (`request_seat` only).
7. Inserts and updates of `seat_holds`, `cancellations`, `pilot_events`, `seat_requests`, `rides`, `ride_series` on rows already locked at levels 3–5 or new rows. Foreign-key checks on these inserts take `for key share` on referenced `accounts`, `ride_series`, `rides`, `seat_requests` and `cancellations` rows.

**Lock strengths.** No TAW-30 writer takes `for update` on any row or updates a key column. `for share`, `for no key update` and `for key share` are mutually compatible where it matters: a foreign-key check never waits for a TAW-30 writer. The remaining stronger locks are held by other writers on **one** row each: `publish_ride`, `set_role`, `complete_profile` (`accounts` own row, `for update`), the admin's `update accounts` (one row), `review_item` (one `verification_items` row). A TAW-30 writer's foreign-key check or level-1 lock may wait for one of them (F24); none of them waits for a lock a TAW-30 writer holds, except as follows, which is why the job is restructured (8.3): `publish_ride` inserting a share code can wait on an **uncommitted** ride with the same code through the unique index (F23).

| Writer | Order |
|---|---|
| `publish_ride` (TAW-29, unchanged) | 1 own `for update`, 2, inserts series and rides |
| admin revocation; TAW-4 `set_role`, `complete_profile` | 1 one row |
| TAW-4 `review_item` | 2 one row |
| `extend_weekday_series` (replaced) | 1 all candidate owners `for share` (`user_id` order) → 2 all their car items `for share` → per series: 3, 4 inserts, 7 |
| `request_seat` | 1 rider → 3 share → 6 → 7 |
| `withdraw_request` | 1 rider → 3 share → 5 → 7 |
| `decide_request` | 1 owner + rider → 2 → 3 → 4 (accept) → 5 → 7 |
| `cancel_my_seat` | 1 rider → 3 → 4 → 5 → 7 |
| `cancel_my_ride` | 1 owner → 3 → 4 → 5 → 7 |
| `expire_seat_requests` | per batch: 5 `skip locked` → 7 |
| `taw30_release_user` | 1 the user and every counterpart (`user_id` order) → 3 → 4 → 5 → 7 |

**Why no cycle.** (a) Among TAW-30 writers, level-1 locks are all `for share`; they block nobody but single-row `for update`/update writers. (b) From level 2 on, every TAW-30 writer acquires levels in increasing order, so TAW-30 writers cannot wait on each other in a cycle. (c) A single-row writer (publish, admin, TAW-4) waits only for its own row (held by TAW-30 writers at most `for share` until they commit) and, for `publish_ride`, for its own car item `for share` and for the share-code unique index; it never holds a lock a TAW-30 writer then needs while that writer holds what it needs — **except** a job that has inserted a ride and then waits at level 1 for that publisher (F23). The replaced job takes all its level-1 and level-2 locks **before its first insert**, so after its first insert it never waits at levels 1–2, and the cycle cannot form. (d) `expire_seat_requests` never waits at level 5 (`skip locked`) and its event inserts take only `for key share`. The F3/F4/F23 cycles are therefore removed. This is UNVERIFIED until 8.2 passes (V6).

**The series row (level 3, `for no key update`) is the serialisation point for seats.** Every writer that changes `seats_taken` or holds holds it.

### 8.2 Concurrency tests (`supabase/tests/taw30/concurrency.sh`)

Two (three where stated) `psql` sessions on the local stack, paused with advisory locks or `pg_sleep`, as TAW-29's script; both orders where order matters. Each scenario ends by asserting, for every touched ride, the seat invariant and `seats_taken <= seats_offered`; stored request states (and effective states); future `held` holds; and the exact count of each event type written. No scenario may raise a deadlock error.

1. Two accepts of different requests for a day's last seat: one `accepted`; the other returns `seats_unavailable`, stays `pending`; one `request_accepted`.
2. Weekdays accept vs one-day accept on one of its days, last seat: exactly one succeeds; the weekdays request has holds on all its target days or none.
3. Accept vs withdraw of the same request: exactly one of `accepted` / `withdrawn`; the loser raises `request_not_pending`.
4. Accept vs `cancel_my_ride(…,'all')`: cancel-first → accept raises `request_not_pending` (stored or effective `expired`, cause `ride_cancelled`); accept-first → the cancel cancels the new holds and the request becomes `cancelled`. No `held` hold on a cancelled ride.
5. The job vs a member's `cancel_my_seat(…,'all')`: afterwards the request is `cancelled` and has no `held` hold on a future day (departed holds retained).
6. The job vs a weekdays accept: the member holds every member day exactly once; no day overbooked.
7. Two `request_seat` with the same key and payload: one request, one event; one `replayed: false`, one `replayed: true`. The same key with a different ride (another series): `request_conflict`, no second request.
8. Rider `cancel_my_seat` on day D vs owner `cancel_my_ride` of D: afterwards D is cancelled with `seats_taken = 0`; the rider's call succeeded first, or raised `invalid_days` (member) or `request_not_cancellable` (one-day request closed by the owner).
9. `request_seat` vs `cancel_my_ride(…,'all')`: request-first → the cancel stores the expiry (`ride_cancelled`, one `request_expired`); cancel-first → `ride_unavailable`.
10. Decline vs withdraw: exactly one stored transition and one event; the loser gets `request_not_pending`. Decline vs `expire_seat_requests` on a request whose anchor has departed: decline raises `request_not_pending` in both orders (effective `expired`); afterwards, after at most one further job run, exactly one stored `expired` (cause `departed`) and exactly one `request_expired`.
11. `expire_seat_requests` vs `cancel_my_ride(…,'all')` on a series whose pending request's anchor departed before the cancel: stored cause `departed`, `closed_at` = departure, one event, in both orders; and a tie case (anchor cancelled at its departure instant, fixture) → `ride_cancelled`.
12. The job vs `cancel_my_ride(…,'chosen_days')`, and the job vs `cancel_my_ride(…,'all')` on a series with live memberships: no cancelled day regains a hold; after `all`, no held future hold and the memberships are `cancelled`.
13. Cycle checks: (a) the job vs a two-account `decide_request` where the job's series order is the reverse of account order (owner A is also the rider on owner B's series); (b) `withdraw_request` vs `expire_seat_requests` on the same request; (c) `cancel_my_ride` expiring rider R's request vs `request_seat` by R on the same series; (d) the job vs `publish_ride` by another owner drawing the **same share code** (forced by a test-only replacement of `taw29_new_share_code` that returns a fixed code), F23. Each completes without deadlock in both orders.
14. A lock wait that crosses departure (F5), one case per writer: session 1 holds the series lock; session 2 calls `decide_request` / `request_seat` / `withdraw_request` / `cancel_my_seat` / `cancel_my_ride` on a day departing 2 seconds later; session 1 commits after departure. Session 2 refuses (`request_not_pending`, `ride_unavailable`, `request_not_pending`, `invalid_days`, `invalid_days` respectively). The same for the job: a day whose departure passes while the job waits is not inserted.
15. Phone revocation vs `request_seat` and vs accept (rider revoked), both orders: revoke-first → `phone_unverified` / `requester_unavailable`; call-first → the revocation waits and the request or acceptance exists.
16. `taw30_release_user` vs a concurrent accept on the same series: no deadlock; afterwards the invariant holds and the released user has no `held` hold on a not-departed day.
17. **Lock-strength probes (F24):** for each client writer, session 1 runs it inside an open transaction (locks held until commit); session 2 then tries, with `nowait`, `for key share` on each row the writer locked (must succeed) and `for update` (must fail with 55P03), and `for share` on the account rows (must succeed). The job's account locks are probed the same way.

### 8.3 `extend_weekday_series` (TAW-29 function, replaced with `create or replace`)

TAW-29 8.1 semantics stay (advisory lock, re-read under lock, authorisation point, ±60-minute skip, never recreating a cancelled day, one transaction), restructured (F5, F8, F23):

1. `pg_try_advisory_xact_lock` as before.
2. Read the candidate series (unlocked). Lock **all** their owners' `accounts` rows `for share` in `user_id` order, then **all** their car `verification_items` rows `for share` in `user_id` order. Nothing is inserted before this step finishes.
3. Per series in id order: lock the series `for no key update`; re-read it (skip unless `active` and `weekdays`); skip unless `taw29_ride_offerable(owner, seats_offered)`; `v_now := clock_timestamp()`; insert each missing weekday date with `departs_at > v_now`, as TAW-29.
4. After a day is inserted (row count 1), for each active membership of the series with `anchor_date <= ride_date`, in `id` order, insert a `held` hold (`created_at = v_now`) and add its seats to `seats_taken`. Acceptance keeps the members' total within `seats_offered` (5.4 step 6.4), so the TAW-29 check cannot fail; if it did, the run fails and rolls back.

Its grants are unchanged and re-asserted. pgTAP covers the F8 backfill: a series day skipped earlier for the ±60-minute rule is created after the conflicting ride is cancelled, and only members with `anchor_date` on or before it get a hold.

### 8.4 Expiry (AC4)

- Readers show `taw30_request_state`, so a request is `expired` the moment its anchor departs or is cancelled.
- `public.expire_seat_requests()` stores it in batches of 100: select `pending` requests whose anchor `departs_at <= clock_timestamp()` with `for no key update of <seat_requests alias> skip locked`; then `v_now := clock_timestamp()`; for each locked request, compute `taw30_request_state(request, v_now)` and, when `expired`, store exactly that result and insert one `request_expired`. Repeat until a batch is empty. Returns the count; a second immediate run returns 0.
- `pg_cron` job `taw30-expire-seat-requests`, `*/5 * * * *` (Proposal), created by the migration like TAW-29's (unschedule by name, then schedule). Local: plan step; hosted: UNVERIFIED, owner-run (V3b).
- `cancel_my_ride` stores expiries synchronously (5.6 step 8).

## 12. Privacy and security

- A request's `pickup_text` and `message` are returned only to its rider and the series owner (request view). No API role reads the new tables or `pilot_events` directly (section 14). Events and cancellations hold no free text.
- Missing and foreign ids give identical responses (`request_not_found`, `ride_not_found`, `series_not_found`).
- No view discloses a user id, last name, phone, plate, community or TAW-4 free text.
- Seat allocation is serialised per series and guarded by the `seats_taken` check (AC2).
- The app never logs RPC payloads, texts or request ids (`noLogging` test).
