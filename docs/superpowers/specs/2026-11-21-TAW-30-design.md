# TAW-30 Request a seat; driver accepts or declines: design spec (scope revision 3)

Authoring card: TAW-37 (docs only, lane Standard). Implementation card: TAW-30 (lane Critical). Criteria snapshot: TAW-30 AC1–AC10, scope revision 3, sha256 `d4b99d6934cf4662dde3aaa750771c1c2259583aadd0f9b2adb38dea9f956472` (verbatim text kept outside the worktree in `.clh/evidence/TAW-37/criteria-TAW-30-rev3.md`). Approved design: Figma file `2j3vO1USLBA8XiRpQKCF3H`, page MVP `228:807`, section `228:810` "MVP · 3 Request and accept" (R1–R9f, light and dark), approved under TAW-28.

Labels: **Fact** = checked in this repository (main `4bb4e6a`) or the Figma file on 2026-11-21; **Owner** = decision recorded on the TAW-30 card (scope revision 3, 2026-11-21); **Proposal** = a tunable value or rule set by this spec, changeable without a new design; **UNVERIFIED** = must be proven by a plan step before it is relied on.

## 1. Purpose and boundaries

A phone-verified rider with a completed profile requests seats on a posted ride, for that one day or, on a weekday series, for every weekday from that day on. The driver sees the requests on the ride and accepts or declines each one. The server allocates seats so that no ride day is ever overbooked. The rider can withdraw a pending request. Either side can cancel one day, chosen days or the whole series, with a reason; nobody is penalised. Pending requests expire at departure and when their day is cancelled. Both sides see current status in the app (My trips and the ride's request list).

In TAW-30: sections 3–12. Not in TAW-30:

- Push notifications (separate PROPOSED card, Owner; needs a paid Apple Developer account).
- Chat, the pickup agreement in chat and in-chat ride offers (TAW-31). Completion, no-shows, ratings, reports and blocks (TAW-32).
- The phone OTP flow and the TAW-26 verification screens (TAW-5).
- Editing a request after it is sent, a rider re-joining a day they cancelled, waitlists, and a rider joining only some weekdays at request time.
- Android (D10) and Arabic/RTL.

## 2. Decisions and inherited facts

**Owner decisions (TAW-30 scope revision 3, 2026-11-21):**

- **O1 Push.** No push in TAW-30; status is shown in the app (AC5).
- **O2 Every-weekday request.** One request for the whole series. Accepting is all-or-nothing on seats; the rider then holds the seat on every upcoming day, including days the weekday job adds later, until they cancel days or leave (AC8).
- **O3 Expiry.** A pending request expires at departure and when its day (or the series) is cancelled. A request asking for more seats than are left cannot be accepted (R6) and stays pending (AC4).
- **O4 Later-card items** on R1–R9f follow the TAW-29 O4 rule (AC10, section 11.2).

**Facts (TAW-29 and TAW-4 migrations on main):**

- `ride_series` holds what the driver posted (`repeat` in `once`, `weekdays`; `status` in `active`, `cancelled`; `seats_offered` 1–8, immutable after insert). `rides` holds one row per day with `seats_offered` (copied), `seats_taken smallint not null default 0 check (seats_taken between 0 and seats_offered)`, `status` in `scheduled`, `cancelled`, `cancelled_at`, `departs_at`, `unique (series_id, ride_date)`. TAW-29 keeps `seats_taken` at 0; nothing writes it today.
- A ride's displayed state (`cancelled`, `withdrawn`, `departed`, `full`, `available`) is computed by the three TAW-29 readers from `rides`, `ride_series` and `taw29_ride_offerable(owner, seats_offered)`. `list_rides` returns only rides with `seats_taken < seats_offered`.
- `public.is_phone_verified()`, `public.require_phone_verified()` (raises `phone_unverified`) and TAW-4 `public.can_request_rides()` (`profile_completed_at` not null) exist, `security definer`, executable by `authenticated`.
- `public.taw29_has_contact(text)` is the contact filter (e-mail, links, digit runs of 7+ in ASCII, Arabic-Indic, Extended Arabic-Indic and full-width digits), owner-only.
- `public.extend_weekday_series()` runs hourly from `pg_cron` as the database owner. It takes `pg_try_advisory_xact_lock`, then for each active weekdays series locks the owner's `accounts` row (`for update`), the owner's `verification_items` car row (`for share`) and the `ride_series` row (`for update`), and inserts missing future weekday rows with `on conflict (series_id, ride_date) do nothing`. A day kept with status `cancelled` is never recreated.
- TAW-29 lock order (spec 8.1): accounts → verification_items → ride_series → rides. The runbook's "stop a series" cancels the series and its future rides in one transaction.
- `pilot_events` has `event_type in ('ride_posted','ride_viewed')` and a table check tying columns to the type. Client roles have no privilege on it; `service_role` has `SELECT`.
- The Trips tab (`src/app/(tabs)/trips.tsx`) is an empty `TabScreen`. D1 cards and D2 show a disabled "Request seat" / "Request a seat" (TAW-29 O4). P2's approved copy "We'll notify you for each request." was kept as pilot copy (TAW-29 deviation 7).

TAW-29 objects are kept unchanged **except** the three changes this spec names: the `pilot_events` columns and check (section 3.4), `extend_weekday_series` (section 8.3), and the TAW-29 runbook entry "stop a series" (section 6.3). TAW-29's readers are not changed.

## 3. Data model (one schema migration)

All new tables live in `public`, have RLS enabled and **no policies**. Client roles have no table privilege; every read and write goes through the `security definer` functions of section 5. No column, argument or screen field holds a price, fare, cost, amount or currency (AC6).

### 3.1 `seat_requests`

| Column | Constraint |
|---|---|
| `id` | `uuid` pk default `gen_random_uuid()` |
| `rider_id` | `uuid not null references accounts(user_id) on delete restrict` (Proposal: deleting an account that holds seats must first cancel them; account deletion is a later card) |
| `client_request_id` | `uuid not null`; `unique (rider_id, client_request_id)` (idempotency) |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `anchor_ride_id` | `uuid not null references rides on delete cascade`: the day the rider opened and asked for; for `weekdays`, the first day |
| `kind` | `text not null check in ('one_day','weekdays')` |
| `seats` | `smallint not null check between 1 and 8` |
| `pickup_text` | `text`, null or trimmed 1–80: the rider's pickup preference; null means "the driver's pickup note" |
| `message` | `text`, null or trimmed 1–200: "Message to <driver>" |
| `status` | `text not null default 'pending' check in ('pending','accepted','declined','withdrawn','expired','cancelled')` |
| `expired_cause` | `text check in ('departed','ride_cancelled')`; not null exactly when `status = 'expired'` |
| `decided_at` | `timestamptz`; not null exactly when `status in ('accepted','declined','cancelled')` (a cancelled request was accepted first) |
| `closed_at` | `timestamptz`; not null exactly when `status in ('declined','withdrawn','expired','cancelled')` |
| `closed_by_side` | `text check in ('rider','owner','system')`; not null exactly when `closed_at` is not null |
| `created_at` | `timestamptz not null default now()` |

Table checks state each "exactly when" pairing above. Inputs (`rider_id`, `series_id`, `anchor_ride_id`, `kind`, `seats`, `pickup_text`, `message`, `client_request_id`) are never updated after insert; only `status`, `expired_cause`, `decided_at`, `closed_at` and `closed_by_side` change, and only forward: `pending → accepted | declined | withdrawn | expired`, `accepted → cancelled`. A test asserts no function performs another transition.

Indexes: `seat_requests (series_id, status)`, `seat_requests (anchor_ride_id) where status = 'pending'`, `seat_requests (rider_id, created_at)`, and a partial unique index `seat_requests (rider_id, anchor_ride_id) where status in ('pending','accepted')` (a backstop for rule 13 of section 5.2).

### 3.2 `seat_holds` (one row per request and day)

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `request_id` | `uuid not null references seat_requests on delete cascade` |
| `ride_id` | `uuid not null references rides on delete cascade` |
| `rider_id` | `uuid not null` (copied from the request) |
| `seats` | `smallint not null check between 1 and 8` (copied from the request) |
| `status` | `text not null default 'held' check in ('held','cancelled')` |
| `cancelled_at` | `timestamptz`; `check ((status = 'cancelled') = (cancelled_at is not null))` |
| `cancellation_id` | `uuid references cancellations(id)`; not null exactly when `status = 'cancelled'` |
| `created_at` | `timestamptz not null default now()` |

`unique (request_id, ride_id)`. Index `seat_holds (ride_id) where status = 'held'`.

**Seat invariant (AC2).** For every ride, `rides.seats_taken = coalesce(sum(seats) of its holds with status 'held', 0)`. Only the functions of section 5 and `extend_weekday_series` write `seats_taken`, always in the same statement block that inserts or cancels the holds, under the ride's row lock (section 8.1). The TAW-29 check `seats_taken between 0 and seats_offered` is the last line of defence: an allocation that would exceed it fails the statement. pgTAP asserts the invariant for every ride after every test scenario, and the concurrency script asserts it after every interleaving (section 13).

### 3.3 `cancellations` (AC3)

One row per cancelled ride day per action:

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `action_id` | `uuid not null`: groups the rows of one user action (chosen days → several rows) |
| `actor_id` | `uuid not null references accounts(user_id) on delete restrict` |
| `actor_side` | `text not null check in ('rider','owner')` |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `ride_id` | `uuid not null references rides on delete cascade` |
| `request_id` | `uuid references seat_requests on delete cascade`; not null exactly when `actor_side = 'rider'` |
| `scope` | `text not null check in ('one_day','chosen_days','all')` |
| `reason` | `text not null`; rider: `change_of_plans`, `found_another_ride`, `owner_changed_plan`, `something_else`; owner: `change_of_plans`, `car_not_available`, `not_enough_riders`, `something_else` (a check ties each set to `actor_side`) |
| `created_at` | `timestamptz not null default now()` |

`unique (action_id, ride_id)`. The record holds no free text (the R9 sheets offer only fixed reasons). No penalty, fee, score or counter is derived from it in TAW-30.

Withdrawing a **pending** request (R2 "Cancel request") is not a seat cancellation: it records the actor (`closed_by_side = 'rider'`) and time (`closed_at`) on the request, with no reason (no sheet in the approved design; Proposal), and logs `request_withdrawn`.

### 3.4 `pilot_events` (TAW-29 table, changed; AC7)

The migration drops the TAW-29 table check and adds columns and a new check. Existing rows remain valid.

- New event types: `request_created`, `request_accepted`, `request_declined`, `request_withdrawn`, `seat_cancelled`, `ride_cancelled`, `request_expired`.
- New nullable columns: `request_id uuid references seat_requests on delete set null`, `request_kind text check in ('one_day','weekdays')`, `seats smallint check between 1 and 8`, `scope text check in ('one_day','chosen_days','all')`, `reason text`, `day_count smallint check (day_count >= 0)`, `cause text check in ('departed','ride_cancelled')`.
- The check keeps the two TAW-29 branches unchanged (each also requires the new columns to be null) and adds:

| `event_type` | `user_id` | Required (not null) | Others |
|---|---|---|---|
| `request_created` | rider | `series_id`, `ride_id` (anchor), `request_id`, `request_kind`, `seats` | null |
| `request_accepted` | owner | `series_id`, `ride_id`, `request_id`, `request_kind`, `seats`, `day_count` | null |
| `request_declined` | owner | `series_id`, `ride_id`, `request_id` | null |
| `request_withdrawn` | rider | `series_id`, `ride_id`, `request_id` | null |
| `seat_cancelled` | rider | `series_id`, `request_id`, `scope`, `reason`, `day_count` | `ride_id` = first cancelled day |
| `ride_cancelled` | owner | `series_id`, `scope`, `reason`, `day_count` | `ride_id` = first cancelled day; `request_id` null |
| `request_expired` | rider | `series_id`, `ride_id`, `request_id`, `cause` | null |

The table check enforces the non-key columns of each row of this table (`request_kind`, `seats`, `scope`, `reason`, `day_count`, `cause`, null or not null by type, and the reason set by `actor` side: rider reasons for `seat_cancelled`, owner reasons for `ride_cancelled`). The key columns (`series_id`, `ride_id`, `request_id`) are **not** in the check, because `on delete set null` may later null them; the writing functions always set them, and pgTAP asserts that for every event type. Events hold no names, phone numbers, pickup text or messages. Every event is written inside the transaction of the action it records and without exception handling, so a failed event fails the action (as `ride_posted` in TAW-29). The unique index `pilot_events_one_daily_view` is unchanged.

## 4. Time and states

- Dates and times are Africa/Cairo as in TAW-29 section 4. "Now" is `now()`.
- A ride day is **open for seats** when: `rides.status = 'scheduled'`, its series is `active`, `departs_at > now()`, and `taw29_ride_offerable(owner, seats_offered)` is true (TAW-29 `available` or `full`).
- **Upcoming days of a weekdays request** at a given moment: the series' rides with `ride_date >= anchor ride_date`, `status = 'scheduled'` and `departs_at > now()`.
- **Displayed request state** (computed by every reader; the stored status catches up through section 8.4):
  - stored `pending` and (anchor `departs_at <= now()`) → `expired`;
  - stored `pending` and (anchor ride cancelled or series cancelled) → `expired` (normally already stored by the cancel function);
  - otherwise the stored status.
- **Held day state** for a rider (R3/R7): `confirmed` (hold `held`, day not departed, ride not cancelled), `cancelled` (hold cancelled, by `rider` or `owner` from the cancellation row), `departed` (hold `held`, departed), `unavailable` (hold `held` and the ride's TAW-29 state is `withdrawn`).

## 5. Server functions

Every function is `security definer`, `set search_path = ''`, with schema-qualified bodies, and raises `raise exception '<code>'` codes. Every set-membership check is null-safe, so a null never reaches a table constraint. Required arguments that are null raise `missing_argument` before anything else except `not_authenticated`. Privileges are in section 14.

### 5.1 `public.can_request() returns text` (stable)

`'phone_unverified'` unless `is_phone_verified()`; else `'profile_incomplete'` unless `can_request_rides()`; else `'ok'`. With no caller it returns `'phone_unverified'`. It authorises nothing; `request_seat` re-checks.

### 5.2 `public.request_seat(p_client_request_id uuid, p_ride_id uuid, p_kind text, p_seats int, p_pickup_text text, p_message text) returns jsonb` (AC1, AC8)

Required: `p_client_request_id`, `p_ride_id`, `p_kind`, `p_seats`. Nullable: the two texts (null or empty after trimming means none). Steps in order; the first failure raises and writes nothing.

1. `auth.uid()` null → `not_authenticated`. 2. Required argument null → `missing_argument`.
3. Lock the caller's `accounts` row `for update` (missing → `account_missing`).
4. **Idempotency.** Normalise inputs as step 10 does. If `(rider_id, client_request_id)` exists: equal stored inputs → return `{request_id, status: <stored status>, replayed: true}`; otherwise `request_conflict`.
5. `require_phone_verified()` → `phone_unverified`. 6. `can_request_rides()` false → `profile_incomplete`.
7. Read the ride; unknown → `ride_not_found`. Lock its `ride_series` row `for share`. Caller is the owner → `own_ride`.
8. The ride must be **open for seats** (section 4) and not full → otherwise `ride_unavailable`.
9. `p_kind` in the set → `invalid_kind`; `weekdays` on a `once` series → `invalid_kind`. `p_seats` between 1 and `seats_offered` → `invalid_seats`; `p_seats > seats_left` of the anchor day → `not_enough_seats`.
10. Texts trimmed, empty to null; lengths → `invalid_pickup_text` / `invalid_message`; `taw29_has_contact` on each → `contact_details_not_allowed`.
11. **Limits** (Proposal, in `request_limits()`): at most 20 requests created by the caller in the rolling 24 hours (replays excluded) → `rate_limited`; at most 5 of the caller's requests in displayed state `pending` → `too_many_pending`.
12. A request by the caller on the same anchor ride was `declined` → `already_declined` (Proposal: a declined rider does not re-ask the same day).
13. **One open request per rider and series day.** Open = displayed `pending`, or `accepted` with at least one `held` hold on a day that has not departed. Refused with `already_requested` when:
    - `one_day`: the caller has an open request whose anchor is this ride, or an open `weekdays` request in this series;
    - `weekdays`: the caller has any open request in this series.
14. Insert the request (`pending`). Insert one `request_created` event. Return `{request_id, status: 'pending', replayed: false}`.

No seat is reserved by a request; seats are allocated only on acceptance.

### 5.3 `public.withdraw_request(p_request_id uuid) returns jsonb` (R2 "Cancel request")

`not_authenticated`; `missing_argument`; lock the caller's `accounts` row; lock the request `for update`; not the caller's → `request_not_found`; displayed state not `pending` → `request_not_pending`. Set `withdrawn`, `closed_at`, `closed_by_side = 'rider'`; insert `request_withdrawn`. Returns the request view (section 5.7).

### 5.4 `public.decide_request(p_request_id uuid, p_decision text) returns jsonb` (AC2, AC4, AC8; R4–R6)

1. `not_authenticated`; `missing_argument`; `p_decision` not in `accept`, `decline` → `invalid_decision`.
2. Read the request and its series without locks. Missing, or the caller does not own the series → `request_not_found` (the same response, so a non-owner learns nothing).
3. **Locks, in the order of section 8.1:** the `accounts` rows of the owner and the rider, `for update`, in `user_id` order; the owner's `verification_items (user_id, 'car_owner')` row `for share`; the `ride_series` row `for update`; for `accept`, the target rides `for update` in `(ride_date, id)` order; then the request `for update`.
4. Re-read the request. Displayed state not `pending` → `request_not_pending` (this includes an anchor that has departed or been cancelled).
5. **Decline:** set `declined`, `decided_at`, `closed_at`, `closed_by_side = 'owner'`; insert `request_declined`; return the request view.
6. **Accept:**
   1. The series is `active` and `taw29_ride_offerable(owner, seats_offered)` → otherwise `ride_unavailable`.
   2. The rider is still phone verified (`accounts.phone_verified` under the lock of step 3) → otherwise `requester_unavailable` (Proposal: an admin who revokes a test rider also stops new acceptances; existing holds stay, as TAW-29's revocation semantics).
   3. **Target days:** `one_day` → the anchor ride; `weekdays` → the upcoming days (section 4). No target day → `request_not_pending`.
   4. **All-or-nothing seat check (O2):** every target day has `seats_offered - seats_taken >= request.seats`; for `weekdays`, also `seats + sum(seats of the series' accepted weekdays requests) <= seats_offered`, so that days the job adds later always fit every member (section 8.3). Any failure → `seats_unavailable` with no write; the request stays `pending` (AC4, R6).
   5. Insert one `held` hold per target day and add `request.seats` to each day's `seats_taken`.
   6. Set `accepted`, `decided_at`; insert `request_accepted` with `day_count` = target days; return the request view.

### 5.5 `public.cancel_my_seat(p_request_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (rider; AC3; R9a, R9c, R9d)

1. `not_authenticated`; `missing_argument` for the request, scope or reason; `p_scope` not in `one_day`, `chosen_days`, `all` → `invalid_scope`; `p_reason` not in the rider set → `invalid_reason`.
2. Read the request; not the caller's → `request_not_found`; status not `accepted` → `request_not_cancellable`.
3. Locks: caller's `accounts` row; `ride_series` `for update`; the affected rides `for update` in `(ride_date, id)` order; the request `for update`.
4. **Affected days** = the request's `held` holds whose ride has not departed:
   - `one_day`: `p_ride_ids` has exactly one element, which must be such a day;
   - `chosen_days`: `p_ride_ids` non-empty, distinct, each such a day;
   - `all`: `p_ride_ids` must be null; every such day.
   Any violation, or no affected day → `invalid_days`.
5. For each affected day: hold → `cancelled` with one shared `cancellation_id`/`action_id`; subtract the seats from `seats_taken`; one `cancellations` row (`actor_side = 'rider'`, the request, scope, reason).
6. The request becomes `cancelled` (`closed_at`, `closed_by_side = 'rider'`) when the scope is `all`, or when it is `one_day` kind and no `held` future hold remains. A `weekdays` request cancelled for chosen days stays `accepted`: the rider keeps the other days and receives days added later (O2).
7. Insert `seat_cancelled` (scope, reason, `day_count`). Return the request view.

### 5.6 `public.cancel_my_ride(p_series_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (owner; AC3, AC4; R9b, R9e, R9f)

1. `not_authenticated`; `missing_argument`; `invalid_scope`; `p_reason` not in the owner set → `invalid_reason`.
2. Series missing or not the caller's → `series_not_found`. Series `cancelled` → `series_not_active`.
3. Locks: caller's `accounts` row; `ride_series` `for update`; the affected rides `for update` in `(ride_date, id)` order; the series' requests in states `pending` and `accepted` `for update` in `id` order.
4. **Affected days** = the series' rides with `status = 'scheduled'` and `departs_at > now()`, restricted as in 5.5 step 4 (`all` → every such day). Violations → `invalid_days`.
5. For each affected day: ride → `cancelled` (`cancelled_at`); its `held` holds → `cancelled` with the action's `cancellation_id`; `seats_taken` → 0; one `cancellations` row (`actor_side = 'owner'`, `request_id` null).
6. Pending requests whose **anchor** is an affected day → `expired`, `expired_cause = 'ride_cancelled'`, `closed_by_side = 'owner'`, one `request_expired` event each (AC4).
7. Scope `all`, or a `once` series (its single day): the series → `cancelled` (`cancelled_at`); every remaining `pending` request of the series → `expired` as in step 6; every `accepted` request → `cancelled` (`closed_by_side = 'owner'`).
8. Otherwise, a `one_day` accepted request whose only future hold was cancelled → `cancelled` (`closed_by_side = 'owner'`). `weekdays` members stay `accepted` and keep their other days.
9. Insert `ride_cancelled` (scope, reason, `day_count`). Return `{series_id, cancelled_days, series_status}`.

This replaces the TAW-29 runbook's manual "stop a series" (section 6.3).

### 5.7 Readers (AC5)

All readers: `not_authenticated` without a caller; `profile_incomplete` unless `can_request_rides()`. `anon` cannot execute them. They never return the other party's user id, last name, phone number, plate, community or TAW-4 free text.

**Person view** (the other party): `display` (first name, first letter of the last name and a dot), `initials`, `member_since` (`Mon YYYY`), `phone_verified` (current `accounts.phone_verified`). Ratings are not returned (AC10).

**Request view**: `request_id`, `kind`, `seats`, `state` (displayed, section 4), `expired_cause`, `closed_by_side`, `created_at`, `decided_at`, `closed_at`, `pickup_text`, `message`, `is_rider` (caller is the rider), `is_owner` (caller owns the series), `rider` (person view; returned only to the owner), `ride` (the TAW-29 ride projection of the anchor ride, built by the same expression as `get_ride`, without logging a view), and `days`: for the rider and the owner, the request's holds as `{ride_id, ride_date, departure_time, departs_at, state}` (section 4), ordered by date. The last cancellation's `reason` is included for the side that did not cancel (R8 "plans changed" copy uses it; Proposal).

- **`public.get_my_ride_status(p_ride_id uuid) returns jsonb`** (D2 and R1): `{can_request: <can_request() code, or 'own_ride' / 'ride_unavailable'>, request: <request view of the caller's open or latest request on this ride's series, or null>, pending_count: <only for the owner: pending requests shown on this day, see list_ride_requests>, riders_count: <owner only>}`. Unknown ride → `ride_not_found`.
- **`public.list_ride_requests(p_ride_id uuid) returns jsonb`** (R4, R6; owner only; not the owner or unknown → `ride_not_found`): `{ride: projection, pending: [request view …], riders: [{request_id, rider: person view, seats, kind}]}`. `pending` = displayed-`pending` requests with `kind = 'one_day'` anchored on this ride, plus `kind = 'weekdays'` requests whose anchor date is on or before this ride's date; oldest first. `riders` = `held` holds on this ride.
- **`public.get_seat_request(p_request_id uuid) returns jsonb`** (R2, R5, R7, R8): the request view, for the rider or the series owner; anyone else → `request_not_found`.
- **`public.list_my_trips(p_tab text) returns jsonb`** (R3): `p_tab` in `upcoming`, `past` → `invalid_tab`. Items, each `{type, …}`:
  - `held_day` (rider): one per `held` hold whose day is upcoming (`upcoming`) or departed within the last 30 days (`past`); with the request id, ride projection and day state;
  - `request` (rider, `upcoming` only): requests in displayed state `pending`, and requests that became `declined`, `expired` or `cancelled` within the last 48 hours (Proposal), with state;

## 8. Concurrency, the weekday job and expiry

### 8.1 Lock order (extends TAW-29 8.1)

Every writer of ride or seat data locks, in this order and never in reverse, only the levels it needs:

1. `accounts` rows (`for update`); when two are needed (accept), in `user_id` order;
2. the series owner's `verification_items (user_id, 'car_owner')` row (`for share`), only where the owner's eligibility is the authorisation point (accept, the weekday job);
3. the `ride_series` row (`for update`; `request_seat` takes `for share`);
4. `rides` rows (`for update`, in `(ride_date, id)` order);
5. `seat_requests` rows (`for update`, in `id` order);
6. `seat_holds` and `cancellations` rows (written under 3–5).

| Writer | Levels |
|---|---|
| `publish_ride` (TAW-29) | 1 (owner), 2, creates 3–4 |
| `extend_weekday_series` (changed) | 1 (owner), 2, 3, inserts 4 and 6 |
| `request_seat` | 1 (rider), 3 share, inserts 5 |
| `withdraw_request` | 1 (rider), 5 |
| `decide_request` | 1 (owner and rider), 2, 3, 4 (accept), 5, 6 |
| `cancel_my_seat` | 1 (rider), 3, 4, 5, 6 |
| `cancel_my_ride` | 1 (owner), 3, 4, 5, 6 |
| `expire_seat_requests` | 5 only, `for update skip locked` |
| admin revocation (runbook) | 1 |

Each writer's sequence is increasing in this order, so no two writers wait on each other in a cycle. **The series row (3) is the serialisation point for seats:** every writer that changes `seats_taken` holds it `for update`, so two acceptances, an acceptance and a cancellation, or an acceptance and the weekday job on the same series never interleave. Rows of other series are independent.

### 8.2 Concurrency tests (`supabase/tests/taw30/concurrency.sh`)

Two `psql` sessions on the local stack, paused with advisory locks or `pg_sleep`, as TAW-29's script. Each scenario runs in both orders where order matters, and ends by asserting the seat invariant (section 3.2) for every touched ride and `seats_taken <= seats_offered`:

1. Two owners' sessions accept two different pending requests for the last seat of one day: exactly one `accepted`; the other raises `seats_unavailable` and stays `pending`.
2. A `weekdays` acceptance and a `one_day` acceptance on one of its days, competing for the last seat: exactly one succeeds; no day is overbooked; the weekdays request is all-or-nothing (holds on all target days or none).
3. Acceptance vs the rider's withdrawal of the same request: exactly one of `accepted`/`withdrawn`; the loser raises `request_not_pending`; no hold exists when withdrawn.
4. Acceptance vs `cancel_my_ride(…, 'all')`: either the acceptance commits first and the cancellation cancels its holds, or the cancellation commits first and the acceptance raises `request_not_pending` (the anchor was cancelled, so the request expired) or `ride_unavailable`; no `held` hold on a cancelled ride remains.
5. `extend_weekday_series` vs a member's `cancel_my_seat(…, 'all')`: after both commit, no `held` hold of that request exists on any day.
6. `extend_weekday_series` vs a `weekdays` acceptance: after both commit, the accepted member holds every upcoming day exactly once (the unique key) and no day is overbooked.
7. Two concurrent `request_seat` calls with the same `client_request_id`: one request and one event; one `replayed: false`, one `replayed: true`.
8. A rider's `cancel_my_seat` on day D vs the owner's `cancel_my_ride` of day D: after both commit, D is cancelled, `seats_taken(D) = 0`, and the rider's call either succeeded first or raised `invalid_days`.

### 8.3 `extend_weekday_series` (TAW-29 function, replaced with `create or replace`)

Everything in TAW-29 8.1 stays (advisory lock, per-series locks 1–3, re-read, authorisation point, ±60-minute skip, never recreating a cancelled day). One addition: **after a day is inserted** (row count 1), for each `accepted` `weekdays` request of the series (read under lock 3, in `id` order), insert a `held` hold for the new day and add its seats to `seats_taken`. Because acceptance keeps the members' total within `seats_offered` (5.4 step 6.4) and a new day has no other holds, the check `seats_taken <= seats_offered` cannot fail; if it ever did, the run fails and rolls back (no silent overbooking). Its grants and owner-only execution are unchanged and re-asserted.

### 8.4 Expiry (AC4)

- **Departure:** readers show a pending request as `expired` once its anchor has departed (section 4), and `decide_request` refuses it. `public.expire_seat_requests()` (owner-only) stores it: it selects `pending` requests whose anchor `departs_at <= now()`, `for update skip locked`, sets `expired`, `expired_cause = 'departed'`, `closed_at`, `closed_by_side = 'system'`, and inserts one `request_expired` per request. It returns the count.
- Scheduled by `pg_cron` job `taw30-expire-seat-requests` every 5 minutes (Proposal), created by the migration the way TAW-29 creates its job (unschedule by name, then schedule). Hosted creation is **UNVERIFIED** (V3, owner-run, as TAW-29).
- **Cancellation:** `cancel_my_ride` expires pending requests synchronously (5.6 steps 6–7).

## 12. Privacy and security

- The rider's `pickup_text` and `message` are visible only to the rider and the series owner, and pass the TAW-29 contact filter. The person view discloses no user id, last name, phone, plate, community or free text.
- A non-owner cannot learn whether a request exists (`request_not_found` for missing and foreign alike); a non-owner cannot list a ride's requests (`ride_not_found`).
- Events and cancellations hold no free text.
- Seat allocation is serialised per series and protected by the `seats_taken` check (AC2).
- The app never logs RPC payloads, texts or request ids (a `noLogging` test, TAW-4 pattern).
