## 1. Purpose and boundaries

A phone-verified rider with a completed profile requests seats on one posted ride day. The driver sees the requests and accepts or declines each one. The server allocates seats so that no ride day is ever overbooked. The rider can withdraw a pending request and can cancel a confirmed seat; the driver can cancel one day, chosen days or the whole weekday series; every cancellation records actor, time and reason, and nobody is penalised. Pending requests expire at departure and when their day is cancelled. Both sides see current status in the app (My trips, the ride, the request).

In TAW-30: sections 3–12. Not in TAW-30:

- Push notifications (separate PROPOSED card, Owner; needs a paid Apple Developer account).
- Standing seats on a weekday series: one request for every weekday, rider chosen days and leaving a series (R1 "Every weekday", R9c, R9d; TAW-40). Posting a ride on chosen weekdays (TAW-39).
- Chat, a pickup agreement in chat and in-chat ride offers (TAW-31). Completion, no-shows, ratings, reports and blocks (TAW-32).
- The phone OTP flow and the TAW-26 verification screens (TAW-5).
- Editing a request after it is sent; waitlists.
- Account deletion for users who have made requests (a later card; section 3.5).
- Android (D10) and Arabic/RTL.

## 3. Data model (one schema migration)

New tables live in `public`, have RLS enabled and **no policies**, and **no privilege for any API role** (`anon`, `authenticated`, `service_role`); section 14. Every read and write goes through the `security definer` functions of section 5. No column, argument or screen field holds a price, fare, cost, amount or currency (AC6).

### 3.1 `seat_requests` (one ride day each)

| Column | Constraint |
|---|---|
| `id` | `uuid` pk default `gen_random_uuid()` |
| `rider_id` | `uuid not null references accounts(user_id) on delete no action` (3.5) |
| `client_request_id` | `uuid not null`; `unique (rider_id, client_request_id)` |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `ride_id` | `uuid not null references rides on delete cascade`: the requested day |
| `seats` | `smallint not null check between 1 and 8` |
| `pickup_text` | `text`, null or trimmed 1–80: the rider's pickup suggestion; null means the driver's pickup note |
| `message` | `text`, null or trimmed 1–200 |
| `status` | `text not null default 'pending' check in ('pending','accepted','declined','withdrawn','expired','cancelled')` |
| `expired_cause` | `text check in ('departed','ride_cancelled')`; not null exactly when `status = 'expired'` |
| `decided_at` | `timestamptz`; not null exactly when `status in ('accepted','declined','cancelled')` |
| `closed_at` | `timestamptz`; not null exactly when `status in ('declined','withdrawn','expired','cancelled')` |
| `closed_by_side` | `text check in ('rider','owner','system')`; not null exactly when `closed_at` is not null |
| `created_at` | `timestamptz not null` (the decision time, 5.0) |

Table checks state each "exactly when" pairing. Input columns never change after insert. Status moves only forward: `pending → accepted | declined | withdrawn | expired`, `accepted → cancelled`; a test asserts no function performs another transition. Every update that changes `status` sets every column the target status requires in the same statement.

Indexes: `(series_id, status)`, `(ride_id) where status = 'pending'`, `(rider_id, created_at)`, and the **one-open-request-per-day backstop** unique index `(rider_id, ride_id) where status in ('pending','accepted')` (O2). A rider may hold such rows on several rides of one series at once.

### 3.2 `seat_holds` (the seat of an accepted request)

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `request_id` | `uuid not null unique references seat_requests on delete cascade` |
| `ride_id` | `uuid not null references rides on delete cascade` (equal to the request's) |
| `seats` | `smallint not null check between 1 and 8` (copied from the request) |
| `status` | `text not null default 'held' check in ('held','cancelled')` |

Index `(ride_id) where status = 'held'`. A cancelled hold sets `status`, `cancelled_at` and `cancellation_id` in one statement.

**Seat invariant (AC2).** For every ride, `rides.seats_taken = coalesce(sum(seats) of its 'held' holds, 0)`. Only the functions of section 5 change holds or `seats_taken`, always together, under the series lock (8.1); `extend_weekday_series` inserts rides with `seats_taken = 0` and no holds. No supported path deletes a hold of a surviving ride (3.5). The TAW-29 check `seats_taken between 0 and seats_offered` is the last line of defence. pgTAP asserts the invariant for every ride after every scenario (section 13).

### 3.5 Account deletion contract (pilot; F18, F24)

Deleting a user who owns rides or has TAW-30 rows is **not a supported operation in TAW-30** (Proposal; a later card builds it). The rider and actor references use `on delete no action` (checked at the end of the deleting statement, after its cascades), so:

- deleting a user who made a request, or who cancelled as a rider, fails with a foreign-key violation and changes nothing; such test accounts are kept (6.3);
- deleting an owner whose rows are only on their own series cascades them away with the series, so no surviving ride is affected. This is a **maintenance-only** action, run with no app traffic (local test fixtures and resets) inside a transaction that first takes `pg_advisory_xact_lock(hashtext('taw30-expire'))`, which pauses `expire_seat_requests` for that transaction (8.4), because its cascade takes locks outside the order of 8.1; it is not in the writer inventory and is not claimed deadlock-free;
- no supported path deletes a `seat_holds` row of a surviving ride, so the seat invariant (3.2) holds without a trigger.

Test-fixture cleanup (integration suites) follows the same rule (F46): in one owner-role transaction holding the expiry advisory lock, it deletes the fixture **owners** first (their series cascade away with every request, hold and cancellation on them), then the fixture riders, whose TAW-30 rows were all on fixture series and are already gone. pgTAP covers both deletion cases (13 item 11).

### 3.6 No future cancellation time (F67, F72)

The TAW-29 checks allow `status = 'cancelled'` with a `cancelled_at` in the future, a state in which a request would stay effectively `pending` (withdrawable, declinable, skipped by the sweep) on a cancelled day. TAW-30 makes that state impossible instead of defining behaviour for it:

- The migration first asserts that no `rides` or `ride_series` row has `cancelled_at > clock_timestamp()` (it raises `future_cancelled_at_present` and aborts otherwise; none exist on main, Expected, plan step).
- A trigger `taw30_no_future_cancel` (`before insert or update of status, cancelled_at`, `for each row`, on `rides` and on `ride_series`, function `security definer`, `set search_path = ''`, owner-only) raises `future_cancelled_at` when `new.cancelled_at > clock_timestamp()`. Every writer sets `cancelled_at` to its own `v_now`, taken before the write, so no supported path is affected; the trigger rejects only manual or out-of-band writes.
- Consequence: a row's `status = 'cancelled'` always has `cancelled_at <=` the time of any later reader or writer. A reader's snapshot sees the row only after the cancelling transaction committed, i.e. after its `cancelled_at`, and a reader's `v_at` is taken after its snapshot; a writer reloads the row after its locks and takes `v_now` afterwards. So a request on a cancelled day is effectively `expired` in every reader, writer and the sweep from the same moment, with the cause and `closed_at` of section 4's **first-trigger rule** (the earlier of departure and cancellation; `ride_cancelled` on a tie), which depends only on stored timestamps and is therefore deterministic (F87).

pgTAP (13 item 5): an owner-role update setting a future `cancelled_at` on a ride and on a series raises `future_cancelled_at`; a past or current one succeeds; for a cancelled day and a stopped series fixture (both written with past timestamps), `withdraw_request` and decline raise `request_not_pending`, accept raises `request_not_pending`, and `expire_seat_requests` stores exactly the effective values of section 4. A further fixture (F87): a pending request whose day departed, on a series stopped **after** that departure, is effectively `expired` with `departed` and `closed_at` = the departure before the sweep, and is stored with the same cause and timestamp by the sweep. Beside it, the **tie fixture (F94)**: the same day with the series stopped at exactly its departure (owner-role write, `ride_series.cancelled_at = rides.departs_at`, both past): the pending request is effectively `expired` with `ride_cancelled` and `closed_at` = the departure, and is stored so by the sweep; the day's `day_state` is `departed`; an accepted request on it stays `accepted` with its hold `held` and hold state `departed`; the rider's request view carries `state = 'expired'`, `expired_cause = 'ride_cancelled'` and `day_state = 'departed'`, the inputs of R8's departure copy (11.2 item 11). A mutation that drops the trigger fails the future-timestamp tests.

## 4. Time and states

- **Decision time.** Every writer (client writer function, `extend_weekday_series` before each ride insert, `expire_seat_requests` per batch) captures `v_now := clock_timestamp()` **after** acquiring the locks for the rows it is about to change, and uses `v_now` — never `now()` — for departure comparisons and stored times. Readers use one `clock_timestamp()` per call.
- A ride day is **open for seats** at time t when: `rides.status = 'scheduled'` (so `cancelled_at` is null), the series has `status = 'active'`, `departs_at > t`, and `taw29_ride_offerable(owner, seats_offered)`. A ride whose `status` is `cancelled` is never open for seats (F67); its `cancelled_at` is never in the future (3.6).
- **Cancellable ride day (F65):** one predicate used by every reader that lists cancellable days or flags a seat as cancellable (`cancellable` in the request view, `cancellable_days` in `list_ride_requests` and `list_my_series`) and by both cancel functions: the ride's `status = 'scheduled'`, its series has `status = 'active'`, and `departs_at > t`. A day whose series is cancelled is therefore never cancellable, even if its ride row is still `scheduled` (a recovery state, produced only outside the functions of section 5).
- **One timestamp and one snapshot per call (F39).** A writer passes its `v_now`, and a reader its single call time `v_at := clock_timestamp()`, into every nested state and view computation (`taw30_request_state`, `taw30_request_view`, the hold state, `day_state`, and the copied ride projection, whose departure test uses that time instead of `now()`), so every part of one response describes the same instant. Readers **and every function they call that reads tables** (`taw30_request_state`, `taw30_open_at`, `taw30_request_view`, `taw30_person_view`, `taw30_ride_projection`, and the inherited `taw29_ride_offerable`, `taw29_post_eligible`, `can_request_rides`, `is_phone_verified`, already `stable`) are declared `stable`, so the whole read chain sees the snapshot taken at the start of the calling query; a test reads `pg_proc.provolatile` for each. A concurrent cancellation is therefore either wholly visible or wholly invisible in a response.
- **Effective request state** — one function, `taw30_request_state(p_request, p_at)`, used by every reader and writer (F6). For stored `pending`: let `t_dep` = the ride's `departs_at` if `<= p_at`; let `t_can` = the earliest of the ride's `cancelled_at` and the series' `cancelled_at` that is `<= p_at`. If neither → `pending`. Else → `expired`, with the **earlier** trigger's values: `departed` (`closed_by_side = 'system'`, `closed_at = t_dep`) or `ride_cancelled` (`closed_by_side = 'owner'`, `closed_at = t_can`); on a tie, `ride_cancelled`. The only tie the functions of section 5 can produce is a series stop whose `v_now` equals a day's `departs_at`: that day is not cancellable (5.6 step 5), keeps its holds and has `day_state` `departed`, while its pending requests expire with `ride_cancelled`; R8 shows that combination as a departure, not as a cancelled day (11.2 item 11; F94). For any other stored status: the stored values. Writers that store an expiry (5.6, 8.4) store exactly the function's result, so the outcome is the same whichever writer runs first. (A cancelled ride or series never has a future `cancelled_at` (3.6), so a request on a cancelled day is `expired` for every caller from the moment the cancellation is visible; F72.)
- **Hold state** (rider and owner), in precedence: `cancelled` (hold cancelled; `by` = its cancellation's `actor_side`) > `departed` (the day's `day_state` is `departed`) > `unavailable` (the hold is still `held` and the day's `day_state` is `withdrawn` — the driver became not offerable, for example a revoked phone or a rejected car — or `cancelled`, which only the recovery state of a series stopped outside the functions can produce) > `confirmed`. A hold that is `unavailable` because of `withdrawn` is still cancellable by the rider (its day is a cancellable ride day); one on a stopped series is not (4, 5.5).
- **Day state (F28, F60):** `day_state` of a ride day at time t, used by every TAW-30 view and by D2 and the shared view for every viewer (7; F58) instead of the TAW-29 projection's `state` (which reports `cancelled` for every day of a stopped series): `cancelled` when the ride row is cancelled, or when the series is cancelled and the day's `departs_at` is **strictly later than the series' `cancelled_at`** (so a day that was still to run when the series stopped stays `cancelled` after its scheduled time passes); else `departed` when `departs_at <= t` (the tie `departs_at = series.cancelled_at` is `departed`, matching 5.6, where a day departing at the stop's `v_now` is not cancellable); else `withdrawn` when not offerable; else `full` or `available`. A `cancelled` day is never cancellable and never Next. The TAW-29 projection state stays as it is inside the TAW-29 readers (`list_rides`, `get_ride`, `resolve_shared_ride`).

## 5. Server functions

### 5.0 Common rules

- All functions are `security definer`, `set search_path = ''`, schema-qualified, raise `raise exception '<code>'`, and check set membership null-safely.
- **Client functions** (those listed in section 14 with `authenticated` `EXECUTE`): first `not_authenticated` (no `auth.uid()`), except `can_request()`, which returns `'phone_unverified'` without a caller; then `missing_argument` (any required argument null). They take **no argument that names a user** and act only for `auth.uid()`.
- **Owner-only functions** (helpers and the job functions): not executable by any API role; they take explicit ids, never read `auth.uid()`, and validate their arguments (`missing_argument`).
- **Isolation contract (F54).** Every writer (client writer functions and the job functions) begins with `if current_setting('transaction_isolation') <> 'read committed' then raise exception 'unsupported_isolation'`. Under read committed, each statement after a lock wait sees rows committed before it, which the seat protocol relies on (fresh reads of the ride and series after the series lock). The app's API path runs at the database default, read committed (Expected; the integration tests of 13 call every client writer through it). The isolation a `pg_cron` run actually gets is **UNVERIFIED (V10)**: a run under another level would refuse every time with `unsupported_isolation`, so the jobs are relied on only after a run started by the scheduler itself has succeeded and done its work (8.4, 16; F63, F70).
- Locks follow section 8.1; after the locks, `v_now` (section 4).
- **State is read under the locks (F57).** Any pre-lock read only locates rows and checks ownership; every status, seat and time check after the locks uses the rows **re-read under those locks** (request status, hold status, ride status, `cancelled_at` and `seats_taken`, series status). A call that finds the target already closed refuses with its code and writes nothing (no second cancellation row or event).
- A refusal writes nothing.

### 5.1 `public.can_request() returns text` (stable)

`'phone_unverified'` unless `is_phone_verified()`; else `'profile_incomplete'` unless `can_request_rides()`; else `'ok'`. Authorises nothing.

### 5.2 `public.request_seat(p_client_request_id uuid, p_ride_id uuid, p_seats int, p_pickup_text text, p_message text) returns jsonb` (AC1, AC8)

Required: `p_client_request_id`, `p_ride_id`, `p_seats`. Texts: null or empty after trimming means none.

1. `not_authenticated`; `missing_argument`.
2. **Gate pre-check, before any ride lookup:** `require_phone_verified()` → `phone_unverified`; `can_request_rides()` false → `profile_incomplete`. It reads without locks, so a caller who fails it learns nothing about the ride id (F34).
3. Read the ride only to find its series and the series owner (unknown → `ride_not_found`). Then, in the order of 8.1: lock the caller's and the owner's `accounts` rows `for share` in `user_id` order (one row when they are the same user; the caller's missing → `account_missing`; only the first row may wait, the second is `nowait` and a locked row → `try_again`, F92); **re-run the gate under the caller's lock** (same codes; so a revoked rider gets no replay, F15, and the gate holds until commit); take the **relation guard** (8.1 level 2; not granted → `try_again`, F85); lock the owner's car `verification_items` row, `vehicles` row and its `car_types` row `for share nowait` (those that exist; F61; a locked row → `try_again`, F85); lock the `ride_series` `for share`; lock the caller's own requests on this ride with stored status `pending` or `accepted` `for no key update` (level 5, `id` order; F104), so neither the sweep (`skip locked`) nor a withdrawal or decision can change them until this call commits; take the caller's rider advisory lock (level 6); then `v_now`; then, as a **separate statement**, `perform public.taw30_test_pause()` (an owner-only function whose production body is empty; it exists only so the concurrency script can pause a send between `v_now` and the following statements, each of which takes a fresh read-committed snapshot; F104, F107); and **reload the ride** (status, `cancelled_at`, `departs_at`, `seats_taken`) and the series under these locks; every later step uses the reloaded rows (F53).
4. **Idempotency.** Inputs normalised as step 6. If `(rider_id, client_request_id)` exists: when its `ride_id`, `seats`, `pickup_text` and `message` are all `is not distinct from` the normalised inputs → `{request_id, state: <effective state>, replayed: true}`; otherwise `request_conflict` (including the same key used on another ride).
5. Caller owns the series → `own_ride`. The ride must be open for seats at `v_now` and not full → `ride_unavailable`. **One decision point (F61):** this test — departure, ride and series status and `taw29_ride_offerable` — runs once, after every lock of step 3 and after `v_now`. Every input of offerability is locked: the owner's `accounts` row (`phone_verified`; also guards `profiles.role`, whose writer `set_role` locks `accounts` first), the car `verification_items` row (`review_item`, `submit_car`), the `vehicles` row and its `car_types` row (`service_role` writes to `car_types`), so none of them can commit a change between `v_now` and this read.
6. `p_seats` (non-null here; a null `p_seats` is `missing_argument` at step 1) outside the inclusive range 1 to `seats_offered` → `invalid_seats`; otherwise `p_seats > seats_offered - seats_taken` → `not_enough_seats` (F110, F112). Boundaries tested (13 item 2): null → `missing_argument`; 0 and `seats_offered + 1` → `invalid_seats`; on a partly taken ride (`0 < seats_left < seats_offered`), 1 and `seats_left` succeed and `seats_left + 1` → `not_enough_seats`; a full ride (`seats_left = 0`) is a separate probe and gives `ride_unavailable` at step 5. Texts trimmed, empty to null; lengths → `invalid_pickup_text` / `invalid_message`; `taw29_has_contact` → `contact_details_not_allowed`.
7. **Limits** (Proposal, `request_limits()`; F26): let n = the caller's requests with `created_at > v_now - interval '24 hours'` (replays create none). n ≥ 20 → `rate_limited` (the 21st is refused). 5 or more of the caller's requests that were **pending at `v_now`** (open at `v_now` by the rule of step 9 and not accepted at `v_now`: a request was accepted at `v_now` when its stored status is `accepted` **or `cancelled`** and its preserved `decided_at <= v_now`, since a cancelled seat keeps its `decided_at`; F107) → `too_many_pending`. Both counts run under the rider advisory lock, so concurrent sends cannot both pass a boundary.
8. A request by the caller on this ride was `declined` → `already_declined` (Proposal).
9. **One open request per day (O2, F104):** the caller has a request on **this ride** that is **open at `v_now`** → `already_requested`. A request r is open at time t (`taw30_open_at(r, t)`, owner-only, `stable`) when `r.created_at <= t` and r was not yet closed at t: its stored status is `pending` or `accepted` and `taw30_request_state(r, t)` is not `expired`, **or** its stored status is closed (`declined`, `withdrawn`, `expired`, `cancelled`) with stored `closed_at > t`. Together with the level-5 locks of step 3 (which keep this ride's open requests of the caller unchanged from before `v_now` until commit), the decision "the day is open and the rider has no open request" holds at the single instant `v_now`; the timestamp rule also covers the caller's requests on other rides used by step 7, which are not locked. Requests on other days of the same series do not count. The check runs under the rider advisory lock (no other `request_seat` by the caller can interleave); the unique index of 3.1 is the backstop.
10. Insert the request (`pending`, `created_at = v_now`); insert `request_created`. Return `{request_id, state: 'pending', replayed: false}`.

A request reserves no seat; seats are allocated only on acceptance.

### 5.3 `public.withdraw_request(p_request_id uuid) returns jsonb` (R2 "Cancel request")

Read the request without locks; missing or not the caller's → `request_not_found` before any lock on its rows (F42). Then lock the caller's `accounts` `for share`, take the relation guard (8.1 level 2; not granted → `try_again`, F85), lock the request's `ride_series` `for share` and the request (level 5); `v_now`; re-check ownership (immutable) and effective state: not `pending` → `request_not_pending`. Set `withdrawn`, `closed_at = v_now`, `closed_by_side = 'rider'`; insert `request_withdrawn`. Return the request view (5.7).

### 5.4 `public.decide_request(p_request_id uuid, p_decision text) returns jsonb` (AC2, AC4; R4–R6)

1. `not_authenticated`; `missing_argument`; `p_decision` not in `accept`, `decline` → `invalid_decision`.
2. Read the request and series without locks. Missing, or the caller does not own the series → `request_not_found` (same response).
3. Locks (8.1): the owner's and rider's `accounts` `for share` in `user_id` order (only the first may wait; the second is `nowait`, a locked row → `try_again`, F92); the relation guard (not granted → `try_again`, F85); the owner's car `verification_items`, `vehicles` and `car_types` rows `for share nowait` (F61; a locked row → `try_again`, F85); `ride_series`; the request's ride; the request. Then `v_now`, and every later step uses the rows re-read under these locks.
4. Effective state not `pending` → `request_not_pending`.
5. **Decline:** `declined`, `decided_at = closed_at = v_now`, `closed_by_side = 'owner'`; insert `request_declined`; return `{result: 'declined', request: <view at v_now>}`.
6. **Accept:**
   1. The ride is **open for seats** at `v_now` (4: ride `status = 'scheduled'`, series `active`, `departs_at > v_now`, offerable) → else `ride_unavailable`. This is checked on the locked rows before any seat arithmetic (F67); with 3.6, a cancelled ride already fails step 4.
   2. Rider `accounts.phone_verified` (under the share lock) → else `requester_unavailable` (Proposal; existing holds of a revoked rider stay, as TAW-29's revocation semantics).
   3. **Seat check, no writes on failure:** `seats_offered - seats_taken >= seats`. On failure return, **without raising**, `{result: 'seats_unavailable', request: <view at v_now>, seats_left}`. Nothing is written; the request stays `pending` (AC4, R6).
   4. Insert one `held` hold (`created_at = v_now`); add `seats` to the ride's `seats_taken`.
   5. `accepted`, `decided_at = v_now`; insert `request_accepted`; return `{result: 'accepted', request: <view at v_now>}`.

### 5.5 `public.cancel_my_seat(p_request_id uuid, p_reason text) returns jsonb` (rider; AC3; R9a)

1. `not_authenticated`; `missing_argument`; reason not in the rider set → `invalid_reason`.
2. Read the request; missing or not the caller's → `request_not_found` before any lock on its rows (F42).
3. Locks: caller's `accounts` `for share`; the relation guard (8.1 level 2; not granted → `try_again`, F85); `ride_series`; the request's ride; the request. `v_now`.
4. **One refusal for every non-cancellable seat (F65):** the request (re-read) is not `accepted`, or its hold is not `held`, or its ride is not a **cancellable ride day** (4) at `v_now` → `request_not_cancellable`, nothing written. This covers a departed day (the hold stays as history), a day the owner cancelled, and the recovery state of a day still `scheduled` on a cancelled series (its hold stays `held` and shows as `unavailable`).
5. One `action_id`. Insert the day's `cancellations` row (`scope = 'one_day'`, `request_id`, `created_at = v_now`); the hold → `cancelled`, `cancelled_at = v_now`, `cancellation_id` = that row; `seats_taken -= seats`; the request → `cancelled` (`closed_at = v_now`, `closed_by_side = 'rider'`; `decided_at` kept).
6. Insert `seat_cancelled`. Return the request view.

### 5.6 `public.cancel_my_ride(p_series_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (owner; AC3, AC4; R9b, R9e, R9f)

1. `not_authenticated`; `missing_argument` (series, scope, reason); `p_scope` not in `one_day`, `chosen_days`, `all` → `invalid_scope`; reason not in the owner set → `invalid_reason`.
2. Series missing or not the caller's → `series_not_found`.
3. Locks: caller's `accounts` `for share`; `ride_series`; all the series' `scheduled` rides in `(ride_date, id)` order; the series' requests with status `pending` or `accepted` in `id` order. `v_now`.
4. **Series status first (F65):** the series (re-read under the lock) is `cancelled` → `series_not_active`, before any day validation, whatever `p_scope` and `p_ride_ids` say.
5. **Cancellable days** = the series' rides that are cancellable ride days (4) at `v_now`. **Affected days**:
   - `one_day`: `p_ride_ids` has exactly one non-null element, a cancellable day;
   - `chosen_days`: `p_ride_ids` non-empty, no nulls, no duplicates, each cancellable (weekdays series only);
   - `all`: `p_ride_ids` null; all cancellable days.
   A day departing exactly at `v_now` is not cancellable: a stop at that instant leaves it `departed` with its holds `held` and its accepted requests unchanged, while its pending requests expire with `ride_cancelled` (the tie of section 4; R8 shows them as a departure, 11.2 item 11; F94).
   Any violation → `invalid_days`, nothing changed. A `once` series accepts only `all`, and only with its day cancellable (a departed once ride → `invalid_days`; F28). Zero affected days is allowed only for `all` on a `weekdays` series (stopping a series whose generated days have all departed).
6. One `action_id`. Per affected day: its `cancellations` row (`request_id` null, `created_at = v_now`); ride → `cancelled`, `cancelled_at = v_now`; its `held` holds → `cancelled`, `cancelled_at = v_now`, `cancellation_id` = that row (F29); `seats_taken = 0`. With zero affected days, one row with `ride_id` null.
7. Scope `all`: the series → `cancelled`, `cancelled_at = v_now`.
8. For each locked `pending` request: compute `taw30_request_state(request, v_now)` after steps 6–7; when it is `expired`, store exactly that result and insert `request_expired`.
9. Each locked `accepted` request whose day was affected → `cancelled` (`closed_at = v_now`, `closed_by_side = 'owner'`). Accepted requests on days that already departed are **not** changed (their history stays, F28).
10. Insert `ride_cancelled` (`scope`, `reason`, `day_count`; `ride_id` = first affected day or null). Return `{series_id, series_status, cancelled_ride_ids}`.

- **`public.get_my_ride_status(p_ride_id uuid) returns jsonb`** (D2, the shared view, R1). Unknown → `ride_not_found`. Returns `{ride, is_owner, day_state, seats_left, can_request, requests, owner}` (F13, F68):
  - `ride`: the ride projection at call time (so R1 has the summary, `repeat` and `pickup_note` on direct entry without navigation state; F68);
  - `is_owner`: the caller owns the series;
  - `day_state` (4) for this day, and `seats_left` (`seats_offered - seats_taken`);
  - `can_request` (`'own_ride'` for the owner): the `can_request()` code if not `'ok'`; else `'ride_unavailable'` if, at call time, the ride is **not open for seats or `seats_left <= 0`** (F73; so a full ride never returns `'ok'` and R1 never renders a stepper with an upper bound below 1); else `'already_declined'` if 5.2 step 8 would refuse; else `'already_requested'` if 5.2 step 9 would refuse; else `'ok'` (F41).   Seat bounds and eligibility on R1 come only from this response's `seats_left`, `day_state` and `can_request`; the projection's `state` and seat fields are not read (F58).
- **`public.list_ride_requests(p_ride_id uuid) returns jsonb`** (R4, R6, R9b/e/f; owner only; else `ride_not_found`): `{ride, day_state, series: {series_id, repeat, status}, pending: [request view], recent: [...], riders: [{request_id, rider, seats, hold_state, by, cancelled_at}], cancellable_days: [{ride_id, ride_date, departure_time, seats_taken}]}`. `pending` = effective-`pending` requests on this ride, only while this day is `scheduled` and not departed (else empty); oldest first, with Accept/Decline. `recent` = requests on this ride that were declined, withdrawn, expired or cancelled within the last 48 hours (Proposal), each `{request_id, rider, seats, state, closed_by_side, closed_at}`, shown without actions. `riders` = every hold on this ride, `held` first, then `cancelled` ones with who cancelled and when. `cancellable_days` = 5.6 step 5 at call time.

Returns `{request: <rider request view at call time>}` when found, else `{request: null}`; another user's key gives the same `{request: null}` as an unknown key. Returns `{series: [...]}`: every series the caller owns with `repeat = 'weekdays'` and `status = 'active'`, whatever the state of its days (including none in the future, all departed, or the owner no longer eligible), ordered by `(created_at, id)`. Each item (exact keys): `{series_id, repeat, status, from_name, to_name, direction, departure_time, first_date, seats_offered, riders_upcoming, next_ride_id, cancellable_days: [{ride_id, ride_date, departure_time, seats_taken}]}`; `riders_upcoming` = the number of `held` holds on its cancellable days; `next_ride_id` = its earliest ride with `day_state` `available` or `full`, or null; `cancellable_days` = 5.6 step 5 at call time (may be empty).
- **`public.list_my_trips(p_tab text, p_after_sort_at timestamptz default null, p_after_key text default null, p_limit int default 50) returns jsonb`** (R3; F52, F69). `p_tab` in `upcoming`, `past` → else `invalid_tab`; the two cursor arguments both null or both set → else `invalid_cursor`; `p_limit` 1–50 → else `invalid_limit`. The app loads further pages as the list scrolls. Item shapes (exact keys):
  - `trip` (rider): `{type, item_key, sort_at, request: <request view>}` → opens the request detail;
  - `drive` (owner): `{type, item_key, sort_at, ride: <projection>, series_id, day_state, seats_taken, seats_offered, pending_count}` → opens R4 for that ride; `day_state` per section 4;

  - `past` contains a `trip` per request of the caller, **in any effective state**, whose day departed (`departs_at <= ` call time) within the last 30 days (`departs_at > ` call time `- interval '30 days'`), and a `drive` per own ride day, in any ride state, with the same departure filter; no confirmation or rating (AC10). So a request that was still pending at departure moves from Upcoming (`pending`) to Past (`expired`, `departed`) on the first refresh after departure, and every closed outcome stays reachable for 30 days after its day (F74). The app shows `day_state`, the request `state` and the hold state, never the embedded projection's `state`.

## 6. Authorisation, manual verification and the launch gate (AC1, AC9)

### 6.1 Server-side rule

Requesting is possible only through `request_seat`, which calls `require_phone_verified()` and `can_request_rides()` before reading the caller's prior requests and before any write. No API role has a privilege on the new tables, and `service_role` no longer reads `pilot_events` (section 14). Identity: the API verifies the JWT signature, so a token signed with another key is rejected, and no client function takes a user argument, so a valid token acts only for its own subject. `authenticated` has no `UPDATE` on `accounts` or any of its columns (accounts migration; re-asserted in 13), so a user cannot set `phone_verified`.

The store is cleared on sign-out and on any change of the signed-in user, and a response that arrives for an attempt of a user who is no longer signed in is discarded, so one user's attempt (and its pickup text and message) is never resent or shown under another user's session. **Dispatch is bound to the attempt's identity (F45):** when an attempt is created, the requests API records the session's user id and access token; every send of that attempt, and its lookup `get_request_by_client_id`, goes through a per-call PostgREST client whose `Authorization` header is that token (`createClient(url, anonKey, { global: { headers: { Authorization: 'Bearer ' + token } }, auth: { persistSession: false, autoRefreshToken: false } })`), never through the shared client. If the token has expired and the current session's user id differs, the attempt is discarded unsent; if it is the same user, the fresh token is recorded and used. Jest tests an account switch while a send is paused. After a network error or unknown result, the inputs are locked ("Checking your request…") and the app re-sends the same key and payload; re-entering R1 for that ride during the app session resumes the same attempt, lookup first (6.2). A gate error (`phone_unverified`, `profile_incomplete`) is raised **before** the key is looked up and proves nothing about an earlier send of the same key, so it does **not** settle the attempt: the app reconciles with `get_request_by_client_id(<key>)`; found → settled as that request; not found → the gate's screen, and the attempt stays saved (6.2). Only the errors raised **after** the key lookup (5.2 steps 5–9: `own_ride`, `ride_unavailable`, `invalid_seats`, `not_enough_seats`, `invalid_pickup_text`, `invalid_message`, `contact_details_not_allowed`, `rate_limited`, `too_many_pending`, `already_declined`, `already_requested`) also settle it, because the server checked this key and found no request with it. Errors raised before the lookup (`not_authenticated`, `missing_argument`, `account_missing`, the gate errors, `ride_not_found`, `try_again`, `unsupported_isolation`) and transport or authentication failures (for example HTTP 401) do **not** settle it; the app reconciles as above (after a 401 once a valid session for the same user exists). Only after settlement may the user change inputs, which starts a new key. **Residual (Owner-accepted, 2026-11-21, "Accept the residual"):** a delayed original can still reach the server after its attempt was settled by an error (or after an app restart, since the store is in memory) and create the request the user originally sent. That request is valid (it passed every rule of 5.2 at its own decision time), appears in Trips and D2, and the rider can withdraw it; the one-open-request-per-day rule (5.2 step 9) prevents a second open request on the same day, and the per-rider limits bound the rest. No seat, event or state can be duplicated by it. Decisions, withdrawals and cancellations are forward-only: a retry after a lost response gets `request_not_pending`, `request_not_cancellable`, `invalid_days` or `series_not_active`, never a second effect or event; the app then refetches and shows the current state with the message of 11.4.

## 8. Concurrency, the weekday job and expiry

### 8.1 Lock order (replaces TAW-29 8.1 for all ride and seat writers)

**Levels**, acquired by every writer in increasing order, each only as needed:

1. `accounts` rows. TAW-30 writers take them **only `for share`**, several in `user_id` order, all before any level-2+ lock. **A writer may wait only for its first `accounts` row (F92)**; every later one is `for share nowait` in a client writer (a locked row → `try_again`, nothing written; for `request_seat` before the key lookup, so the attempt stays unsettled, 7) and `for share skip locked` in the job (that owner's series is skipped in this run, 8.3). A `service_role` transaction that holds one account `for update` through a TAW-4 definer call and then asks for another (2, F92) therefore never waits for a TAW-30 writer that is itself waiting for an account.
2. **Relation guard (F85)**, first step of level 2, taken right after level 1 by every writer that reads a guarded relation after level 1 (`request_seat`, `withdraw_request`, `decide_request`, `cancel_my_seat`: offerability and the request view; the job: offerability): one statement `lock table public.car_types, public.car_brands, public.car_models, public.places, public.routes in row exclusive mode nowait` — the relations read by TAW-30 writers on which an API role can take a table lock stronger than `ACCESS SHARE` (2, Fact). `NOWAIT` on a locking read applies to rows only; the table lock it needs (`ROW SHARE`), and the `ACCESS SHARE` locks of plain reads and index opens, would still wait. `ROW EXCLUSIVE` is the weakest mode that conflicts with every mode that can block those (`SHARE`, taken on the table by `reindex` before it locks an index `ACCESS EXCLUSIVE`; `EXCLUSIVE` and `ACCESS EXCLUSIVE`, taken by `lock table`, and `ACCESS EXCLUSIVE` by `truncate` and `cluster`), and it conflicts with nothing ordinary traffic takes (reads, `for share`, `insert`/`update`/`delete`, `vacuum`, `analyze`). Not granted at once → client writers raise `try_again` (SQLSTATE 55P03 from the guard, as from a `nowait` row, maps to `try_again`), holding no level-2 row and writing nothing; the job returns 0 for the run, having inserted nothing. Once granted, it is held to commit; no other transaction can then take `SHARE` or a stronger mode on these relations, so `lock table`, `truncate`, `cluster` and `reindex` inside a transaction cannot block the writer's later reads, row locks or index opens of them. `cancel_my_ride` and `expire_seat_requests` read no guarded relation (no offerability, no request view) and take no guard; 8.2 scenario 28 shows that they complete while the relations are locked.
   Offerability inputs of the series owner: the car `verification_items` row, then the `vehicles` row, then its `car_types` row, all `for share` (F61). Client writers that read offerability as an authorisation point (`request_seat`, `decide_request`) take one owner's three rows `for share nowait` and **never wait** at this level (F85): if any of the three is locked `for update` by another transaction (a `review_item`, a car change, a catalogue update — possibly the same `service_role` transaction doing several of these), the call raises `try_again` and writes nothing. The app shows "Something changed. Try again." and refetches; for `request_seat` the error is raised before the key lookup, so it does not settle the attempt (7), and the retry uses the same key. The job takes several owners' rows and **never waits** at this level: it locks them `for share skip locked` (8.3; F66).
3. `ride_series` rows (`for no key update`; `request_seat` and `withdraw_request` take `for share`). The job takes them `for no key update skip locked` and never waits at this level either (8.3; F66).
4. `rides` rows (`for no key update`, `(ride_date, id)` order).
5. `seat_requests` rows (`for no key update`, `id` order; queries lock with `for no key update of <the seat_requests alias>` so no joined table is locked).
6. The rider advisory lock `pg_advisory_xact_lock(hashtext('taw30-rider'), hashtext(<rider uuid>::text))` (`request_seat` only).
7. Inserts and updates of `seat_holds`, `cancellations`, `pilot_events`, `seat_requests`, `rides`, `ride_series` on rows already locked at levels 3–5 or new rows. Foreign-key checks on these inserts take `for key share` on referenced `accounts`, `ride_series`, `rides`, `seat_requests` and `cancellations` rows.

**No late account references (F80).** A foreign-key check on an inserted row takes `for key share` on the referenced `accounts` row, which waits for any transaction holding that row `for update` (for example TAW-4 `submit_car`, which then waits for a catalogue row). So every row a TAW-30 writer inserts that references `accounts` references **only accounts the writer locked at level 1**: `request_seat` (request `rider_id`, `request_created` `user_id`: the caller), `withdraw_request` and `cancel_my_seat` (the caller), `decide_request` (`request_accepted`/`request_declined` `user_id`: the owner, the caller), `cancel_my_ride` (`cancellations.actor_id` and `ride_cancelled` `user_id`: the owner, the caller). `request_expired`, written by `cancel_my_ride` and `expire_seat_requests` for other users' requests, carries `user_id` null (3.4), and no TAW-30 writer updates an `accounts`-referencing column (status updates of `seat_requests` do not re-run its foreign-key check, since `rider_id` is unchanged). Hence after level 1 no TAW-30 writer waits for an `accounts` row. 8.2 scenario 25 holds a rider's `accounts` row `for update` in another session and shows that `cancel_my_ride` and `expire_seat_requests` complete without waiting for it.

**Lock strengths.** No TAW-30 writer takes `for update` on any row or updates a key column. `for share`, `for no key update` and `for key share` are mutually compatible where it matters: a foreign-key check never waits for a TAW-30 writer. The stronger locks of other writers: `publish_ride`, `set_role`, `complete_profile`, `submit_car` and the admin's `update accounts` each take **one** `accounts` row (their own) `for update` per call, and `submit_car` and `review_item` then **one** car `verification_items` or `vehicles` row; a `service_role` catalogue transaction may update **several** `car_types` rows in any order (F66). A TAW-30 writer's **first** level-1 lock may wait for one of them (F24); its later level-1 locks, the relation guard and its level-2 row locks never wait (`nowait` / `skip locked`; F85, F92). Since O5, `service_role` cannot lock `accounts` rows `for update` directly (that needs `UPDATE`), but it can through the TAW-4 definer functions it may still execute (`complete_profile`, `submit_car`, `set_role`; 2), for **several** users in one transaction and in any order (F92); and it can lock the guarded relations of level 2 in any mode (F85). Both are in the inventory below.

**Share-code reservation (F23, F5).** An insert into `rides` waits on an **uncommitted** row with the same share code. TAW-30 replaces `taw29_new_share_code()` (same signature, grants and output format) so that, for each candidate code, it also takes `pg_try_advisory_xact_lock(hashtext('taw-share-code'), hashtext(<code>))` and draws again if the lock is not granted. Every transaction that inserts a ride (`publish_ride`, the job) draws codes only through this function, so two uncommitted transactions never hold the same code, and an insert never waits on the unique index; a code committed meanwhile raises `unique_violation` at once and the existing retry draws again (up to 5 attempts, as TAW-29). `publish_ride`'s body is unchanged.

|---|---|
| `publish_ride` (TAW-29, unchanged body) | 1 own `for update`, 2 own, inserts series and rides (share codes reserved) |
| admin revocation; TAW-4 `complete_profile` | 1 own row `for update` |
| TAW-4 `set_role` | 1 own row, then own `profiles` row (not locked by TAW-30) |

**Why no cycle.** (a) Among TAW-30 writers, level-1 locks are all `for share`; they block only the `for update` writers (single-row TAW-4, publish and admin writers, and `service_role` transactions calling the TAW-4 definer functions for one or several users; F92). (b) From level 2 on, every TAW-30 writer acquires levels in increasing order, so TAW-30 writers cannot wait on each other in a cycle. (c) **No wait from a TAW-30 writer to another kind of transaction while it holds a row lock (F85, F92).** A TAW-30 writer can wait for a lock held by a non-TAW-30 transaction only while acquiring its **first** `accounts` row, when it holds no row lock and only `ACCESS SHARE` locks from its unlocked reads, which no other transaction can be waiting for (API roles can take nothing stronger on those relations, 2). After that: later `accounts` rows are `nowait` / `skip locked`; the relation guard is `nowait`, and level-2 rows are `nowait` / `skip locked`; levels 3–5 and 7 touch only rows and relations that no API role can lock in a conflicting mode (`service_role` has at most `SELECT` on `rides`, `ride_series`, `accounts`, `profiles`, `vehicles`, `verification_items` and nothing on the new tables or `pilot_events`, 2), the guarded relations are already locked against `SHARE` and stronger, and its account foreign-key checks are on rows it already holds (F80); level 6 waits only for another `request_seat` of the same rider (hand-taken advisory locks: Not in the inventory, below). So any wait-for chain from a TAW-30 writer that holds a lock stays among TAW-30 writers past level 2, which (b) keeps acyclic, and no cycle can contain both a TAW-30 writer and another transaction. For example, a `service_role` transaction that calls `submit_car` for B and then `complete_profile` for A, while `decide_request` holds A `for share` and needs B, makes the decision raise `try_again` at B instead of waiting (the job skips B's series), and a `service_role` transaction that holds `car_types` `EXCLUSIVE` and then calls `review_item` or a TAW-4 function for the writer's own account finds the writer already gone with `try_again` (8.2 scenarios 28 and 29). A publish/admin/TAW-4 writer waits only for its own rows (held by TAW-30 writers at most `for share`); with share-code reservation it never waits on another transaction's ride insert. (d) **Catalogue updates and reviews (F66, F85):** no TAW-30 writer waits for a level-2 row or for a table lock on a level-2 relation (the relation guard comes first and is `nowait`; rows: client writers `nowait`, the job `skip locked`), so a transaction that holds a `car_types` or `verification_items` row `for update` and then waits for another level-2 row held `for share` by a TAW-30 writer — for example one `service_role` transaction that updates a car type and then calls `review_item` — waits only for a TAW-30 writer that is itself never waiting at level 2; that writer waits at most at levels 3–5 for other TAW-30 writers, which are past level 2 and never wait for a non-TAW-30 transaction after level 1. (e) **The job never waits once it holds a row lock (F66, F92):** it waits only for its first level-1 share lock, when it holds no row lock; its later account locks and levels 2 and 3 are `skip locked`, and its relation guard is `nowait` (a series it cannot lock is skipped this run); its inserts never wait on the share-code index (reservation) or on `unique (series_id, ride_date)` (only the job inserts into an existing series, and its advisory lock excludes overlapping runs); foreign-key checks of its inserts take `for key share` on the series it holds and on catalogue rows, which no writer locks `for update` or with a key change. A transaction that never waits while holding the locks others wait for cannot be part of a cycle, so every chain through the job (for example: job holds type A, `cancel_my_ride` holds series S and waits for rider R's account held by R's `submit_car`, which waits for type B held by a catalogue transaction that waits for A) ends at the job, which proceeds (it skips S) and commits. (f) `expire_seat_requests` never waits at level 5 (`skip locked`), and its event inserts reference no `accounts` row (F80) and take only `for key share` on series and ride rows, which no writer holds `for update`. (g) **Client writers and catalogue updates (F80):** a client writer may hold one `car_types` row while it waits at level 3+; every transaction it can wait for there is a TAW-30 writer that, past its own level 1, waits only for TAW-30 levels 3–5 (no late account references), never for an `accounts` row held by a TAW-4 writer, so the chain request_seat (type A) → series S → `cancel_my_ride` → rider R's account → R's `submit_car` → type B → catalogue → type A cannot form. This is UNVERIFIED until 8.2 passes (V6).

**Not in the inventory:** account deletion cascades (maintenance-only, 3.5); maintenance commands that cannot run inside a transaction block (`reindex … concurrently`; maintenance-only, like 3.5); advisory locks on TAW-30's or TAW-29's keys (`taw30-rider`, `taw30-expire`, `taw-share-code`, `taw29-extend-weekday-series`) taken by hand in another session (any role can call `pg_advisory_xact_lock`; Proposal: a residual, since the functions take these keys only as stated here). Each can at worst cause a deadlock that Postgres detects (below).

**One writer invocation per transaction (F102).** Levels are ordered within one call, but row locks last until the transaction ends. The claim therefore covers transactions that run **one** TAW-30 writer call: every supported entry point does — each PostgREST RPC is its own transaction, the runbook snippet (6.3) calls `cancel_my_ride` once per transaction, and the jobs run one call per `pg_cron` run. SQL that composes several writer calls in one transaction (for example two `cancel_my_ride` calls for two series in opposite orders) is unsupported; it can deadlock, and Postgres then aborts one transaction with no partial state. The runbook says so (6.3).

**Scope of the deadlock-freedom claim (F97).** The claim of "Why no cycle" covers every cycle that contains **a TAW-30 writer** (the client writers of section 5, `extend_weekday_series`, `expire_seat_requests`). Cycles made only of inherited non-TAW-30 transactions are TAW-29/TAW-4 behaviour that TAW-30 neither adds nor changes, and are outside it: for example TAW-29 `publish_ride` (unchanged body) locks the owner's `accounts` row `for update` and then reads `car_types`, so it can deadlock with a `service_role` transaction that holds an `ACCESS EXCLUSIVE` catalogue lock and then calls `complete_profile` for the same user. No TAW-30 writer can join such a cycle: a TAW-30 writer never waits for a catalogue relation or catalogue row (guard and level-2 locks are `nowait`/`skip locked`) and waits for an `accounts` row only for its first one, while holding nothing that `publish_ride` or the TAW-4 functions wait for (only `for share` account locks, which they wait for only on their own single row before taking any catalogue lock). Handling of the inherited case: Postgres aborts one of the two transactions (`40P01`) with no partial state; the app already maps a failed publish to TAW-29's retry message; the runbook (6.3) adds the rule "one admin change per service-key transaction; never combine a catalogue table lock with TAW-4 function calls". 8.2 scenario 30 shows that a TAW-30 writer stays out of it.

**Liveness, not safety.** No invariant depends on deadlock freedom: every writer is one transaction, and Postgres aborts one transaction of any deadlock it detects, leaving no partial state. Deadlock freedom is a liveness goal, tested by 8.2.

**The series row (level 3, `for no key update`) is the serialisation point for seats.** Every writer that changes `seats_taken` or holds holds it; `request_seat`'s `for share` on it keeps the ride's status and seat count fixed while it decides.

### 8.3 `extend_weekday_series` (TAW-29 function, replaced with `create or replace`)

TAW-30 keeps TAW-29 8.1 semantics (advisory lock, re-read under lock, authorisation point, ±60-minute skip, never recreating a cancelled day, one transaction, inserted days start with `seats_taken = 0`) and changes only its locking and time handling, because its per-series `accounts … for update` would deadlock with TAW-30's share locks (F3, F4) and its capacity read was unlocked (F61):

1. **Isolation contract first** (5.0: raise `unsupported_isolation` unless read committed), **then** `pg_try_advisory_xact_lock` as before, returning 0 when it is held; so a successful run, even a no-op, proves the guard ran (F78).
2. Read the candidate series (unlocked). Lock **all** their owners' `accounts` rows `for share` in `user_id` order: the first may wait, every later one is `for share skip locked`, and a series whose owner's account was not locked is **skipped in this run** (F92). Then take the relation guard (8.1 level 2) `nowait`; if it is not granted, the run returns 0 having inserted nothing (F85). Then lock their level-2 rows (8.1) `for share skip locked`: the car `verification_items` rows in `user_id` order, their `vehicles` rows, then the distinct `car_types` rows in id order. A series whose owner's verification item, vehicle or car type was not locked is **skipped in this run** (the next hourly run retries. A skipped day is created only by a later run that still finds it before its departure: a day that becomes eligible less than an hour before departure, for example after a conflicting ride is cancelled, and whose next successful run comes after its departure, is **never created** — the same outcome as TAW-29's departure check; F103). Nothing is inserted before this step finishes.
3. Per remaining series in id order: lock the series `for no key update skip locked`; a series held by another writer (a decision, a cancellation) is **skipped in this run** without waiting (F66); re-read it (skip unless `active` and `weekdays`); skip unless `taw29_ride_offerable(owner, seats_offered)`, evaluated on the locked rows; for each missing weekday date, immediately before each insert attempt (including share-code retries) take `v_now := clock_timestamp()` and insert only if `departs_at > v_now`, skipping the date when the owner has another `scheduled` ride on the same route and direction within ±60 minutes (the TAW-29 predicate, F37).

It writes no hold, request or cancellation. Its grants are unchanged and re-asserted. pgTAP covers the F8 backfill (a series day skipped earlier for the ±60-minute rule is created after the conflicting ride is cancelled), the skip of a series whose level-2 row is locked and of a series whose row is locked, a skipped run whose retry comes after the missing day's departure (the day is not created, F103), each without waiting, and the insertion by the next run after release.

**TAW-29 concurrency suite (F71).** `supabase/tests/taw29/concurrency.sh` scenarios 2 ("Extension vs review_item rejecting the car") and 3 ("Extension vs runbook cancellation") assert that the job **waits** when the other writer goes first. Under 8.3 it skips instead. The TAW-29 baseline is kept as evidence of TAW-29 (its committed T12 report); after the TAW-30 migration those two first-holder cases are changed, and only they: rejection-first and cancellation-first → the job returns **without waiting** (no lock wait observed; `statement_timeout = '2s'` would not be reached) and creates no day for that owner; after the holder commits, a further run creates no day either (not offerable / cancelled). The extension-first halves are unchanged (the rejection or cancellation waits for the job and commits after it; the new day is kept). Scenario 5 ("Extension vs publish_ride by the same owner", F95): its extension-first half is unchanged; in its **publish-first half** the publishing owner (`owners[5]`) is not the job's first candidate account (other active candidates precede it in `user_id` order), so under 8.3 the job takes that account `skip locked` and skips its series instead of waiting. That half is changed, and only it: with the publish transaction still open, the job finishes (no lock wait observed on the publisher's account) and creates no day for that owner; after the publish commits, a further job run creates no day on the published date (the TAW-29 ±60-minute rule skips it) and the existing duplicate assertions still hold. Scenarios 1, 4 and 6 are unchanged in their assertions. ### 8.4 Expiry (AC4)

- Readers show `taw30_request_state`, so a request is `expired` the moment its day departs or is cancelled.
- `public.expire_seat_requests()` first applies the isolation guard (5.0), **then** takes `pg_try_advisory_xact_lock(hashtext('taw30-expire'))` and returns 0 if it is held (F78) (an overlapping run or a maintenance transaction, 3.5). It then stores expiries in batches of 100: with `v_t := clock_timestamp()`, select stored-`pending` requests whose ride `departs_at <= v_t`, **or** whose ride has `cancelled_at <= v_t`, **or** whose series has `cancelled_at <= v_t` — exactly the predicates of `taw30_request_state` (F33, F49) — ordered by `id`, after the last id of the previous batch, with `for no key update of <seat_requests alias> skip locked`; then `v_now := clock_timestamp()`; for each locked request, compute `taw30_request_state(request, v_now)` and, when `expired`, store exactly that result and insert one `request_expired`. The id cursor guarantees progress; the run ends when a batch is empty. Returns the count. A second run over unchanged, unlocked rows returns 0; a row skipped because it was locked is picked up by a later run. (The cancel functions normally store these expiries themselves; the sweep is the recovery path.)
- `pg_cron` job `taw30-expire-seat-requests`, `*/5 * * * *` (Proposal), created by the migration like TAW-29's (unschedule by name, then schedule). Local: plan step; hosted: UNVERIFIED, owner-run (V3b).
- **Scheduler-run evidence (F63, F70, V10).** `supabase/tests/taw30/cron-run.sh`, on the disposable local database after `supabase db reset`, for each writer job (`taw30-expire-seat-requests` and the replaced `taw29-extend-weekday-series`):
  1. **Identity:** reads the job's row in `cron.job` by name and **asserts** `command` equals the expected text exactly (`select public.expire_seat_requests()` / the TAW-29 command `select public.extend_weekday_series()`, whitespace-normalised), `username` equals the migration owner role (`postgres` locally, Expected; the script reads `current_user` of the migration connection and asserts equality), `database` equals `current_database()`, and `active` is true; it also records the role and database settings from `pg_db_role_setting` in the evidence. A mismatch fails the script.
  2. **Fence (F78, F111):** a fence session takes the session-level advisory locks `pg_advisory_lock(hashtext('taw30-expire'))` and `pg_advisory_lock(hashtext('taw29-extend-weekday-series'))` (the keys the two job functions try first, returning 0 when held; 8.3, 8.4), then sets both jobs inactive with `cron.alter_job(<jobid>, active => false)`. While the fence holds, any run, including one the scheduler selected before the deactivation and starts at any later time, returns 0 without reading or writing a fixture row. **Scheduler barrier (F111):** still under the fence, the script ends every task the scheduler selected before the deactivation: it terminates the `pg_cron` launcher backend and every backend running either job's command (`pg_terminate_backend`; job IDs, rows in `cron.job` and their identity are untouched), then waits until a launcher backend with a **new** pid is running and no backend runs either command. The restarted launcher loads the jobs as inactive, so it holds no selected task of them; every run of either `jobid` after the barrier was selected after step 4's activation. The launcher's `backend_type` text (Expected `pg_cron launcher`) is confirmed at plan time (T0); if the launcher cannot be identified or does not restart within 60 seconds, the script exits 2 (harness error).
  3. **Fixtures**, created while the fence holds and both jobs are inactive: for expiry, one stored-`pending` request whose day has departed; for extension, an active weekdays series of an offerable owner with one missing future weekday inside the window, chosen as a date that is **not** the series' `published_ride_id` day (that ride is referenced by `ride_series.published_ride_id` and is never deleted), with no ±60-minute conflict; the fixture deletes only that non-anchor day's ride row (it has no requests).
  4. **Run:** after the barrier, the script reads the marker `m := clock_timestamp()` in the transaction that runs, for each job, `cron.alter_job(<same jobid>, schedule => '* * * * *', active => true)` (command, user and database untouched), before that transaction commits; after the commit the fence session releases both advisory locks. The script then waits up to 3 minutes per job for the fixture's work to appear (step 5).
  5. **Real work and attribution:** the expiry fixture must be stored `expired` (its `request_expired` event's `occurred_at` = t), and the extension fixture's day must exist with `seats_taken = 0` (its `created_at` = t). For each fixture there must be exactly one `cron.job_run_details` row of that job's `jobid` with `start_time >= m`, `start_time <= t <= end_time`, `status = 'succeeded'` and a `return_message` free of `unsupported_isolation`; that run is the attributed run (any run of that `jobid` has the identity asserted in step 1, and after the barrier every such run was selected after activation). Work done with no such row (for example by a session that is not the scheduler), or not done within 3 minutes, fails the script; no fixture can be consumed before `m`, because the fence held until after it.
  It restores the schedules with a final `supabase db reset` (trap on every exit path) and saves the rows in the evidence. The same identity and run checks are part of the hosted owner-run verification (V3b, V10).

## 12. Privacy and security

- A request's `pickup_text` and `message` are returned only to its rider and the series owner (request view). No API role reads the new tables or `pilot_events` directly (section 14). Events and cancellations hold no free text.
- **Service-role boundary (F36).** The **project service credential** (the service key) is the owner's server-side secret: it administers Auth and is never shipped in the app (TAW-29's secrets scan covers the bundle). The **`service_role` database role** keeps the grants inherited from TAW-4 and TAW-29 (`SELECT` on `rides`, `ride_series`; `ALL` on `car_types`). TAW-30's boundary is narrower and exact: the `service_role` role cannot read `seat_requests`, `seat_holds`, `cancellations` or `pilot_events`, so it cannot link a rider to a request, a seat, a cancellation or an event, or read a rider's pickup text or message. Tests assert exactly this (14).
- Missing and foreign ids give identical responses (`request_not_found`, `ride_not_found`, `series_not_found`).
- No view discloses a user id, last name, phone, plate, community or TAW-4 free text.
- Seat allocation is serialised per series and guarded by the `seats_taken` check (AC2).
- The app never logs RPC payloads, texts or request ids (`noLogging` test).
