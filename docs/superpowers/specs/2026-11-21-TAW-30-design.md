## 1. Purpose and boundaries

A phone-verified rider with a completed profile requests seats on a posted ride, for that one day or, on a weekday series, for every weekday from that day on. The driver sees the requests and accepts or declines each one. The server allocates seats so that no ride day is ever overbooked. The rider can withdraw a pending request. Either side can cancel one day, chosen days or the whole series, with a reason; nobody is penalised. Pending requests expire at departure and when their day is cancelled. Both sides see current status in the app (My trips, the ride, the request).

In TAW-30: sections 3–12. Not in TAW-30:

- Push notifications (separate PROPOSED card, Owner; needs a paid Apple Developer account).
- Chat, a pickup agreement in chat and in-chat ride offers (TAW-31). Completion, no-shows, ratings, reports and blocks (TAW-32).
- The phone OTP flow and the TAW-26 verification screens (TAW-5).
- Editing a request after it is sent; waitlists; a weekdays member adding back a single day they cancelled while still a member (they may leave and request again, R9d: "You can request to join again later").
- Android (D10) and Arabic/RTL.

## 2. Decisions and inherited facts

**Owner decisions (TAW-30 scope revision 3, 2026-11-21):**

- **O1 Push.** No push in TAW-30; status is shown in the app (AC5).
- **O2 Every-weekday request.** One request for the whole series. Accepting is all-or-nothing on seats; the rider then holds the seat on every upcoming day from their first day on, including days the weekday job adds later, until they cancel days or leave (AC8).
- **O3 Expiry.** A pending request expires at departure and when its day (or the series) is cancelled. A request asking for more seats than are left cannot be accepted (R6) and stays pending (AC4).
- **O4 Later-card items** on R1–R9f follow the TAW-29 O4 rule (AC10, section 11.2).

**Facts (migrations on main):**

- `ride_series` (`repeat` in `once`, `weekdays`; `status` in `active`, `cancelled`; `seats_offered` 1–8, immutable). `rides`: one row per day with copied `seats_offered`, `seats_taken smallint not null default 0 check (seats_taken between 0 and seats_offered)`, `status` in `scheduled`, `cancelled`, `cancelled_at`, `departs_at`, `unique (series_id, ride_date)`. Nothing writes `seats_taken` today.
- The three TAW-29 readers compute a ride state `cancelled` > `withdrawn` > `departed` > `full` > `available` (in that precedence) using `taw29_ride_offerable(owner, seats_offered)`. `list_rides` returns only rides with `seats_taken < seats_offered`, departing after `now()`, with `p_day` inside the 14-day window (else `invalid_day`).
- `is_phone_verified()`, `require_phone_verified()` (raises `phone_unverified`) and TAW-4 `can_request_rides()` (`profile_completed_at` not null) exist, `security definer`, executable by `authenticated`. `taw29_has_contact(text)` is the owner-only contact filter.
- `public.accounts`: `user_id references auth.users on delete cascade`; `revoke all … from public, anon, authenticated`; `grant select … to authenticated`. `service_role`'s table privileges on `accounts` are not set by the migration (left to platform defaults) — whether `service_role` can update `phone_verified` is **UNVERIFIED** (F21; section 6.3).
- `extend_weekday_series()` (TAW-29): `pg_try_advisory_xact_lock`, then per active weekdays series, in series-id order: owner `accounts` row `for update`, owner `verification_items` car row `for share`, `ride_series` `for update`; inserts missing future weekday rows from `first_date` with `on conflict (series_id, ride_date) do nothing`, skipping dates within ±60 minutes of another scheduled ride of the owner. The migration schedules it hourly (`cron.schedule`, **Fact**); its hosted existence and run identity are **UNVERIFIED** (V3, owner-run).
- `pilot_events.event_type` has an inline column check `event_type in ('ride_posted','ride_viewed')` **and** a separate table check tying columns to the type. `pilot_events.user_id references accounts on delete cascade`. `service_role` has `SELECT` on it.
- TAW-29 `publish_ride`, TAW-4 `set_role` and `complete_profile` lock the caller's own `accounts` row `for update`; TAW-4 `review_item` updates a `verification_items` row.
- The Trips tab is an empty `TabScreen`. D1 and D2 show a disabled request button (TAW-29 O4). `RideDetail` shows the D4a banner for a full ride. `NotVerifiedRide.tsx` hard-codes the posting copy. `__tests__/rides/shared-ride-resume.test.tsx` names `./ride/[id].tsx` in its route fixture.

TAW-29 objects are kept unchanged **except**: the `pilot_events` checks and columns (3.4), `extend_weekday_series` (8.3), the TAW-29 runbook entry "stop a series" (6.3), and the moved detail route (11.3). TAW-29's readers and `publish_ride` are not changed.

## 3. Data model (one schema migration)

New tables live in `public`, have RLS enabled and **no policies**, and **no privilege for any API role** (`anon`, `authenticated`, `service_role`); see section 14. Every read and write goes through the `security definer` functions of section 5. No column, argument or screen field holds a price, fare, cost, amount or currency (AC6).

### 3.1 `seat_requests`

| Column | Constraint |
|---|---|
| `id` | `uuid` pk default `gen_random_uuid()` |
| `rider_id` | `uuid not null references accounts(user_id) on delete cascade` |
| `client_request_id` | `uuid not null`; `unique (rider_id, client_request_id)` |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `anchor_ride_id` | `uuid not null references rides on delete cascade`: the day the rider asked for; for `weekdays`, the first day |
| `anchor_date` | `date not null` (copied from the anchor ride, for the day predicates of section 4) |
| `kind` | `text not null check in ('one_day','weekdays')` |
| `seats` | `smallint not null check between 1 and 8` |
| `pickup_text` | `text`, null or trimmed 1–80: the rider's pickup suggestion; null means the driver's pickup note |
| `message` | `text`, null or trimmed 1–200 |
| `status` | `text not null default 'pending' check in ('pending','accepted','declined','withdrawn','expired','cancelled')` |
| `expired_cause` | `text check in ('departed','ride_cancelled')`; not null exactly when `status = 'expired'` |
| `decided_at` | `timestamptz`; not null exactly when `status in ('accepted','declined','cancelled')` |
| `closed_at` | `timestamptz`; not null exactly when `status in ('declined','withdrawn','expired','cancelled')` |
| `closed_by_side` | `text check in ('rider','owner','system')`; not null exactly when `closed_at` is not null |
| `created_at` | `timestamptz not null default now()` |

Table checks state each "exactly when" pairing. Input columns never change after insert. Status moves only forward: `pending → accepted | declined | withdrawn | expired`, `accepted → cancelled`; a test asserts no function performs another transition.

Indexes: `(series_id, status)`, `(anchor_ride_id) where status = 'pending'`, `(rider_id, created_at)`, and the backstop unique index `(rider_id, anchor_ride_id) where status in ('pending','accepted')`.

### 3.2 `seat_holds` (one row per request and day)

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `request_id` | `uuid not null references seat_requests on delete cascade` |
| `ride_id` | `uuid not null references rides on delete cascade` |
| `seats` | `smallint not null check between 1 and 8` (copied from the request) |
| `status` | `text not null default 'held' check in ('held','cancelled')` |
| `cancellation_id` | `uuid references cancellations(id) on delete set null`; set when the hold is cancelled |
| `cancelled_at` | `timestamptz`; `check ((status = 'cancelled') = (cancelled_at is not null))` |
| `created_at` | `timestamptz not null default now()` |

`unique (request_id, ride_id)`; index `(ride_id) where status = 'held'`.

**Seat invariant (AC2).** For every ride, `rides.seats_taken = coalesce(sum(seats) of its 'held' holds, 0)`. It is maintained:

- by the functions of section 5 and `extend_weekday_series`, which change holds and `seats_taken` together under the series lock (8.1);
- for deletions (account deletion through the TAW-4 `auth.users → accounts` cascade, or an admin deleting a request), by the trigger `taw30_hold_deleted` (`after delete on seat_holds for each row`, `security definer`, `search_path = ''`): when the deleted row was `held` and its ride still exists, it subtracts the seats from that ride's `seats_taken`. A ride deleted in the same cascade needs nothing.

The TAW-29 check `seats_taken between 0 and seats_offered` is the last line of defence. pgTAP asserts the invariant for every ride after every scenario (section 13), including the TAW-4 cascade.

### 3.3 `cancellations` (AC3)

One row per cancelled ride day per action (a zero-day leave or stop has one row with `ride_id` null):

| Column | Constraint |
|---|---|
| `id` | `uuid` pk |
| `action_id` | `uuid not null`: shared by the rows of one user action |
| `actor_id` | `uuid not null references accounts(user_id) on delete cascade` |
| `actor_side` | `text not null check in ('rider','owner')` |
| `series_id` | `uuid not null references ride_series on delete cascade` |
| `ride_id` | `uuid references rides on delete cascade`; null only when the action affected no day (`day_count` 0 in its event) |
| `request_id` | `uuid references seat_requests on delete cascade`; not null exactly when `actor_side = 'rider'` |
| `scope` | `text not null check in ('one_day','chosen_days','all')`; `ride_id` null only with `scope = 'all'` |
| `reason` | `text not null`; rider: `change_of_plans`, `found_another_ride`, `owner_changed_plan`, `something_else`; owner: `change_of_plans`, `car_not_available`, `not_enough_riders`, `something_else` (a check ties each set to `actor_side`) |
| `created_at` | `timestamptz not null` (the action's decision time, 5.0) |

Unique `(action_id, ride_id)` (nulls distinct; at most one null row per action, enforced by the writer). Each cancelled hold points to **its own day's** row; rows of one action share only `action_id`. No free text; no penalty, fee, score or counter is derived (AC3).

Withdrawing a **pending** request (R2 "Cancel request") is not a seat cancellation: it records actor (`closed_by_side = 'rider'`) and time (`closed_at`) on the request, with no reason (no sheet in the approved design; Proposal), and logs `request_withdrawn`.

**Deletion contract (pilot; F18).** Account deletion is a later card. Until then the existing TAW-4 cascade (`auth.users` → `accounts`) remains possible for admins: it deletes the user's requests, holds and cancellation rows; the trigger keeps every surviving ride's `seats_taken` correct; a deleted owner's series and rides cascade away. pgTAP covers both.

### 3.4 `pilot_events` (TAW-29 table, changed; AC7)

The migration drops **both** TAW-29 checks (the inline `event_type` check, named by the catalogue as `pilot_events_event_type_check`, and the table check; the plan reads their actual names from `pg_constraint` before dropping) and adds:

- Columns (nullable): `request_id uuid references seat_requests on delete set null`, `request_kind text`, `seats smallint`, `scope text`, `reason text`, `day_count smallint`, `cause text`.
- A new `event_type` check with the two TAW-29 types and `request_created`, `request_accepted`, `request_declined`, `request_withdrawn`, `seat_cancelled`, `ride_cancelled`, `request_expired`.
- A new table check: the two TAW-29 branches exactly as before, each additionally requiring the seven new columns to be null; plus one branch per new type:

| `event_type` | `user_id` | Non-key columns that must be set | Must be null |
|---|---|---|---|
| `request_created` | rider | `request_kind`, `seats` | `scope`, `reason`, `day_count`, `cause`, `source`, `ride_state`, `repeat`, `ride_count` |
| `request_accepted` | owner | `request_kind`, `seats`, `day_count` | the rest |
| `request_declined`, `request_withdrawn` | owner / rider | — | all new and TAW-29 optional columns |
| `seat_cancelled` | rider | `scope`, `reason` (rider set), `day_count` | the rest |
| `ride_cancelled` | owner | `scope`, `reason` (owner set), `day_count` | the rest |
| `request_expired` | rider | `cause` | the rest |

Value checks: `request_kind in ('one_day','weekdays')`, `seats between 1 and 8`, `scope in (…)`, `day_count >= 0`, `cause in ('departed','ride_cancelled')`.

Key columns (`series_id`, `ride_id`, `request_id`) are not in the check, because `on delete set null` may null them later. The writers always set `series_id` and `request_id` (except `ride_cancelled`, which has no request) and `ride_id` (the anchor, or the first affected day, or null for a zero-day action); pgTAP asserts this per type. Every writer sets `event_day = (v_now at time zone 'Africa/Cairo')::date` and `occurred_at = v_now` (5.0). Events hold no names, phone numbers, pickup text or messages. Each is inserted inside its action's transaction, without exception handling, so a failed event fails the action. `pilot_events_one_daily_view` is unchanged.

## 4. Time, membership and states

- **Decision time.** Every writing function captures `v_now := clock_timestamp()` **after** acquiring all its locks (5.0) and uses `v_now`, never `now()`, for departure comparisons and stored times. Readers use `clock_timestamp()` once per call.
- A ride day is **open for seats** at time t when: `rides.status = 'scheduled'`, the series is `active`, `departs_at > t`, and `taw29_ride_offerable(owner, seats_offered)`.
- **Active membership:** a request with `kind = 'weekdays'` and `status = 'accepted'`. It is active whether or not it currently has a future `held` hold.
- **Member days** of a weekdays request at time t: the series' rides with `ride_date >= anchor_date`, `status = 'scheduled'` and `departs_at > t`. Acceptance (5.4) and the weekday job (8.3) use exactly this predicate.
- **Effective request state** (one function, `taw30_request_state`, used by every reader and writer; F6). For stored `pending`:
  - let `t_dep` = the anchor's `departs_at` if it is `<= t`, else none; let `t_can` = the earliest of the anchor's `cancelled_at` and the series' `cancelled_at`, if any;
  - if neither → `pending`;
  - else → `expired` with cause and close time of the **earlier** trigger: `departed` (`closed_by_side = 'system'`, `closed_at = t_dep`) or `ride_cancelled` (`closed_by_side = 'owner'`, `closed_at = t_can`); a tie counts as `ride_cancelled`.
  For any other stored status, the stored values. Writers that store an expiry (5.6, 8.4) store exactly what this function returns, so the outcome never depends on which writer runs first.
- **Held day state** (rider), in this precedence: `cancelled` (hold cancelled; `by` = the cancellation's `actor_side`) > `departed` (`departs_at <= t`) > `unavailable` (the ride's TAW-29 state is `withdrawn`) > `confirmed`.

## 5. Server functions

### 5.0 Common rules

- Every function is `security definer`, `set search_path = ''`, schema-qualified, raises `raise exception '<code>'`, and checks set membership null-safely. Order of the first checks: `not_authenticated` (no `auth.uid()`), then `missing_argument` (any required argument null). Privileges: section 14.
- Locks follow section 8.1. After the last lock: `v_now := clock_timestamp()`, then all state checks against `v_now`.
- No argument names a user; each function acts only for `auth.uid()`.
- A function that refuses for state reasons writes nothing and leaves every row unchanged.

### 5.1 `public.can_request() returns text` (stable)

`'phone_unverified'` unless `is_phone_verified()`; else `'profile_incomplete'` unless `can_request_rides()`; else `'ok'`. With no caller: `'phone_unverified'`. Authorises nothing.

### 5.2 `public.request_seat(p_client_request_id uuid, p_ride_id uuid, p_kind text, p_seats int, p_pickup_text text, p_message text) returns jsonb` (AC1, AC8)

Required: `p_client_request_id`, `p_ride_id`, `p_kind`, `p_seats`. Texts: null or empty after trimming means none.

1. `not_authenticated`; `missing_argument`.
2. Locks: the caller's `accounts` row `for share` (missing → `account_missing`); read the ride (unknown → `ride_not_found`) and lock its `ride_series` row `for share`; then the caller's **rider advisory lock** `pg_advisory_xact_lock(hashtext('taw30-rider'), hashtext(auth.uid()::text))` (serialises one rider's requests; level 7 of 8.1). Then `v_now`.
3. `require_phone_verified()` → `phone_unverified`; `can_request_rides()` false → `profile_incomplete`. (The gate runs **before** the replay check, so a revoked rider cannot use replays; F15.)
4. **Idempotency.** Inputs normalised as step 7. If `(rider_id, client_request_id)` exists: equal stored inputs → `{request_id, state: <effective state>, replayed: true}`; otherwise `request_conflict`.
5. Caller owns the series → `own_ride`. The anchor must be open for seats at `v_now` and not full → `ride_unavailable`.
6. `p_kind` in the set → `invalid_kind`; `weekdays` on a `once` series → `invalid_kind`. `p_seats` between 1 and `seats_offered` → `invalid_seats`; `p_seats > seats_offered - seats_taken` of the anchor → `not_enough_seats`.
7. Texts trimmed, empty to null; lengths → `invalid_pickup_text` / `invalid_message`; `taw29_has_contact` → `contact_details_not_allowed`.
8. Limits (Proposal, `request_limits()`): more than 20 requests created by the caller in the 24 hours before `v_now` (replays excluded) → `rate_limited`; 5 or more of the caller's requests in effective state `pending` → `too_many_pending`.
9. A request by the caller anchored on this ride was `declined` → `already_declined` (Proposal).
10. **Open requests** (Proposal; F7): refused with `already_requested` when the caller has, in this series,
    - an active membership (4), or
    - a request in effective state `pending`, or
    - (`one_day`) an `accepted` one-day request anchored on this ride;
    and, for `weekdays`, any `accepted` one-day request in this series whose day has not departed.
11. Insert the request (`pending`, `anchor_date` from the ride, `created_at = v_now`); insert `request_created`. Return `{request_id, state: 'pending', replayed: false}`.

A request reserves no seat; seats are allocated only on acceptance.

### 5.3 `public.withdraw_request(p_request_id uuid) returns jsonb` (R2 "Cancel request")

Locks: caller's `accounts` row `for share`; the request's `ride_series` `for share`; the request `for update`. `v_now`. Not the caller's request (or missing) → `request_not_found`. Effective state not `pending` → `request_not_pending`. Set `withdrawn`, `closed_at = v_now`, `closed_by_side = 'rider'`; insert `request_withdrawn`. Return the request view (5.7).

### 5.4 `public.decide_request(p_request_id uuid, p_decision text) returns jsonb` (AC2, AC4, AC8; R4–R6)

1. `not_authenticated`; `missing_argument`; `p_decision` not in `accept`, `decline` → `invalid_decision`.
2. Read the request and series without locks. Missing, or the caller does not own the series → `request_not_found` (same response either way).
3. Locks (8.1): the owner's and the rider's `accounts` rows `for share`, in `user_id` order; the owner's `verification_items (user_id, 'car_owner')` row `for share`; `ride_series` `for update`; for `accept`, the rides of the series with `ride_date >= anchor_date` `for update` in `(ride_date, id)` order; the request `for update`. Then `v_now`.
4. Effective state not `pending` → `request_not_pending`.
5. **Decline:** `declined`, `decided_at = closed_at = v_now`, `closed_by_side = 'owner'`; insert `request_declined`; return `{result: 'declined', request: <view>}`.
6. **Accept:**
   1. Series `active` and `taw29_ride_offerable(owner, seats_offered)` → else `ride_unavailable`.
   2. Rider `accounts.phone_verified` (read under the share lock) → else `requester_unavailable` (Proposal; existing holds of a revoked rider stay, as TAW-29's revocation semantics).
   3. **Target days:** `one_day` → the anchor; `weekdays` → the member days at `v_now` (4). The anchor is always a target (step 4 guarantees it is open).
   4. **All-or-nothing check (O2), no writes on failure:** for each target day, `seats_offered - seats_taken >= seats`; for `weekdays`, also `seats + sum(seats of the series' active memberships) <= seats_offered` (so every day the job adds later fits all members, 8.3). On failure return, **without raising**, `{result: 'seats_unavailable', request: <view>, limit: {kind: 'day', ride_id, ride_date, seats_left}}` for the earliest short day, or `{… limit: {kind: 'members', seats_left: seats_offered - sum(members)}}`; nothing is written and the request stays `pending` (AC4, R6).
   5. Insert one `held` hold per target day; add `seats` to each day's `seats_taken`.
   6. `accepted`, `decided_at = v_now`; insert `request_accepted` (`day_count` = target days); return `{result: 'accepted', request: <view>}`.

### 5.5 `public.cancel_my_seat(p_request_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (rider; AC3; R9a, R9c, R9d)

1. `not_authenticated`; `missing_argument` (request, scope, reason); `invalid_scope`; reason not in the rider set → `invalid_reason`.
2. Read the request; not the caller's → `request_not_found`.
3. Locks: caller's `accounts` `for share`; `ride_series` `for update`; the series' rides with `ride_date >= anchor_date` `for update` in `(ride_date, id)` order; the request `for update`. `v_now`.
4. Status not `accepted` → `request_not_cancellable`.
5. **Cancellable days** = the request's `held` holds whose ride `departs_at > v_now`. **Affected days**:
   - `one_day`: `p_ride_ids` has exactly one non-null element, a cancellable day;
   - `chosen_days`: `p_ride_ids` non-empty, no nulls, no duplicates, each cancellable;
   - `all`: `p_ride_ids` null; all cancellable days (possibly none).
   Otherwise `invalid_days` (nothing partial).
   `one_day` and `chosen_days` with no cancellable day → `invalid_days`. A one-day request accepts only `one_day` or `all`.
6. One `action_id`. Per affected day: insert that day's `cancellations` row (rider, request, scope, reason, `created_at = v_now`); its hold → `cancelled`, `cancelled_at = v_now`, `cancellation_id` = that row; `seats_taken -= seats`. If there is no affected day (`all` only), insert one row with `ride_id` null.
7. The request → `cancelled` (`closed_at = v_now`, `closed_by_side = 'rider'`) when the scope is `all`, or when it is one-day. A weekdays request cancelled for `one_day`/`chosen_days` stays an active membership (O2).
8. Insert `seat_cancelled` (`day_count` = affected days; `ride_id` = first affected day or null). Return the request view.

### 5.6 `public.cancel_my_ride(p_series_id uuid, p_scope text, p_ride_ids uuid[], p_reason text) returns jsonb` (owner; AC3, AC4; R9b, R9e, R9f)

1. `not_authenticated`; `missing_argument`; `invalid_scope`; reason not in the owner set → `invalid_reason`.
2. Series missing or not the caller's → `series_not_found`.
3. Locks: caller's `accounts` `for share`; `ride_series`; all the series' `scheduled` rides in `(ride_date, id)` order; the series' requests with status `pending` or `accepted` in `id` order (row-lock strengths per 8.1). `v_now`.
4. Series `cancelled` → `series_not_active`.
5. **Cancellable days** = the series' rides with `status = 'scheduled'` and `departs_at > v_now`. Affected days per scope, as 5.5 step 5. A `once` series accepts only `all` (its sheet offers no day choice).
6. One `action_id`. Per affected day: its `cancellations` row (owner, `request_id` null); ride → `cancelled`, `cancelled_at = v_now`; its `held` holds → `cancelled` pointing to that row; `seats_taken = 0`. With no affected day (`all` only), one row with `ride_id` null.
7. Pending requests: for each, compute `taw30_request_state` **after** step 6 at `v_now`; when it is `expired`, store it (its cause is `departed` if the anchor had already departed, else `ride_cancelled`) and insert `request_expired`.
8. Scope `all`: the series → `cancelled`, `cancelled_at = v_now`; remaining pending requests expire as step 7 (cause by 4's rule; the series' `cancelled_at` is now set); every `accepted` request → `cancelled` (`closed_at = v_now`, `closed_by_side = 'owner'`).
9. Otherwise, each `accepted` one-day request whose day was affected → `cancelled` (`closed_by_side = 'owner'`). Active memberships stay and keep other days.
10. Insert `ride_cancelled` (`day_count`, `ride_id` = first affected day or null). Return `{series_id, series_status, cancelled_ride_ids}`.

### 5.7 Readers (AC5)

All readers: `not_authenticated`; `profile_incomplete` unless `can_request_rides()`; never return another person's user id, last name, phone, plate, community or TAW-4 free text; never write. (TAW-29's `get_ride` and `resolve_shared_ride` still log `ride_viewed` through `taw29_log_view`; TAW-30 adds no reader write.)

**Person view:** `display` (first name + first letter of last name + "."), `initials`, `member_since` (`Mon YYYY`), `phone_verified`. No ratings (AC10).

**Request view** (exact keys, built once by `taw30_request_view(p_request, p_caller)`):

| Key | Rider (caller is `rider_id`) | Owner (caller owns the series) |
|---|---|---|
| `request_id`, `kind`, `seats`, `state`, `expired_cause`, `closed_by_side`, `created_at`, `decided_at`, `closed_at` | yes | yes |
| `pickup_text`, `message` | yes (own text) | yes |
| `role` | `'rider'` | `'owner'` |
| `rider` (person view of the rider) | absent | yes |
| `driver` (person view of the owner) | yes | absent |
| `ride` (TAW-29 26-key projection of the anchor, same expression as `get_ride`, no view logging) | yes | yes |
| `series_id`, `series_repeat`, `series_status` | yes | yes |
| `days`: `[{ride_id, ride_date, departure_time, departs_at, state, by}]` for the request's holds (held day state, 4), by date | yes | yes |
| `cancellable_ride_ids`: the request's held future days (5.5 step 5) | yes | absent |
| `last_cancel_reason`: reason of the latest cancellation by the other side affecting this request, or null | yes | yes |

Anyone else gets `request_not_found`, identical to a missing id.

- **`public.get_my_ride_status(p_ride_id uuid) returns jsonb`** (D2, R1). Unknown → `ride_not_found`. Returns `{role, can_request, request, owner}`:
  - `role`: `'owner'`, `'rider'` (the caller has any request in this series, any state, created in the last 30 days), or `'none'`;
  - `can_request`: for `'none'` and for riders without an open request (5.2 step 10): the `can_request()` code, or `'ride_unavailable'` when the ride is not open-and-not-full, else `'ok'`; null otherwise;
  - `request`: the request view of the caller's most relevant request in this series (open first, else the latest), or null;
  - `owner` (owner only): `{series_id, series_repeat, series_status, pending_count, riders_count}` for this day (the rules of `list_ride_requests`).
- **`public.list_ride_requests(p_ride_id uuid) returns jsonb`** (R4, R6, R9b/e/f; owner only; else `ride_not_found`): `{ride, series: {series_id, repeat, status}, pending: [request view], riders: [{request_id, rider, seats, kind}], cancellable_days: [{ride_id, ride_date, departure_time, seats_taken}]}`. `pending` = effective-`pending` requests that would occupy this day: one-day anchored here, plus weekdays with `anchor_date <= ride_date`; oldest first. `riders` = `held` holds on this ride. `cancellable_days` = 5.6 step 5 at call time.
- **`public.get_seat_request(p_request_id uuid) returns jsonb`** (R2, R5, R7, R8): the request view.
- **`public.list_my_trips(p_tab text) returns jsonb`** (R3; `p_tab` in `upcoming`, `past` → else `invalid_tab`). Items `{type, …}` ordered by `departs_at` (requests by their anchor), at most 100 (Proposal):
  - `upcoming`:
    - `held_day` (rider): each `held` hold whose day has not departed, with request id, the ride projection and held day state;
    - `request` (rider): each request in effective state `pending`; each active membership (one item, with its next held day or "no upcoming days"); each request whose `closed_at` is within the last 48 hours (Proposal), with its state;
    - `driving_day` (owner): each own ride day not departed and not cancelled, with `seats_taken`, `seats_offered` and `pending_count`;
    - `next`: the earliest `held_day` or `driving_day`, or null.
  - `past`: `held_day` and `driving_day` items whose day departed within the last 30 days; no confirmation or rating (AC10).

## 8. Concurrency, the weekday job and expiry

### 8.1 Lock order (replaces TAW-29 8.1 for all ride and seat writers)

Levels, always acquired in increasing order, each level only as needed:

1. `accounts` rows. **TAW-30 functions and the replaced job take them only `for share`**, several in `user_id` order. (`for share` conflicts with an admin's `update … phone_verified` and with TAW-29/TAW-4 `for update`, so those remain authorisation points, and it does not conflict with the `for key share` locks taken by foreign-key checks on inserts into `pilot_events`, `seat_requests` and `cancellations` (F3).)
2. The series owner's `verification_items (user_id, 'car_owner')` row `for share` (accept, the job).
3. `ride_series` row (`for no key update`; `request_seat` and `withdraw_request` take `for share`).
4. `rides` rows (`for no key update`, `(ride_date, id)` order).
5. `seat_requests` rows (`for no key update`, `id` order).
6. Writes to `seat_holds`, `cancellations`, `pilot_events` (their foreign-key checks take `for key share` on the referenced `accounts`, `ride_series`, `rides`, `seat_requests` and `cancellations` rows).

**Lock strengths.** Every row lock that this spec writes as "for update" in sections 5 and 8 is taken as `for no key update`, and every row update by a TAW-30 writer changes no key column. `for no key update` and `for share` do not conflict with `for key share`, so a foreign-key check never waits for a TAW-30 writer (F3). The only row locks stronger than `for no key update` that remain are TAW-29 `publish_ride`'s and TAW-4's `for update` on the caller's own `accounts` row, and the `update`s of an admin or `review_item`, each on a single row.
7. The rider advisory lock (`request_seat` only).

| Writer | Levels |
|---|---|
| `publish_ride` (TAW-29, unchanged) | 1 own `for update`, 2, creates 3–4, events |
| admin revocation, TAW-4 `set_role`/`complete_profile` | 1 one row (`for update` / update) |
| TAW-4 `review_item` | 2 one row (update) |
| `extend_weekday_series` (replaced) | 1 owner `for share`, 2, 3, 4 inserts, 6 holds |
| `request_seat` | 1 rider share, 3 share, 7, 6 |
| `withdraw_request` | 1 rider share, 3 share, 5, 6 |
| `decide_request` | 1 owner + rider share, 2, 3, 4 (accept), 5, 6 |
| `cancel_my_seat` | 1 rider share, 3, 4, 5, 6 |
| `cancel_my_ride` | 1 owner share, 3, 4, 5, 6 |
| `expire_seat_requests` | 5 `for update skip locked`, 6 |

**Why no cycle.** Among TAW-30 writers, level-1 locks are all `for share` and never conflict with each other, so waits happen only from level 3 on, and every writer acquires levels 3 → 7 in increasing order. The writers that take a level-1 or level-2 lock `for update` (publish, admin, TAW-4) hold exactly one such row and then wait only for locks no TAW-30 writer holds in a conflicting mode (publish waits only for its own `verification_items` row `for share`, which conflicts only with `review_item`). `expire_seat_requests` never waits at level 5 (`skip locked`) and at level 6 takes only `for key share` on `accounts`, which `for share` does not block. The F3 cycles (job vs `withdraw_request`; `cancel_my_ride` vs `request_seat`) and the F4 cycle (job vs a two-account decision) are therefore removed: the job no longer takes `accounts` `for update`, and `request_seat` serialises a rider with an advisory lock taken last. This claim is **UNVERIFIED** until the scenarios of 8.2 pass (V6).

**The series row (level 3, `for update`) is the serialisation point for seats.** Every writer that changes `seats_taken` or holds holds it.

### 8.2 Concurrency tests (`supabase/tests/taw30/concurrency.sh`)

Two (three for 11) `psql` sessions on the local stack, paused with advisory locks or `pg_sleep`, as TAW-29's script; both orders where order matters. Every scenario ends by asserting, for every touched ride, the seat invariant and `seats_taken <= seats_offered`; the stored request states; future `held` holds; and the exact count of each event type written. No scenario may end in a deadlock error.

1. Two accepts of different requests for the last seat of a day: one `accepted`; the other returns `seats_unavailable`, stays `pending`; one `request_accepted` event.
2. Weekdays accept vs one-day accept on one of its days, last seat: exactly one succeeds; the weekdays request has holds on all its target days or none.
3. Accept vs withdraw of the same request: exactly one of `accepted` / `withdrawn`; the loser raises `request_not_pending`.
4. Accept vs `cancel_my_ride(…,'all')`: cancel-first → accept raises `request_not_pending` (the anchor's expiry is `ride_cancelled`); accept-first → the cancel cancels the new holds and the request becomes `cancelled`. No `held` hold on a cancelled ride.
5. The job vs a member's `cancel_my_seat(…,'all')`: afterwards the request is `cancelled` and has no `held` hold on any **future** day (departed holds are retained).
6. The job vs a weekdays accept: the member holds every member day (4) exactly once; no day overbooked.
7. Two `request_seat` with the same `client_request_id`: one request, one event; one `replayed: false`, one `replayed: true`.
8. Rider `cancel_my_seat` on day D vs owner `cancel_my_ride` of D: afterwards D is cancelled with `seats_taken = 0`; the rider's call succeeded first, or raised `invalid_days` (weekdays member) or `request_not_cancellable` (one-day request closed by the owner).
9. `request_seat` vs `cancel_my_ride(…,'all')` (F16): request-first → the cancel expires it (`ride_cancelled`, one `request_expired`); cancel-first → `ride_unavailable`.
10. Decline vs withdraw, and decline vs `expire_seat_requests` on a departed anchor: exactly one transition is stored; the loser gets `request_not_pending` (or the job skips/does nothing); one event.
11. `expire_seat_requests` vs `cancel_my_ride(…,'all')` on a series whose anchor already departed: the stored cause is `departed` in both orders (4).
12. The job vs `cancel_my_ride(…,'chosen_days')`: no cancelled day regains a hold; days added by the job for active members are consistent with the invariant.
13. **F3/F4 cycle checks:** (a) the job (holding owner A's series) vs a `decide_request` where A is also the rider of owner B's series and series order is the reverse of account order; (b) `withdraw_request` vs `expire_seat_requests` on the same request; (c) `cancel_my_ride` expiring rider R's request vs `request_seat` by R on the same series. Each completes without deadlock in both orders.
14. A lock wait that crosses departure (F5): session 1 holds the series lock; session 2 calls `decide_request` on a request whose anchor departs 2 seconds later; session 1 commits after departure; session 2 raises `request_not_pending`.

### 8.3 `extend_weekday_series` (TAW-29 function, replaced with `create or replace`)

As TAW-29 8.1, with two changes:

- The owner's `accounts` row is locked `for share` instead of `for update` (8.1, F4). Revocation semantics are unchanged: an admin update of `phone_verified` still waits for, or is waited on by, the job.
- After a day is inserted (row count 1), for each active membership of the series whose `anchor_date <= ride_date` (F8), in `id` order, insert a `held` hold and add its seats to `seats_taken`. Because acceptance keeps the members' total within `seats_offered` (5.4 step 6.4) and a new day has no other holds, the TAW-29 check cannot fail; if it did, the run fails and rolls back.

Its grants are unchanged and re-asserted. A pgTAP case covers the backfill F8 describes: a series day skipped earlier for the ±60-minute rule is created after the conflicting ride is cancelled, and only members whose `anchor_date` is on or before it get a hold.

### 8.4 Expiry (AC4)

- Readers show `taw30_request_state` (4), so a request is `expired` the moment its anchor departs or is cancelled.
- `public.expire_seat_requests()` (owner-only) stores it: `pending` requests whose anchor `departs_at <= clock_timestamp()`, `for update skip locked`, each set to the values `taw30_request_state` returns, with one `request_expired` event each. Returns the count. A second immediate run returns 0.
- `pg_cron` job `taw30-expire-seat-requests`, `*/5 * * * *` (Proposal), created by the migration like TAW-29's job (unschedule by name, then schedule). Local creation: plan step; hosted: **UNVERIFIED**, owner-run (V3).
- `cancel_my_ride` stores expiries synchronously (5.6 steps 7–8).

## 9. Not changed from TAW-29

`publish_ride`, `list_rides`, `get_ride`, `resolve_shared_ride`, the projection, the share link. A ride whose seats are all held is `full` and leaves the list by TAW-29's rule; a non-party opening it sees D4a (section 7).
